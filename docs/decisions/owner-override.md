- It lifts nothing else: not the settings-write ask of `agent-model-cap`, and no other rule (rule `roles-opus-override-guarded`).
- It reaches agents, as a timed `override` does. The turn grant below does not. It covers only the session where the owner typed it.
- On the keyword route the unit is required. `opus 4` may name a model, so it grants nothing there.
- The keyword counts only as the whole prompt, in any case. Any other text after `opus` grants nothing on this route. The plain ask below is the other route.
- The Opus keyword has the same gate as the `override` keyword: the payload `source` must be absent, null or `user`, and the prompt's own record must pass the owner-turn test (Owner Q1, the Opus gate). `opus off` is ungated, because it only narrows: a harness `opus off` removes the Opus file and ends no one-act override. A typed `opus off` also ends a pending one-act override, with or without an Opus file. `opus 2h please` grants nothing and makes no judge call.
- The timed file is `state/override/opus/<session>.json`. It has the format of the override, with kind `opus` and one more field, `role`. Its `until` is always set, from the length the owner typed. Nothing removes the file at session end: the SessionEnd sweep (`janitor/session_end_sweep.py`) names no override file. So for its session id, a timed grant lasts to its `until`. Unmeasured: whether a resumed session keeps its session id. If it does, the grant carries over until its `until`. It sits in its own folder, beside the override and the turn file, so none replaces another, and `override off` leaves an Opus override in place. `state/` is frozen against Claude's writes, so a session cannot grant itself an override.
- An Opus spawn that both overrides cover uses the Opus override, so a one-act `override` stays unspent.
- `guard.log` gets one line per grant (`opus-grant`, with the role and the end, or for a turn grant its backstop), per lift (`opus-override`), per end (`opus-off`), and per unreadable file (`opus-unread`).
