# A git write after a cd joins with `&&`

## The ruling

Rule `git-after-cd` in `hooks/guard.py` refuses a git write that follows a `cd` joined to it by `;`, a newline or `||`.

A write is one of these:

- A verb of `SESSION_HOME_GIT_VERBS`, `push` or `update-ref`.
- A file verb of `GIT_FILE_VERBS` (`rm`, `mv`).
- A `fetch` that writes a branch (`fetch_moves_branch`).
- A `branch` with a force, move or delete flag.
- A verb of `GIT_AFTER_CD_EXTRA_VERBS`: an `add` that is no dry run, a `tag` that names or deletes a tag, a `config` that sets or unsets a value (not `--get`, `--list` or a bare key), and `worktree add`. They are a second list because rule session-home pins `worktree add` as allowed.

A call whose argv names a read, such as `push --dry-run` or `push -n` (`read_verb`), is no write.

1. When the cd fails, the shell stays in its folder and a `;` runs the next command there. The write then lands in the primary checkout the session meant to leave alone.
2. The rule reads `cd_walk(...).stranded` for each write, with `failed_cd_stays=True`. A missing folder leaves the shell where it was, so `stranded` is true until a cd to a full path, home or `-` lands. `cd_walk(...).skipped` marks a segment that a failed `&&` chain never runs.
3. The refusal tells the session to join the cd to the write with `&&`, or to leave out the cd and use `-C` with a full path. It names no target.

The rule also refuses a `git push` that runs after a `;`- or newline-joined command whose failure the push cannot see, with or without a cd (coordinator step push-after-check-semicolon, 2026-11-08 09:51 CST; lane pick 2026-11-08 10:38 CST, which replaced the pick of 10:01 CST). A failed check does not stop a push joined to it by `;` or a newline. Incident 2026-11-08, PR #2098: a check and a push were joined by `;`, and the push ran after the check failed. The refusal of a `;` or newline join tells the session to join the commands with `&&`. A pipe that hides its check prints its own remedy. When `&&` joins it to the push: start the command with `set -o pipefail;`, or run the check alone and join it to the push with `&&`. When `;` or a newline joins it, a failed pipe does not end the shell, so `set -o pipefail;` alone is no remedy: it names `set -eo pipefail;` or `&&` (lane pick 2026-11-08 19:31 CST). A `||` before the push's chain prints its own too: join the check to the push with `&&` alone, or stop the shell with `|| exit 1`. An `|| exit` that reads another command's status (`echo $(make x) || exit 1 && git push`) prints a fourth, which names `&&` and never `|| exit 1`, since the command holds one already. A push in an `else` or `until` body, or in the `then` body of an `if !` or the body of a `while !`, prints a fifth that names its opener (step 6). Each reason has one constant in `GIT_PUSH_REASONS`, and none names a target (lane pick 2026-11-08 18:07 CST). `git_push_after_check_hit` reads the same segments and ends as `git_after_cd_hit`.

A quoted delimiter (`<<'EOF'`) holds literal text, so it stays a data source.

The push check walks back from the push:

1. It goes back over the push's `&&` chain to the chain's start. A `||` or `|` before that start is no `;` join, but three shapes of it refuse (`_push_hidden_by_tail`; lane picks 2026-11-08 15:07 and 16:46 CST).
   - A `||` whose first step after it is no exit. That step runs on the failed check, may succeed, and the `&&` chain goes on to the push, whatever steps stand between them. `pytest -q || echo x && git push`, `pytest -q || echo x && git add -A && git push`, `pytest -q || command echo x && git push`, `pytest -q || /bin/echo x && git push`, `pytest -q || (echo x) && git push`, `pytest -q || echo x | cat && git push` and `pytest -q || cat log && git push` are refused. `pytest -q || exit 1 && git push` passes, since the exit stops the shell, unless the exit reads another command's status (`echo $(make x) || exit 1 && git push` is refused, as in step 5). `cd X || echo x && git push` is refused by the cd walk (`git_after_cd_hit`), since the failed cd leaves the shell in place and the echo lets the chain run on; the push check itself finds no check before the `||`.
   - A push that runs only when a check fails: the push is the step after the `||` (`pytest -q || git push`), or stands in the `{ }` group that is that step (`pytest -q || { echo x && git push; }`). A `{` group that closes before the push is not read. A cd or other inert command as the left side is no check.
   - A pipe whose stage before the last is a check, in the `&&` chain before the push: `pytest -q | tail -5 && git push`, `make check | tee l && git push`, `{ make check; } | tee l && git push` (a stage that closes a `{ }` group, or an `fi` or `done`, counts when the group holds a check; a group of git calls does not). A pipe's status is its last stage's, so the `&&` runs the push whatever the check did. `set -o pipefail` (or `set -eo pipefail`) sure to run first, read like the `set -e` of step 4, makes the pipe fail with its check, so the same pipe passes. A `set +o pipefail` turns it off. A print step (`echo`, `printf`, `true`, `:`) with no substitution is no check, so `printf '%s' "$m" | git commit -F - && git push` passes. A call of the version-control tool is no check here (`<vcs> commit -m m 2>&1 | tail -1 && <vcs> push` passes), nor on the left of a `||` (`<vcs> push || <vcs> pull --rebase && <vcs> push` passes, a retry with no check; `pytest || <vcs> pull --rebase && <vcs> push` is refused): it is the step the chain carries on, and the roadmap-note command of the env heredoc case (test `env: heredoc-allow: the incident python write`) ends in that form.
   A line that ends in `&&`, `||` or `|` joins the next line by that operator, not by the newline.
2. If a `;` or a newline stands before that start, it looks at the command before it.
3. A cd, `exit`, `set`, `true`, or an `export`, `echo` or `printf` whose words run no substitution (or a group or `if` made only of them) is skipped, and the walk goes on from it over its own `&&` chain. That chain must be inert too, so `pytest -q && cd X; git push` is refused.
4. A lone command after a `set -e` sure to run is skipped too, since its failure ends the shell. The lone command stands at the top level, outside any group, `if`, loop or `( )`, and outside any `&&` or `||` list, pipe, `!` or `&`. So `set -e; pytest -q; git push` passes, and `set -e; pytest -q && true; git push` is refused. A pipe that ends the `;`-joined step passes when a `set -o pipefail` (or `set -eo pipefail`) sure to run stands before it too, since a failed stage fails the pipe and ends the shell: `set -eo pipefail; pytest | tail; git push` passes, and `set -e; pytest | tail; git push` is refused. The pipe must start its own `;`-joined step.
5. A command that exits on failure protects itself and the whole `&&`, `||` or `|` list before it, and nothing before that list: `pytest || exit 1`, `pytest || { echo bad; exit 1; }` and `if ! pytest; then exit 1; fi` pass when nothing stands before them. The walk goes on back past them, so `pytest -q; <fetch> || exit 1; <push>` is refused, with a fetch and a push in the two places. A substitution in a command the exit covers is a check it does not cover, since the exit reads the command's status, not the substitution's: `echo $(make x) || exit 1; git push` is refused (lane pick 2026-11-08 15:07 CST). Two commands hold their substitution's status, or read only its output, so the exit reads the check: a bare assignment (`out=$(make x) || exit 1; git push`) and a `[`, `[[` or `test` command whose substitutions all run a git call (`[ -z "$(git status --porcelain)" ] || exit 1; git push`, true only on a clean tree). Both pass. A test of any other command's output passes when that command fails silently, so `[ -z "$(make x)" ] || exit 1; git push` is refused (lane pick 2026-11-08 17:17 CST). A pipe before the `||` hides its check, since the exit reads the pipe's last stage: `make check | tee l || exit 1; git push` and `make check | tee l || { exit 1; }; git push` are refused unless a `set -o pipefail` is sure to run first. A `{ exit N; }` group after `||` is an exit tail, also when `&&` joins the push to it: `pytest || { exit 1; } && git push` passes. `cd "$(git rev-parse --show-toplevel)" || exit 1; git push` is refused, since a failed substitution leaves `cd ""`, which succeeds in place. An exit after a `||` step that cannot fail (`echo`, `true` or `:`, bare, behind `command` or a path, or in a `( )`, as `(true)`) never runs, so `make a || echo bad || exit 1; git push` is refused. A step that can fail is a fallback the exit reads: `make a || make b || exit 1; git push` passes. Only a bare `exit` counts: `|| return` and `|| (exit 1)` do not stop the shell, and neither does an `exit` inside a `( )` group, as in `( pytest -q || exit 1 ); git push`, `( pytest -q || { echo bad; exit 1; } ); git push` and `( if ! pytest -q; then exit 1; fi ); git push`. The `if !` body may stand on the lines after the test, and may print before it exits: `if ! pytest -q; then echo bad; exit 1; fi` passes on one line or over three. Only `echo`, `printf`, `true` and `:` with no pipe or `||` count as that print, and a substitution in it is fine, since the step's status is its own: `if ! pytest -q; then echo "$(date)"; exit 1; fi` passes. A step joined to the exit by `&&` must not fail, since a failed step skips the exit. So it counts only when it has no redirect: `then echo bad > /no/dir && exit 1` is refused. Only `>&2`, `1>&2` and `2>&1` count as fd copies that cannot fail: `then echo bad >&2 && exit 1` passes (lane picks 2026-11-08 14:34 and 15:07 CST). Any other descriptor may be closed, so `then echo bad >&3 && exit 1` and `then echo bad >&- && exit 1` are refused. `printf` can fail (`printf '%d' abc` returns 1), so it is no print step before `&&`: `then printf '%d' abc && exit 1` is refused. Before `;` it still counts. A redirect on a `;`-joined print is fine. A substitution the split cut open (`echo $(a; exit 1)`) is no print step. Any other step, and an `exit` after `else`, `elif` or `fi`, is no exit tail.
6. The test of the compound that holds the push guards the body, and nothing before the compound. The body opener (`then`, `do`, `else`, `elif`) may stand on the push's line or on the line before it. The walk goes on back past the compound's head (`if`, `for`, `while`, `until`) to any earlier `;`-joined check: `pytest -q; for r in a b; do git push; done`, `pytest -q; until false; do git push; done`, `pytest -q; if <fetch>; then <push>; fi` and a push in an `elif` or `else` body are refused. With nothing before the compound the push passes, as in `if pytest -q; then git push; fi`. A pipe in the test of a `then` or `do` body hides its check as in step 1 (`_push_test_hides_check`): `if make check | tail -3; then git push; fi` and `while make check | tail; do git push; done` are refused, unless a `set -o pipefail` is sure to run first. A `fi` or `done` between them closes that body, so `if pytest; then :; fi; git push` is refused. A push in an `else` body runs when the `if` test fails, and a push in an `until` body runs while the test fails, so each refuses when a test of the compound is a check (`_push_body_runs_on_failure`, lane pick 2026-11-08 18:50 CST): `if pytest -q; then echo ok; else git push; fi` and `until pytest -q; do git push; done` are refused, with a reason that names the opener (`else`, `until`) and, for `else`, the `then` branch, and `&&`. The tests are the `if` test, each `elif` test, or the `until` test. A push in the `then` body of an `if !` and in the body of a `while !` runs when the check fails too (lane pick 2026-11-08 19:31 CST): `if ! pytest -q; then git push; fi` and `while ! make check; do git push; done` are refused, with a reason that names that opener. There the test just before the body counts, and only a test with a `!` (the last `elif` test for a `then` body). A `!` test of a git call, a `[` condition or a cd is no check. A test is a check as the `||` rule reads it: not inert and no git call. A `[`, `[[` or `test` command is a condition, no check (`if [ -n "$X" ]; then :; else git push; fi` passes), and a test with `!` runs the `else` body when its command passes (`if ! pytest -q; then exit 1; else git push; fi` passes). A `while` body and a `then` body are guarded by their test, as before.
7. A group opener `{` or `(` is walked into. So `{ pytest -q; git push; }`, `( pytest -q; git push )` and `cd X && { pytest -q; git push; }` are refused. The opener is read past when a compound stands inside it: `pytest -q; { for r in a b; do git push $r; done; }` and `pytest -q; ( if true; then git push; fi )` are refused, since the compound's own test covers only its body.
8. Any other command refuses, a subshell `( ... )` included: `cd X; (pytest -q); git push` is refused.

Forms the push check passes:

- A push with nothing before it, or with only skipped commands before it: `cd X; git push`, `set -e; cd X; git push`, `cd X || exit 1; git push`, `if ! cd X; then exit 1; fi; git push`.
- A push that starts a compound body, on the opener's line or on the next one: `if pytest; then git push; fi`, `while pytest; do\n  git push\ndone`.
- A chain joined by `&&` over lines: `pytest -q &&\ngit push`.
- A `--dry-run` push, a read.
- A check joined to the push by `&&` alone.

A `git add`, `git commit` or other command before the `;` is not skipped, so `git commit -m m; git push` is refused.

Allowed forms:

- `cd X && git push`: a failed cd stops the chain. The skip covers a whole compound that follows the `&&`: a `{ ... }` group, an `if ... fi`, a `for`, `while` or `until` loop through `done`, across `;` and newlines, so `cd X && { git add -A; git commit -m m; }` passes. Every opener and closer in a segment counts, so nested ones do: `{ { git add; } }`, `{ for f in a; do git add; done }`. A closer with a redirect attached counts once (`}>/dev/null`, `done>/dev/null`). A word counts only as the shell reads it: a quoted `"done"`, `echo "done }"` and `done_x` open and close nothing. The skip ends when the compound closes: a `;` or newline after it runs in the stranded folder, so `cd X && { git add -A; }; git push` is refused. A `case` is not read, so the skip ends at its first `;`.
- `if ! cd X; then exit 1; fi; git push`: the test passes when the cd fails, `exit` runs, and the shell ends. The `then` body must reach a bare `exit` through steps that only print (`echo`, `printf`, `true`, `:`): `if ! cd X; then echo bad; exit 1; fi; git push` passes. With any other step first, as `then make x; exit 1`, or no exit, as `then echo no`, the write after `fi` is refused.
- `set -e; cd X; git push`: under `set -e` a failed cd that stands alone, ending in `;` or a newline, ends the shell. `set -eu`, `set -o errexit` and a `set -e` on its own line count, but only a `set -e` sure to run: a top-level segment, first word `set`, not inside a `{ }`, `if`, loop, `case` or function body or a `( )`, not after `&&` or `||`, not piped or in the background. Any `set +e` (or `+o errexit`) before the cd turns it off again, wherever it stands, even in a function nothing calls. A cd before or after `&&`, `||` or `|` (it may never run), inside `( ... )`, or inside a group, `if` or loop, does not count as the exit. The same holds for the `if ! cd X; then exit` form after `&&` or `||`. Options end at the first word that is not one, so `set -- -e` and `set -- ""` set nothing.
- `cd X || exit 1; git push`: the shell exits when the cd fails. The `exit` is read as the first command after the `||`, bare or as a `;`-joined step of a `{ ... }` group. A top-level `return` does not stop bash, so `cd X || return 1; git push` is refused. So are `cd X || (exit 1); git push`, because a subshell's `exit` ends only the subshell, and an `exit` in a pipe, as `cd X || exit 1 | cat; git push` or `cd X || { exit 1; } | cat; git push`.
- `if cd X; then git push; fi`: the `then` body runs only when the cd landed. An `else` body and the commands after `fi` run in the stranded folder and are refused.
- `git -C /full/path push`, with or without a cd before it. A `-C` that holds a variable is unknown and passes.
- A read: `status`, `log`, `branch -l`, `stash list`, `tag -l`, `config --get`.
- A cd inside `( ... )`: its scope ends at the `)`. The folder it names is read without the `)`. The shell outside is still stranded after the `)`, so `cd X; (cd /tmp) && git push` is refused, and `cd X; (cd /tmp && git push)` passes, because the chain inside runs in `/tmp`.
- A cd that lands, or a cd whose word holds a variable: the folder is known or unknown, never stranded.
- A cd, a git word or a comment opener inside quotes or after `#`.

Risk kind: incident 2026-11-07 ~16:15 CST. A session ran `cd <gone worktree> && <vcs> status; <vcs> fetch; <vcs> checkout -B ...; <vcs> merge ...`. The cd failed, so the `;`-joined writes ran in the primary checkout.

Limits:

- A redirect to a file before `&&` in an `if !` body ends the exit tail, `>/dev/null` included, though bash exits first when the file opens. The rule fails closed; a `;` join in place of the `&&` passes. Only `>&2`, `1>&2` and `2>&1` (`FD_COPY`) count as fd copies, so `then echo bad >&2 && exit 1` passes. A copy of any other descriptor fails closed, even one a script opened (`exec 3>log`).
- `A || make x && push` is refused like `A || echo x && push`, though `make x` may be a fallback the owner meant (`git fetch || git fetch && push`). The rule fails closed. In the exit form the two differ: `A || make b || exit 1; push` passes (the exit reads b), `A || echo b || exit 1; push` is refused. A `{` group that closes before the push is not read, and a push in the group that is the first step after the `||` is refused (`A || { echo x && push; }`). Not read either: a `cd` as the whole left side (`cd X || echo x && push`), which `git_after_cd_hit` judges.
- An assignment is read as holding its substitution's status only when it is the whole segment (`out=$(make x)`, or several such words); `out=$(make x) cmd` and `export out=$(make x)` are not. A `[ ]` or `test` command with two substitutions passes when each runs a git call, so `[ "$(git rev-parse HEAD)" = "$(git rev-parse @{u})" ] || exit 1; push` passes. One substitution that is no git call refuses.
- The `else` and `until` read (step 6) judges the compound's own tests only, at the compound's own level. A `!` anywhere in a test segment clears that segment, so `if ! A && B; then X; else git push; fi` is judged by B alone. A `[ ]` test is never a check, so `if [ -f x ]; then X; else git push; fi` passes though the push runs when the file is missing. A `case` arm and a `for` loop have no failing test and are not read.
- A `;` or newline after a pipe of data sources still refuses: `ls | head -1; git push` is refused as a `;` join, since `head` is a command before the `;`. Only the `&&` and compound-body forms read the data-source list (`_pipe_hides_check`).
- A pipe that holds a git call, after a `;`-joined check, still passes: `pytest -q; git commit | tail -1 && git push` is allowed, though a failed pytest does not stop the push. The env heredoc incident case pins that form as allowed, so the walk stops at such a pipe.
- A `then` or `while` body read as a negated check (step 6) judges the segment of the test, so `if ! A && B; then git push; fi` is judged by A alone, as the `else` read is.
- The heredoc substitution read (`_mark_heredoc_substitutions`) marks every heredoc operator on the header line of a body that runs one, so a second heredoc on that line is marked with it. It fails closed.
- A cd that fails only at run time, not at check time, is not seen. A folder that exists when the guard looks is trusted.
- A relative `-C` joins onto the stranded folder, so it is refused; a `-C` that holds a variable is not read.
- A segment the tokenizer cannot read, because a quote is cut in it, is unknown and passes. An interpreter's heredoc body is dropped from the push check before it reads (`git_push_after_check_hit`), so a lone quote in a python body hides no `;` after it. The cd check reads the body, and a quote cut in it leaves its segment unknown.
- A cd into a folder an earlier `;` segment creates is refused: `mkdir -p X; cd X; git commit` and `git worktree add ../x; cd ../x; git commit`. The folder is not there when the guard looks. The `&&` form passes.
- A cd to a variable is not judged: `cd "$WT"; git push` passes. Failing closed would also refuse `cd "$REPO"; git status` in normal work. Debt `git-after-cd-variable-cd` holds the gap.
- An `|| exit` is read only as the first command after the `||`, or a `;`-joined step of a `{ ... }` group. An `exit` behind an `&&` inside the group, or in a function, is not read, so the write after it is refused. `cd M || { echo a && exit 1; }; git push` is refused though bash exits first. The rule fails closed, and the `&&` remedy passes.
- errexit fails closed, so these are refused though bash exits first: a `set -e` inside a group, `if`, loop, function or `( )` (`{ set -e; }; cd X; git push`, `f() { set -e; }; f; cd X; git push`), a `set -e` after `&&` or `||` (`true && set -e; cd X; git push`), and a failed cd inside a group under `set -e` (`set -e; { cd X; }; git push`). A `set +e` anywhere, in dead code too, turns errexit off. Only the opener and closer words are read: `case` and `esac`, `select` and a function's `{` count for errexit only, and a function that is called is not followed.
- The compound count takes a word that starts with a quote as text (`_quoted_opens`). A keyword quoted after its first character, `i"f"`, reads as the keyword. When the two readings of a segment differ in word count, no word is marked, so a quoted `"{"` at the head of such a segment opens a compound.
- A crash in `cd_walk` read with `failed_cd_stays` reads as stranded, so the write is refused, and a `guard-crash` line is logged. The guard otherwise fails open on a crash.
- `echo x | ( cd X; push )` and `cd X || { push; exit 1; }` are not read as stranded cases.
  Fix: none — a pipe into a subshell cd, or a push inside the || block, is not a form Claude writes by mistake (guard-guards-mistakes-only). Until: 2026-11-21
- `f() { cd M; push; }; f`, `function f { cd M; push; }; f` and `case x in x) cd M; push;; esac` are not read: a cd inside a function body or a case arm.
  Fix: none — a cd and a push inside one function body or case arm is not a form Claude writes by mistake (guard-guards-mistakes-only). Until: 2026-11-21
- An `if` is read only when the cd is the whole test and the next segment opens the `then`. `if cd X && Y; then`, `while cd X; do` and `elif` are not read, so the write in their body is refused.
- A `tag` is a read when it holds a listing flag (`-l`, `--contains`, `--points-at`, `--merged`, `--sort`) or no word. A `config` is a write when it names a key and a value, or holds a write flag. A `worktree` verb other than `add` is not a write here: `worktree remove` and `prune` are judged by their own rules.
- A quoted `>` in an `echo` is text, not a redirect (rule conflict-markers, `_chain_safe`). A backtick or `$(` inside it still counts as a step that may change the tree.
- PowerShell is out of scope. The lane brief named Bash, and `cd_walk` reads Bash joins.
- A `bash -c` or `sh -c` body is read as its own script by the push check (`inline_script`), so `bash -c "pytest -q; git push"` is refused. The cd check does not walk it (`guard-guards-mistakes-only`).
