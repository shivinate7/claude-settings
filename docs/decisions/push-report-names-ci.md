# A report after a push names the head's CI state

## The ruling

A turn that pushes a head names that head's CI state in its report. This closes the gap that a report could name a push before its checks finished. The owner's ruling of 2026-11-07 13:20 CST says a found gap gets a fix, not a note (decision `cull-rules`, the owner's cull of rules). A Stop hook cannot wait without polling, so it reads once: the report must not claim a pending head as done.

- `lint/report_guard.py` names a push after the last human message: `git push` (not a dry run, a delete or a tag push) or the GitHub MCP `push_files`, `create_or_update_file` or `delete_file`. Merges are out; the merge-checks rule covers them. Only the newest head of each branch counts.
- `hooks/ci_wake.py` `head_state` is the one home of the read, a sibling of the CI wake in decision `ci-wait-reads-run-status`. A branch with no open PR, a draft PR, or a head the PR has moved past needs no CI ("none"). A ready PR drops skipped runs (as `wait_for` does), then `judge_runs` judges the rest. With no run listed, one workflow-list read (`no_workflows`, the home the watch uses) decides: a repo with no workflows reads none. Then a push that no workflow path filter matches reads none. Every workflow file at the head is read. Each must have only dispatch or schedule events, or a push event whose `paths` or `paths-ignore` filter fails every changed file (`workflow_runs_for`, `push_may_start_run`). A form that reader does not parse, a read that fails, and a new branch (no old head to diff from) keep a run due. Otherwise a ready PR with no run yet is pending. A PR read that still names the head before the push (the REST read lags) is not a moved-past head: the pushed head's runs are read direct. A push to main reads the head's runs direct; with no run listed and workflows present it is unknown.
- Red beats pending: a head with one red run and one running run reads red. A cancelled run alone reads red.
- A short name with no `refs/` prefix is a tag, and names no head, when the output has a `[new tag]` line for it and no ref line. A ref line, a ref-update or `[new branch]`, is still a branch head when a tag of the name is pushed too. With no such line (a wrapper prints none), a remote-tracking ref of the name makes it a branch and names the head. Else a local branch of the name does the same, so the first push of a branch on a single-branch clone names the local head. This holds also when a local tag has the name: the branch is checked, and its head is the one named, never the tag's. With neither, a local tag makes it a tag, and so does a bare refspec (`git push origin v1.0`, no `:`). That last case is the ambiguous one. A bare name no ref anywhere backs reads as a tag, so a wrapper-printed push of a branch this clone never held passes unchecked. The `:` form (`HEAD:name`) stays a branch. A failed read does not drop the name: it reads unknown.
- A push is read from its ref lines: `! [rejected]` is a ref line anchored at a line start, so a branch named with the word rejected is checked, and the accepted refs of a multi-ref push still count. `cd <dir> && git push` reads the head in that directory (`guard_core.dir_before_segment`, the guard's one reader of `cd`).
- What the report says, per state:
  - Pending: `CI running on <sha7>` under Next, and no BUILT or RECORDED Done item that names the head. A Done item may cite the PR or an earlier commit.
  - Red: `CI red on <sha7>`, anywhere in the reply, and no BUILT or RECORDED Done item that names the head, as for pending.
  - Unknown, a read that failed or ran out of budget: `CI unknown on <sha7>`, anywhere in the reply. A head no read can name reads unknown, never dropped. The line names the branch, or `HEAD` when the branch read of a bare push failed, and the block reason carries the cause: a spent budget, a failed branch read or head read (its own message: the tool missing, timed out), no remote-tracking ref for the branch, or a URL remote, which updates no remote-tracking ref (a URL push with no ref line, or with a `[new branch]` line, reads unknown on the branch).
  - Green or none (no open PR, a draft, a repo with no workflows): no line.
- The missing-report marker also holds each head's state, so the rewrite makes no second read. A block for the CI line alone leaves the same marker, flagged `ci-only`: its rewrite is checked for that line and nothing else.
- Measured 2026-11-07 14:12 CST (cloud): the REST read of a branch's open PR and the run list of a commit both work (route rows `ci-pr-read-gh-api-cloud`, `ci-runs-list-gh-cli-cloud`, `ci-runs-read-gh-api-cloud`).

Cost: only on a Stop after a push that is not a `stop_hook_active` Stop, inside the Stop hook already running. At most 3 gh processes per head (the PR read, the run list, and the workflow list only when the run list is empty). A push with no ref line adds 1 git process per name when its remote-tracking ref names the head, else at most 3 per name (the remote ref, the local branch, then the tag, read only when no local branch names a head). A ready PR with no run listed and a workflow list that shows workflows adds 2 git processes and 1 per workflow file, to read the path filters. It adds 1 more to read the branch of a `HEAD` refspec or a push with no refspec. A short head on main costs 1. All reads, git and gh, are inside one 20 s budget with 8 s at most each (`ci_wake.Budget`, a clock seam), under the 35 s Stop timeout in `settings.json`. It writes only the existing marker file. It starts no timer and no long-lived process.

Known limit: the shape of a `push_files` result is unmeasured. The guard reads a 40-hex `sha`, then `commit.sha`, then `object.sha`; a result with none of these is not checked. `update_pull_request_branch` names no branch, so it yields no head. The path-filter reader skips a `pull_request` event's own filters and a push `branches` filter, so those keep a run due. An unquoted `echo git push ...` and `cd <missing dir> && git push` read as pushes, a rare false alarm. A `cd $VAR` is not resolved: the push reads the hook's cwd.

A check that did not run reads `Push-CI guard: UNKNOWN, the check did not run` in the systemMessage, a note and never a block (rule `verification-report-unknown-reads`). It fires when the CI check raises, and when `guard.py` does not load on a turn that may push. Without the parser, a Bash command whose words hold git and push counts as a push for the note alone.

Why: a session could report a push as done while its checks still ran or had failed.
