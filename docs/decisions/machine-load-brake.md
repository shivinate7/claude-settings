# The machine-load brake

## The ruling

Owner, 2026-10-21 (spec), 2026-10-22 (foreground), 2026-10-23 (disk) and 2026-10-25 (CPU dropped: a 200 ms sample is noise; memory and disk are what stall a machine). Locally, a call that starts a lane or an agent reads the machine's load. A busy or full machine refuses new lanes and agents (disk is the smaller of a share and a GB cap). Owner, 2026-10-26 (incident) and 2026-10-27 11:45 CDT (option a): locally, a running agent stops at full only, never at busy. The brake lives in `hooks/guard.py` (`read_load`, `load_hit`, rule `load-brake`), on every local device.

- **Readings.** `read_load()` reads memory in use as a share of the machine's memory, and free GB and total GB of the home drive (2**30 bytes to the GB, never clamped). It reads no CPU, and counts no claude process and no running agent.
- **Busy.** Memory over 85%, or disk free under the smaller of 10% of the disk and 15 GB. A 926 GB disk: busy under 15 GB. A 100 GB disk: busy under 10 GB. Any Workflow is refused. An Agent or Task call passes only when it leaves `run_in_background` out or sets it to exactly false. Any other present value (true, "true", null, 1) is refused. In the desktop app a left-out call still runs in the background and the field is not offered, so busy no longer slows Agent calls there. Only full does. The owner chose this on 2026-10-22: a memory spike must not stall a session that cannot choose a foreground form.
- **Full.** Memory over 95%, or disk free under the smaller of 5% and 5 GB. Every Agent, Task or Workflow call is refused. A background lint start (`merge --lane-lint`, `bin/ci-job --lint`) is refused at a full machine the same way (owner, 2026-11-19 21:30 CST). The `load-brake` family pins the full-disk case.
- **Not covered: `start_session`.** No PreToolUse hook sees a `start_session` call, because a hook on it makes the desktop app show its start card on every start (decision `start-session-not-pretooluse`). The brake (`guard.py` `load_hit`) never reads the load for it at PreToolUse, at busy or at full. The started session's SessionStart hook (`start_check.py` `flag_text`) reads the load once at a local startup, and flags a start at full (decision `start-checks-after-call`, the start checks run in the started session). It flags; it does not stop. Whether the desktop app delivers the flag to a `start_session` session is unknown (debt `start-session-load-unbraked`, open). `create_session` is not read either (debt note `load-brake-skips-create-session`).
- **The refusal** names each reading that tripped it. At busy, an Agent or Task call is told to wait for the load to drop (memory) or free disk space (disk). It is also told to make the call an Agent call that leaves `run_in_background` out or sets it false. A Workflow has no foreground form, so it gets only the wait or free-disk remedy.
- **A read error counts as normal.** On Linux, memory is read from `/proc/meminfo` (MemTotal, MemAvailable), so memory and disk can both trip the brake there (owner, 2026-11-19 21:30 CST: "read memory on linux if u can"). A reading that fails or cannot be read, `/proc/meminfo` included, is unread, and one unread reading hides no other.
- **Linux memory beside Mac and Windows (session pick, 2026-11-19 23:08 CST; not an owner ruling).** On a local Linux session the busy refusal (memory over 85%) and the running-agent and lane-session refusals (memory over 95%) now fire from the `/proc/meminfo` read, as they do from the OS counter on Mac and Windows. A cloud session stays exempt from busy and from the running-agent and lane-session refusals.
- **Running agents.** On a local session, an agent's own Bash, PowerShell, Edit, Write, MultiEdit or NotebookEdit call reads the load once (`running_agent_hit`, `RUNNING_AGENT_TOOLS`). Full refuses it and tells the agent to stop and report. Busy lets it run. The hook already runs for each such call, so the brake does not depend on the orchestrator's turn: an agent stops even while its orchestrator waits on the owner. A call is an agent's when its payload carries a valid `agent_id`.
- **Lane sessions.** Owner, 2026-11-04 07:56 CST (item 168 a): a lane is a session, local or cloud (decision `lanes-start-as-agents`, a lane is a session). On a local session, a lane session's own shell or file write is braked as an agent's is (`lane_session_hit`). Full refuses it. The lane is told to end its turn and send the reading to its parent (`send_message` `@parent`), which frees space. Busy lets it run. A session is a lane session when two things hold. `CLAUDE_CODE_REMOTE_SESSION_ID` names its own id. Its own newest `get_session` record carries `cs-build:lane` and no other `cs-build:` tier tag, with no `set_session_tags` call on it after the record. A `parent_session_id` alone makes no lane: triage and the batch runner carry one. `hooks/session_start.sh` prints the tier line to any session with an own id, so a local lane reads its own record at start. No own id, no record, or a read error counts as no lane. The load is read first; the transcript is read only at full.
- **Not covered for lane sessions.** A local session with no `CLAUDE_CODE_REMOTE_SESSION_ID` (such as one `start_session` starts) has no own record to read, so a lane of that kind is braked only at its start. Whether a Remote Control lane on the Mac sets that variable is unmeasured. A command already running (a long build) keeps writing; only its next call is refused. An MCP tool that writes files (such as a GitHub file push) is not read. At full an agent or lane cannot commit its last pass either, so that pass stays uncommitted in its worktree until the orchestrator frees space.
- **Full only.** A running agent or lane session is refused only at a full machine: memory over 95%, or disk free under the smaller of 5% of the disk and 5 GB. A busy machine never stops it.
- **Rule exception.** The rule file `.claude/rules/hooks.md` (loaded under `hooks/**` and `janitor/**`) is the home of an exception to rule `outcomes-mechanize-rules`: an agent's own write may read the machine load once, inside the guard hook already running for it. Locally, a lane session's own write may too. On a local session, its cost is one memory read and one `statfs` per agent write. The same cost applies per write of a session with an own id. A transcript read is added only at full. It starts no process, writes no file and sets no timer. The rule file cites this decision.
- **The orchestrator is never braked on its own shell or writes, except a background lint start.** A coordinator, triage or batch-runner session carries no lane tag, so `lane_session_hit` passes it. It is the session that frees the disk, so a recovery does not depend on the full disk it recovers (`verification-recovery-independent-of-state`).
- **Which calls read.** On a local session, Agent, Task and Workflow read once each. On a cloud session the same three read the disk and memory once each. An agent's shell or file write reads once. So does the shell or file write of a session with an own id. A background lint start on Bash (`merge --lane-lint`, `bin/ci-job --lint`) reads once too, on a local session and on a cloud one. A cloud lint start reads the disk from `/` and memory, as a cloud Agent start does. A lint start is a call that sets `run_in_background`, a lint a trailing `&` sends to the background, or a lint inside `bash -c`, `sh -c` or `( ... )` under either. A foreground lint with no `&` is no start and reads nothing. No other call reads load.
- **Cloud sessions.** Owner, 2026-11-18 14:45 CST (goal E9, ruling on the cloud full disk), and owner, 2026-11-19 21:30 CST ("read memory on linux if u can"), owner confirmed in chat, 2026-11-19 22:25 CST ("yes q1 covered cloud too"): a session with `CLAUDE_CODE_REMOTE=true` brakes a new Agent, Task or Workflow start, and a background lint start, at a full disk or at memory over 95%, and nothing else. `load_hit` reads the disk once, from `/` (`shutil.disk_usage` free, which is df "available", `f_bavail`), and refuses under the full point: the smaller of 5% of the disk and 5 GB, the same constant as a local session. A cloud session runs Linux, so `load_hit` also reads memory once, from `/proc/meminfo` (MemTotal, MemAvailable), and refuses at memory over 95%, the same full point as a local session. Busy memory, busy disk and `start_session` stay allowed. A running agent and a lane session keep the skip (`running_agent_hit` and `lane_session_hit` return before `read_load`), since a braked cloud lane on a full disk could not even `rm` or `git push`, and its parent cannot free that disk. The refusal names each reading that tripped it. A disk refusal also names the sweep command (`python3 ~/.claude/janitor/sweep.py --root <repo> --attended --fast`, preview first, then `--confirm`), and never tells the session to wait, because disk space comes back only when it is freed. Owner, 2026-11-01 21:34 CST, which the rulings above change for the disk and for memory at full: `why would there be brake refusals when you are running on the cloud? that's specific to local sesions`. The cloud check is `guard_core.is_cloud`, true only for exactly `true`. `hooks/guard.py` and `lint/guard_log_report.py` both use it.
- **Lane lint at the full point, cloud too.** Owner pick a, 2026-11-17 13:22 CST: `merge --lane-lint` refuses under the full point, in a cloud session and a local one. Its own read is the disk, never memory or CPU. The disk read goes through the guard's reader and floor (`guard.py` `_read_disk`, `load_full`; `refuse_full_disk` in `merge/merge.py`). Memory over 95% refuses a background lint start through the guard's brake, before the call runs, as the Full bullet above says (owner, 2026-11-19 21:30 CST). It refuses before it makes a lint tree, and names `sweep.py --root <repo> --confirm`. An unreadable disk reads unknown and goes ahead. The lint reads the drive of the home folder in a cloud session too, as on a local one (`_read_disk` called bare), and the drive of the temp folder. Only the guard's own cloud read, at an Agent, Task, Workflow or lint start, reads `/` (see Cloud sessions).
- **How it reads.** Windows: `GlobalMemoryStatusEx`, through ctypes. Mac: `kern.memorystatus_level`, through ctypes. Linux: memory from `/proc/meminfo` (MemTotal, MemAvailable). Disk everywhere: `shutil.disk_usage`. Never the load average (107 on 15 cores while `top` showed half idle). The lane-lint load gate in decision `lanes-run-no-full-ci-job` is a separate gate that does read the load average. No platform starts a child process.
- **An owner override lifts a refusal.** The brake is not in the never-lifted list (`owner-override`).

Why: many lanes and agents at once can exhaust memory or disk and stall every session.

Risk kind: lane and agent starts, likely, landed 2026-10-22; running agents, incident, landed 2026-10-27; lane sessions, incident class, landed with this change. The incident (owner, 2026-10-26): a session waited on the owner's answer while its background agents kept writing. The brake read only on lane starts, so nothing refused them, the Mac's disk filled and the agents crashed. The memory level is a placeholder for the owner to tune.

Cost, per `outcomes-mechanize-rules`: process starts, none. Files written, none on an allowed call; a refusal adds one line to `guard.log` (unmeasured here), which `lint/guard_log_report.py` reads. How often, on a local session: once per call that starts a lane or an agent, once per background lint start on Bash (a `run_in_background` call, a trailing `&`, a `bash -c`, `sh -c` or `( ... )` lint), and once per agent shell or file write (unmeasured). Also once per shell or file write of a session whose `CLAUDE_CODE_REMOTE_SESSION_ID` is set (unmeasured). That last read adds one transcript read only when the reading is full (unmeasured). On a cloud session: once per Agent, Task or Workflow start and once per background lint start on Bash, one `statfs` of `/` and one `/proc/meminfo` read for each; an agent's or lane's shell or write reads one env value through `guard_core.is_cloud` and nothing else (unmeasured). Each read is one memory counter and one `statfs`, inside the hook process that already runs. No read waits, on any platform. No timer, no watcher, no read on any other call, and none on the shell or writes of a session with no own id. `hooks/test_guard.py` (family `load-brake`) pins the zero children and zero files. It pins one read per lane call, per agent write, per own-id session write and per background lint start, and no transcript read below full, in `hooks/test_guard.py` (family `load-brake`). `hooks/test_guard_load_os.py` checks each reading against the OS's own tool on the Windows and Mac runners.
