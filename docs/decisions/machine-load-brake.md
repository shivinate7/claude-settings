# The machine-load brake

## The ruling

Owner, 2026-10-21 (spec), 2026-10-22 (foreground), 2026-10-23 (disk) and 2026-10-25 (CPU dropped: a 200 ms sample is noise; memory and disk are what stall a machine). A call that starts a lane or an agent reads the machine's load. A busy or full machine refuses new lanes and agents (disk is the smaller of a share and a GB cap). Owner, 2026-10-26 (incident) and 2026-10-27 11:45 CDT (option a): a running agent stops at full only, never at busy. The brake lives in `hooks/guard.py` (`read_load`, `load_hit`, rule `load-brake`), on every device, local and cloud (owner, 14:36 CST Nov 10, glossary topic 1: no rule-chosen local/cloud split; a split the platform forces lives only inside the tool). In the cloud only the Agent, Task and Workflow start refusal runs; see **Cloud sessions** for the splits the platform forces.

- **Readings.** `read_load()` reads memory in use as a share of the machine's memory, and free GB and total GB of the home drive (2**30 bytes to the GB, never clamped). It reads no CPU, and counts no claude process and no running agent.
- **Busy.** Memory over 85%, or disk free under the smaller of 10% of the disk and 15 GB. A 926 GB disk: busy under 15 GB. A 100 GB disk: busy under 10 GB. Any Workflow is refused. An Agent or Task call passes only when it leaves `run_in_background` out or sets it to exactly false. Any other present value (true, "true", null, 1) is refused. In the desktop app a left-out call still runs in the background and the field is not offered, so busy no longer slows Agent calls there. Only full does. The owner chose this on 2026-10-22: a memory spike must not stall a session that cannot choose a foreground form.
- **Full.** Memory over 95%, or disk free under the smaller of 5% and 5 GB. Every call that starts a lane or an agent is refused.
- **Not covered at busy.** `start_session` has no foreground form, and the rulings name only Agent, Task and Workflow. It is refused at full only. `create_session` is not read either (debt note `load-brake-skips-create-session`).
- **The refusal** names each reading that tripped it. At busy, an Agent or Task call is told to wait for the load to drop (memory) or free disk space (disk). It is also told to make the call an Agent call that leaves `run_in_background` out or sets it false. A Workflow has no foreground form, so it gets only the wait or free-disk remedy.
- **A read error counts as normal.** A reading that fails or cannot be read is unread, and one unread reading hides no other.
- **Running agents.** Outside the cloud, an agent's own Bash, PowerShell, Edit, Write, MultiEdit or NotebookEdit call reads the load once (`running_agent_hit`, `RUNNING_AGENT_TOOLS`). Full refuses it and tells the agent to stop and report. Busy lets it run. The hook already runs for each such call, so the brake does not depend on the orchestrator's turn: an agent stops even while its orchestrator waits on the owner. A call is an agent's when its payload carries a valid `agent_id`.
- **Lanes.** Owner, 2026-11-04 07:56 CST (item 168 a): a lane is a session, local or cloud (decision `lanes-start-as-agents`, a lane is a session). Outside the cloud, a lane's own shell or file write is braked as an agent's is (`lane_session_hit`). Full refuses it. The lane is told to end its turn and send the reading to its parent (`send_message` `@parent`), which frees space. Busy lets it run. A session is a lane when two things hold. `CLAUDE_CODE_REMOTE_SESSION_ID` names its own id. Its own newest `get_session` record carries `cs-build:lane` and no other `cs-build:` session role tag, with no `set_session_tags` call on it after the record. A `parent_session_id` alone makes no lane: triage and the batch runner carry one. `hooks/session_start.sh` prints the session role line to any session with an own id, so a local lane reads its own record at start. No own id, no record, or a read error counts as no lane. The load is read first; the transcript is read only at full.
- **Not covered for lane sessions.** A local session with no `CLAUDE_CODE_REMOTE_SESSION_ID` (such as one `start_session` starts) has no own record to read, so a lane of that kind is braked only at its start. Whether a Remote Control lane on the Mac sets that variable is unmeasured. A command already running (a long build) keeps writing; only its next call is refused. An MCP tool that writes files (such as a GitHub file push) is not read. At full an agent or lane cannot commit its last pass either, so that pass stays uncommitted in its worktree until the orchestrator frees space.
- **Full only.** A running agent or lane session is refused only at a full machine: memory over 95%, or disk free under the smaller of 5% of the disk and 5 GB. A busy machine never stops it.
- **Rule exception.** The rule file `.claude/rules/hooks.md` (loaded under `hooks/**`) is the home of an exception to rule `outcomes-mechanize-rules`: an agent's own write may read the machine load once, inside the guard hook already running for it. A lane's own write may too. Outside the cloud, its cost is one memory read and one `statfs` per agent write; in the cloud, one env read. The same cost applies per write of a session with an own id. A transcript read is added only at full. It starts no process, writes no file and sets no timer. The rule file cites this decision.
- **The orchestrator is never braked on its own shell or writes.** A coordinator, triage or batch-runner session carries no lane tag, so `lane_session_hit` passes it. It is the session that frees the disk, so a recovery does not depend on the full disk it recovers (`verification-recovery-independent-of-state`).
- **Which calls read.** Agent, Task and Workflow read once each. Outside the cloud, so do `start_session`, an agent's shell or file write, and the shell or file write of a session with an own id. No other tool reads load.
- **Cloud sessions.** In a cloud session (`CLAUDE_CODE_REMOTE=true`) the Agent, Task and Workflow start refusal runs as it does locally. Owner, 2026-11-10 14:36 CST (glossary topic 1): no rule-chosen local/cloud split; a split the platform forces lives only inside the tool. This replaces the owner's 2026-11-01 21:34 CST ruling that the brake is local-only. Measured in a cloud container, 14:00 CST Nov 12: writes of about 29 GB failed on a 252 GB disk that showed 29.7 GB free, so `shutil.disk_usage` free is the true allowance and the disk thresholds stay. Three forced splits remain:
  - `start_session` is not read in the cloud, and `create_session` is read nowhere today (debt note `load-brake-skips-create-session`). Each runs the new session in another container or machine, so this one's load says nothing about it.
  - The running agent and lane brake (`running_agent_hit`, `lane_session_hit`) reads nothing in the cloud. A cloud disk does not drain by waiting, and the parent runs in another container and cannot free this disk. The braked call (an `rm`, a `git push`) is the only way to free it or push the work, so braking it would make the recovery depend on the full disk it recovers (`verification-recovery-independent-of-state`). A cloud agent's or lane's write can fill the disk (debt note `cloud-disk-full`).
  - A full cloud disk's start refusal carries a steer (`cloud_steer`) in place of "Wait, then retry": free disk space you created, or end the session and tell the parent. It sits ahead of the citation.

  The cloud check is `guard_core.is_cloud`, true only for exactly `true`.
- **How it reads.** Windows: `GlobalMemoryStatusEx`, through ctypes. Mac: `kern.memorystatus_level`, through ctypes. Linux: `/proc/meminfo`, 100 * (MemTotal - MemAvailable) / MemTotal, and nothing else; a container memory limit is unmeasured, so no cgroup file is read. Any read failure is unread. Disk everywhere: `shutil.disk_usage`. Never the load average (107 on 15 cores while `top` showed half idle). No platform starts a child process.
- **An owner override lifts a refusal.** The brake is not in the never-lifted list (`owner-override`).

Why: many lanes and agents at once can exhaust memory or disk and stall every session.

Risk kind: lane and agent starts, likely, landed 2026-10-22; running agents, incident, landed 2026-10-27; lane sessions, incident class, landed with this change. The incident (owner, 2026-10-26): a session waited on the owner's answer while its background agents kept writing. The brake read only on lane starts, so nothing refused them, the Mac's disk filled and the agents crashed. The memory level is a placeholder for the owner to tune.

Cost, per `outcomes-mechanize-rules`: process starts, none. Files written, none on an allowed call; a refusal adds one line to `guard.log`, which `lint/guard_log_report.py` reads. How often: once per call that starts a lane or an agent, and once per agent shell or file write. Also once per shell or file write of a session whose `CLAUDE_CODE_REMOTE_SESSION_ID` is set. That last read adds one transcript read only when the reading is full. In a cloud session, a `start_session` call and each agent or lane shell or file write read no load: one env read through `guard_core.is_cloud`, in the same process. Each read is one memory counter and one `statfs`, inside the hook process that already runs. No read waits, on any platform. No timer, no watcher, no read on any other call, and none on the shell or writes of a session with no own id. `hooks/test_guard.py` (family `load-brake`) pins the zero children and zero files. It pins one read per lane call, per agent write and per own-id session write, and no transcript read below full. `hooks/test_guard_load_os.py` checks each reading against the OS's own tool. CI runs it on the Windows and Mac runners; its Linux arm is run by hand.
