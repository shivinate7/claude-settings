# The mutation report scores suites, on demand

## The ruling

`hooks/mutate_guard.py --report` scores the suites of other verdict-deciding files with mechanical mutants, on demand. It answers the owner's question: do the tests pin anything that matters, or a static result? It is the report mode of the one home of mutation testing (`hooks/mutate_guard.py` with `hooks/mutate_shared.py`). It is not a second tool.

The mode makes mutants of a target file mechanically, with the `ast` module. It flips a comparison, swaps `and` with `or`, drops a `not`, and swaps `True` with `False`. It negates an `if` or `while` test, sets a return value to `None`, and drops a `return`. It samples 10 mutants per file, the same 10 on every run (seed 0). It runs each suite that names the file, in a copy of the repository, against each mutant. It prints, per file: mutants made, killed, crashed, survived, the kill rate, and the suites that killed no mutant. `REPORT_TARGETS` in `hooks/mutate_guard.py` lists the files and their suites. A new verdict-deciding file joins the report by one line there.

Two counts are held shut:

- A crash is not a kill. A mutant is killed only when a suite prints a `FAIL` line. A throw, an import error and a timeout leave no `FAIL` line, or end at the timeout, so they count as crashed.
- A suite that is not green on the clean source is not a killer. Each suite first runs on the clean source after the same parse and unparse that every mutant carries. A suite that is red there is listed as unusable for that file. A file with no usable suite, a parse error or a missing target reads UNKNOWN, never a rate.
- A usable suite that stays green on a wholly broken copy of the file never loaded it: the report lists it as `unloaded`. A file whose every usable suite is unloaded reads UNKNOWN, never a rate.

`--report` makes its mutants with `ast_mutants` only. The JS engine serves the replay below. For a JavaScript or TypeScript file the engine makes the same kinds of mutant, from `hooks/mutate_js.mjs`, run by `js_mutants` in `hooks/mutate_shared.py`. The engine parses with the TypeScript compiler API, loaded only through the plain-english-map loader (`lazy-typescript.mjs`, the one home of that import). It reads sites from the parse tree. A string, template text, a comment or JSX text that holds `a === b` gets no mutant. A `true` or `false` in a type position is a literal type and gets none. Each mutant is one text edit on the original source, and nothing else is reprinted. `js_mutants` samples as `ast_mutants` does. `classify_node_tap` reads a `node --test` run as `classify_run` reads a Python suite: only an assertion in a `not ok` block is a kill, and any other red is a crash.

Both engines take a `lines` filter. `changed_lines` lists the lines that a commit range adds to a file, so a run can mutate only the code a change touched.

`hooks/mutate_guard.py --replay <repo> --profile <name> [--prs N] [--limit N] [--suite-timeout S] [--jobs N]` is the replay mode of the same home. It asks of past work what the report asks of a file. Would the suites a merged pull request changed have caught a wrong line in the product code it added? `merged_prs` lists the newest pull request merges on the clone's first-parent line. It sees merge commits only: a squash or rebase merge has no row, so a repository that squashes is not replayable. `replay_pr` reads the files the pull request changed, makes mutants only of the product lines it added (`changed_lines`, then `ast_mutants` or `js_mutants`), and runs only the suites it changed, never one it deleted. It prints a row per pull request as that row ends, then the table (`format_replay`), and exits 0 whatever the scores.

A `REPLAY_PROFILES` entry in `hooks/mutate_guard.py` says how one repository is read. It holds the regex of product files and of suites, and the command that runs one suite. It names the classifier that reads the output (`fail_line`, `node_tap` or `playwright`), the install, and the top folders left out of each checkout. A test file is not product code, where a profile can name one: q_max's `code_not` leaves out `harness/tests/` and every `*.test.*` or `*.spec.*` file. Banchi's Python part leaves out `harness/tests/` (through its `code` regex) and self-test scripts under `scripts/` (through `code_not`). Banchi's TypeScript part has no `code_not`. The two counts above hold in a replay. A suite red on the clean source (a crash, a timeout, a missing dependency) is listed unusable, and a row with no usable suite reads UNKNOWN with its reason. A pull request that changed no product file reads NO_PRODUCT. One that changed product code and no suite reads NO_TESTS. UNKNOWN never reads as a rate or as green. A file that does not parse is listed skipped. A pull request is never dropped from the table.

A batch pull request can change dozens of suites, and a mutant that survives runs all of them. A profile may carry `select`, a command with `{path}` that prints the suites testing one product file (q_max: `harness/tests-for.mjs`; banchi: `scripts/tests-for.py`). It runs in the checkout at the pull request's commit. A script it names that the commit lacks is read from the clone's HEAD with its whole folder, and a row note names it. A changed suite then runs on the mutants of a file only when `select` lists it. A `select` that fails or is missing runs every changed suite, and a row note says so. `--pr-budget SECONDS` stops the pull request from starting more mutants once its time has passed.

A mutant that never ran counts as `not_run`: no changed suite reaches its file, or the budget had passed. It is never a survivor, and a note names each file no changed suite reaches. `format_replay` shows `not_run` when it is above 0. A row where no mutant ran reads UNKNOWN. Each finished mutant prints one progress line, with its pull request and verdict, before that pull request's row.

Each pull request is checked out as a detached `git worktree` of the clone in a temp folder, written from the index so the clone's settings stay as found. One install runs per lockfile hash, install and link into a shared deps folder, linked into each checkout. A suite writes no bytecode: a mutant of the same size and second as the clean file would load the clean bytecode. The clone is left as found. Every npm install runs with `--ignore-scripts`, banchi's included, and pip has no such flag. An install script is code from a past commit, and the unit tier launches no browser, so it needs none. The install and each suite run in their own process group, killed whole at the timeout. SIGTERM and SIGINT end a replay through its `finally` blocks, which kill the live groups and remove each checkout. SIGKILL cannot run them, so it can leave a worktree record in the clone. `git worktree prune` removes it, once its temp folder is gone. The `banchi` profile has two parts. Its TypeScript part runs one file through the Playwright unit config. Its Python part runs one `harness/tests/tN_*.py` module through its `run()` under `isolated_home()`, as `harness/run.py` does. A module is a suite only when it is green on a clean checkout. T6 reads `demo-assets/extra/photos/0000.jpg`, which the checkout leaves out, so T6 still reads UNKNOWN. T7 runs for minutes whole. A changed `harness/tests/t7/<group>.py` that defines `CHECKS` is a suite of its own. Its runner loads `harness/tests/t7_store_and_seams.py` and runs only that group's checks, in T7's order, each inside `hermetic()`. A helper with no `CHECKS` is no suite. A group with empty `CHECKS` reads unusable, and a check that raises is a crash. A changed `t7_store_and_seams.py` still runs T7 whole.

The report and the replay refuse nothing. No timer starts them, they start no long-lived process, and neither is a CI job. The CI report (below) is a third mode: it refuses only on a known defect. `hooks/test_mutate_report.py` pins the two counts (fixture suites that pin nothing, catch a mutant, crash, are red on the clean source, and an unrunnable file). `hooks/test_mutate_js.py` pins the JS engine, the filter and the TAP classes. `hooks/test_mutate_replay.py` pins the replay on fixture repositories of merged pull requests.

## The scores

One run, 10 mutants per file, 3 suites at a time. The gold standard is the guard's own kill rate: `python3 hooks/mutate_guard.py` killed 367 of 367 hand-written mutations (0 survived, 0 wrong cause), each one tied to a named required case. The same ast engine on `hooks/guard_wsl.py` with `hooks/test_guard.py` read UNKNOWN: that suite is not green on the clean, unparsed source. So the gold is the hand-written rate, and the ast rates below are not held against it on equal terms.

- `lint/report_guard.py`: `hooks/test_reply_judge.py`, `hooks/test_wrappers.py`, `lint/test_rule_audit.py`, `lint/test_settings_matcher.py`. Only `lint/test_report_guard.py` kills.

- `lint/check_silent_undo.py`: none. Its one suite kills.

How to read it. A review probe broke each file wholly. Every silent suite except `hooks/test_reply_judge.py` stayed green, so those suites do not test the file's logic at all: they name it in a list (a hook registered, a platform exit, a wrapper shape). `hooks/test_reply_judge.py` went red, so it loads `lint/report_guard.py` and only missed the sample. The mode itself does not prove a silent suite loaded the mutant. A mutant that throws in a child process that the suite reports as a FAIL line counts as killed, so each rate is an upper bound. The verdict logic of each file is pinned by its own suite. So the measure does not show a worthless suite. It shows that nothing except the file's own suite guards the verdict. A survivor may be an equivalent mutant (no change in behaviour), which the mode cannot tell from a gap. A sample of 10 gives a coarse rate: read 60% as "a gap exists", not as an exact figure. A suite silent on 10 mutants may still catch one outside the sample.

Not measured (UNKNOWN): `hooks/test_guard.py`, `merge/test_merge.py` and `lint/test_ci_scope.py` against these files. The first two take minutes for each mutant. The third only passes a file path to the scope detector.

## The CI report

The job's ruling and its reason are in decision `mutation-ci-report-and-replay`. Three modes of the same home (`hooks/mutate_guard.py` with `hooks/mutate_shared.py`) carry it. The shared action `actions/mutation-report` runs the first two, and the `mutation-report` job of `checks.yml` calls it on a pull request from a `batch-` branch and on workflow_dispatch.

- `--changed` mutates the product lines a change adds past its merge base with the base ref (`replay_pr` with `base` and `select_all`; `changed_lines`, the engines and the classifiers are the replay's). It runs, on the mutants of each file, every suite the profile's `select` lists for it, changed or not. It prints `catch share: K/R`: K mutants killed over R that ran, a crash is no kill, and 0/0 prints no rate. It prints each line with a surviving or not-run mutant as `untested: path:line`. It exits 1 when no mutant ran, after one `no mutant ran: <cause>` line (owner, 2026-11-10 16:47 CST), because 0/0 would read as a pass. The causes are: mutants were made and none ran, the diff could not be read, a changed file did not parse, the install was refused, the checkout was refused, or the replay raised. A change with no target lines exits 0. Otherwise it exits 0 whatever the share. The action's step shows that line in the summary only when the exit is 1 and the line is in the output. Any other non-zero exit, exit 1 without the line included, reads `UNKNOWN: the report did not run (exit N)`. The step still exits 0. The share is a report: it moves with the mutants sampled, the budget and the load of the machine.
- `--known-defects` plants each defect of `.github/known-defects.json` in a checkout of HEAD, prepared with the profile's install as `--changed` prepares its own (a second install in the action), and runs its catcher suite. A suite that goes red with an assertion on the planted copy is CAUGHT. A suite that passes, crashes or times out is a MISS. A stale or ambiguous anchor, a catcher not green on the clean copy, and an install or link that fails, are UNKNOWN. It exits 1 on any MISS or UNKNOWN (decision `ci-unknown-is-red`), and is the only part of the job that can fail it. With `--base REF` it also exits 1 on a `MISSING <id>`: an id on REF's list that the head list dropped, with no `Known-defect-removed: <id>` trailer in REF..HEAD. It exits 1 on a `CHANGED <id>` too: an entry that differs from REF's, with no `Known-defect-changed: <id>` trailer there.
- `--tests-for PATH` prints the suites that test one file: the `REPORT_TARGETS` suites when the file is listed, else each tracked `test_<stem>.py` and `test_<stem>_*.py` beside it. It also prints each tracked `test_*.py` that imports or loads the file, or names its basename in a path expression it copies, opens or runs (read with `ast`). A file that a guard section file loads prints `hooks/test_guard.py`, the runner, whole. A guard module with a row in `GUARD_MODULE_FAMILIES` prints its `hooks/test_guard.py::<family>` lines in place of the whole file. `GUARD_MODULE_DROPPED_SUITES` takes suites away from a row's list. For `hooks/guard.py` it drops `merge/test_merge.py` (times out). It also drops the three suites that assert on its own text, which the report's `ast.unparse` copy changes. `hooks/guard_core.py` has no row (`GUARD_MODULE_EXEMPT`). A change to `hooks/guard.py` ran 10 of 10 mutants in 978 to 1023 s with the 1800 s budget (3 runs), and 0 of 10 in 300 s with either selector. The table is in decision `mutation-ci-report-and-replay`. It is the `select` of the `claude_settings` profile in `REPLAY_PROFILES`.

`hooks/test_mutate_ci.py` pins the three modes and the list. A file that no tracked `test_*.py` beside it or importing it covers has no suite, so its mutants are not run and its lines read untested. A load whose path is a function parameter is followed to that function's calls in the same file (`_loads_module`). Only the forms `_loads_module` lists as handled are followed. Other forms are not, and the list of examples is not complete. Examples are an attribute call, an imported loader and a wrapper that calls a wrapper. More are a path parameter left to its default, a lambda loader and a bare alias of the loader. More are a loader that takes the path as `*args` or `**kwargs`, and a call that spreads the path in. More are a name bound only as a `for` or comprehension target. More are a name bound by tuple unpacking, augmented assignment, `with ... as`, a walrus or an attribute store. Also a class constructor that takes the path, `functools.partial(load, "widget.py")`, `map(load, [...])` and a split literal `"widget" + ".py"`. So an untested line may be a file that `--tests-for` does not map. The read also selects a suite wrongly in two cases. A bare call `load(path=X)` feeds a method of the same name. A loader that reassigns its path reads the argument its calls pass.

On 2026-11-02 no CI check read the replay. The CI report above is the first.

## Cost

One full report run, measured: 41.5 minutes on 4 cores with `--jobs 3` (not pinned). About 155 suite process starts and 5 `git init` starts (unmeasured). The slowest suite, `hooks/test_stall_watch.py`, takes 150 s a run. The JS engine is not in this run. In the replay it adds one `node` start per file mutated (unmeasured). Files written: temporary copies of the repository (about 13 MB each; the clean copy and up to 3 mutant copies at a time) in the system temp folder, all removed at the end. Nothing is written to the repository. `--limit N` and `--only TEXT` bound a run. A run stopped before its end keeps the rows already printed, because each file's row prints as that file ends.

A replay costs, per pull request scored, one control run per suite and then one run per suite per mutant (unmeasured). A mutant ends at its first assertion, and the quickest suites run first. It adds one `node` start per product file mutated and `--jobs` `git worktree` starts (unmeasured). The install runs once per lockfile hash, install and link for the whole run (unmeasured). Files written: the temp checkouts (one per job) and one deps folder per lockfile hash, install and link, all removed at the end, and nothing in the clone. A pull request with no product file or no suite starts no suite process.
