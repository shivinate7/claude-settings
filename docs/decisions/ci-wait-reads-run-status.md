# CI waits read the run status

## The ruling

Owner, 2026-10-16 01:47 CDT ("Status read only") and 03:00 CDT ("Change them too"): no program and no agent runs `gh run watch`, in the foreground or the background. Each wait reads the run's status until the run ends or its deadline passes. `bin/merge` reads once every 30 s. The CI wake reads 30 s apart for the first 4 minutes, then at gaps that grow to 120 s (owner, 2026-10-21, back-off).

- `merge/merge.py`, `block`: no watch. It pauses 30 s when a check has an Actions run, else a minute. The next pass of the wait loop reads the checks and runs.
- `hooks/ci_wake.py`, `watch_run`: no watch. It reads `gh run view <id> --json status` on one schedule (`pauses`): 30 s apart through 240 s, then gaps that grow by 30 s up to 120 s, never shorter than the gap before. `wait_for` lists the head's runs on the same schedule, and lists once more at once after the first judged run (one extra `gh run list` per wait), to catch a run that shows late. The watch returns when the status is `completed` or the deadline passes. The deadline stays 3300 s, and `watch_run` makes no status read at or after it. A failed read gets one retry after a 30 s pause, never past the deadline. A second failure ends the wait as unknown, never green.
- A session waits on CI through the CI-wake notice that follows `gh pr ready`. The guard's remedy never names `bin/merge`, because it merges when the wait ends.

Why: one `gh run watch` made 131 API calls in 60 s, about 7,900 an hour. The core limit is 5,000 an hour, shared by every session on the account. Merges failed on it.

### The CI wake-up

Owner, 2026-10-13 11:20 CDT: the CI wake-up hook lives in claude-settings. The mods session drops its own CI wake-up step. The hook is a Python hook registered in `settings.json`, with a red test first.

A PostToolUse hook on Bash, PowerShell and the GitHub MCP `update_pull_request` tool (`hooks/ci_wake.py`) starts an `asyncRewake` watcher after `gh pr ready <n>`, or after an MCP `update_pull_request` call with `draft` false. The MCP call is the cloud's ready route, because `gh pr ready` gets a 403 there (owner, 2026-11-11 11:55 CST, relayed by the retrospective session: "the wake-up that tells a session CI is done never fires in the cloud"; lane `ci-wake-mcp-ready`).

- Each `gh pr ready` in one command gets its own watch. A push alone starts no watch, because a PR goes ready after its last push and a push read can see the old head. A draft PR starts no watch. An MCP call with `draft` absent or true starts none. The MCP call names its PR by `owner`, `repo` and `pullNumber` in `tool_input`. The hook's `settings.json` row reads `tool_input` only. It picks its pattern by `tool_name`. A shell call (Bash or PowerShell) starts python only when gh, pr and ready occur in that order, each at most 16 characters after the one before (any case of gh). The MCP `update_pull_request` call starts python only when its `tool_input` holds the text `"draft": false`. Python then reads the JSON `draft` key. A shell call never matches on `draft`, so a `draft` in a shell command starts no watch.
- The watcher reads the PR head once and waits on its runs. A head whose only runs are skipped counts as no run yet.
- It exits 2 with a one-line verdict, which wakes the session even when idle. It stops at its own deadline, under the hook `timeout`, and wakes with "still running".
- One watcher runs per PR: a second one for the same PR exits at once.
- Text in quotes, in a heredoc body or after `#` never starts a watch. Any error, including an import or flush error, wakes with an "unknown" line.

Why: sessions waited for CI with long background commands that ran on for hours.

The CI wake is a named exception to rule `outcomes-mechanize-rules` (owner ruling, Cockpit item 180, pick a, 2026-11-06 12:19 CST; home `.claude/rules/hooks.md`). Status: ruled (`stall-watch-exceptions-180a`). The watch lives up to its 3300 s budget. Cost, per `outcomes-mechanize-rules`: each status read starts one `gh` child (`hooks/ci_wake.py`, `gh`), and that count is unpinned (note `ci-wake-gh-proxy`). The watch itself runs inside the hook process (`hooks/test_ci_wake.py`, class `CostTests`). The hook makes no model call. Each PR keeps a lock file, named by its URL, for the next watch of that PR (`hooks/test_ci_wake.py`, class `CostTests`). A second watch of the same PR exits at once and writes no file (same class). A run that never completes is read at most 35 times, up to the 3300 s budget (same class). The hook's own timeout is 3600 s. Whether the watch costs less than what it watches is unmeasured.

### The cloud wake

A cloud session marks a PR ready by MCP `update_pull_request` with `draft: false`. The PostToolUse row for `ci_wake.py` covers that call, and python starts only for a ready call. Whether the hook and its `gh` reads run in a cloud session is unmeasured: no live cloud run exists yet. Until one does, the session also waits through the PR subscription. A watched PR wakes its session on a new comment, a review, and a run whose jobs all passed. A run with a red job sends no "all checks done" wake, and a green job alone wakes nobody. Why: a red job can go unseen for hours when no session sets a check-in (owner gripe, 2026-10-26: about 2.5 hours).

- `checks.yml`'s last job, `ci-done`, needs every other job and runs when no run was cancelled. When a job ended `failure` or `cancelled`, it posts one PR comment: the head, each red job and the run link. A green run posts nothing. A superseded run posts nothing. `actions/ci-done-comment` holds the script, and other repos call it.
- Measured 2026-10-27: a red run's `ci-done` comment by `github-actions[bot]` reached the watching session as `issue_comment.created`, about 2 minutes after the post. A run that a newer push cancelled posted no comment, as designed.
- The fallback: a session that waits on CI sets a one-time `send_later` check-in when it starts to wait, and again after each red job, each wider apart, never past 55 minutes (rule `git-ci-wait-checks-in`). The 55 is a dated cache fact in `hooks/ci_wait_cap.json`, read through `hooks/ci_wait_cap.py`, by the guard too: it refuses a longer CI check-in (rule `ci-wait-cap`, decision `ci-wait-cap-guard`). It spaces check-ins and limits no run. The watch deadline in `hooks/ci_wake.py` is a separate number, owned by step `time-limits-end-hangs-only`. Known gap, not handled here: under the 5-minute overage cache a 55-minute wait misses the cache. A check-in costs one read, and it catches a wake lost before it fires. Limit: a wake lost after a check-in that found no new event is not caught. Owner, 2026-11-06 13:59 CST (waiting page item 290): "shouldnt the rules first not conflict?" Resolution: rule `outcomes-mechanize-rules` (on-demand reads; a timer only when its record shows it costs less than it saves) carves out a one-time check-in set to wait for one named outside event (such as a CI run or a reply); the next check-in waits for a new named event.
- Enforced: `hooks/stall_watch.py --stop` blocks a Stop while a ready PR has no check-in after its ready call or its last red verdict. A check-in whose result is an error does not count. A green or cancelled verdict closes the wait, and an unknown one does not. So does a merge or close that names the waited PR. The calls are `bin/merge N`, `merge N`, `gh pr merge N`, `gh pr close N`, and MCP `merge_pull_request` with its `pullNumber`. A `gh` global flag before `pr` (`gh -R o/r pr ready 5`) is skipped. The ready call's PR is read as a merge's is: the first all-digit word or the `N` of a `/pull/N` URL. A flag and its value (`-R o/r`, `-C /repo`, `--body "x"`, `--body-file f`, `--subject "Fix"`, `--comment x`, `--session lane`) are skipped. With no number, the first non-dash word (a branch) is the PR named. A `gh pr merge` or `gh pr close` with no PR word, only flags and their values, closes any open wait. In those two calls, a `$var` PR word is an unknown number, so it counts as no PR word. A `bin/merge` with no PR word, or a `$var` one, gives no event. A wait for N then stays open, a false block. A wait whose ready call named no number (bare `gh pr ready`) closes on a merge or close of any PR. `gh pr merge --auto` and `--disable-auto` close nothing, since nothing has merged. A red verdict is the line `ci_wake.py` prints (`CI red on <sha7>`) or the one `actions/ci-done-comment` posts (`CI finished red on <sha7>`). Limits: a check-in is any `send_later`, `create_trigger`, `CronCreate` or `ScheduleWakeup` call, since the rule says "check-in", not a tool (coordinator pick, 2026-11-14 11:07 CST, undoable; owner not yet asked). Any of them covers the wait, even one set for another errand. The second Stop after one block passes (`stop_hook_active`). The check keeps one wait, opened by the newest ready call. An older ready PR with no check-in goes unblocked once a newer one opens (open for the owner: one wait, or one wait per ready PR). An undo (`--undo`, or MCP `update_pull_request` with draft true) closes the wait on its PR. A wait that names no number (bare, a branch or a `$var`) closes on a merge of any PR. It reads the transcript only: no process, no network, no file written, no timer.
