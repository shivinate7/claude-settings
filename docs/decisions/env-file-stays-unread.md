# The environment file stays unread

## The ruling

No session reads, writes or commits the contents of an environment file. The user manages that file, and its values stay out of the session. The guard refuses a shell command that would do any of those, and a write tool call that names the file. The settings deny list refuses a Read or Edit call on it. A runner may load the file into its own process with its loader flag. The guard stops node, bun and deno given the file when they run inline code (`-e`, `-p`, `--eval`, `--print`, deno's `eval`) or a script read from stdin (`-`, a pipe, a heredoc, a here-string or a `<` file), since that code can print the variables. It does not catch deno's `run -`, which reads stdin after the word `run`. It does not read a script file: a script the session wrote can still print them.

One scope covers every form: a write tool call, a shell command and a Read call. A name is any basename that starts with `.env`, except `.env.example`. The guard's forms read one shared basename matcher in guard_env (`names_env_file`).

Shell form. `judge_shell` calls `env_refusal` and `env_heredoc_refusal`. A name is a word whose basename is in the scope above. A glob that could match a name counts as the name (`_glob_could_name_env`).

- Refused: a redirect onto the file. A shell variable that holds its path, because the guard cannot follow a variable to its use. The file given to a command that is not a runner. Any other command that would read, write or commit it.
- Allowed: an existence check (`ls`, `test`, `[`, `[[`). `echo` and `printf`, where the name is text. The message or body value of `git commit` and `gh pr create`. A runner in `ENV_LOADER_COMMANDS` (node, npm, npx, pnpm, bun, deno, uv, docker, podman, and their variants) given `--env-file` or `--env-file-if-exists`, except that node, bun and deno given the file must run a script file, not inline code or a stdin script.
- Interpreter code (`python -c`, `node -e`, python, node, bun and deno heredoc bodies, quoted or not) is judged by its string literals, one path each, read by guard_core `code_paths`. Text uses are allowed, as `echo` is. They are: printed, written as content, dumped as JSON, an exception message, and a compare. A `str.join` list takes the mode of its consumer, as `os.path.join` does: text when it is printed, written as content or compared, a read when `open` takes it. Existence checks are allowed, as `ls` is. They are `os.path.exists`, `Path(p).is_file()` and `fs.existsSync`, also through a join. Metadata calls count as existence: `os.stat`, `os.path.getsize`, `Path(p).stat()`, `fs.statSync`. They read no contents, as `ls -la` does. A name tested against the file's name is refused when a read, write or unknown call takes it inside the test's positive branch: `if f == '.env': open(f)`, `f in ('.env', 'x')`. An `in` picks only a name on its left: `'.env' in line` asks about the text of `line`, so it picks nothing. The positive branch is the `if` body, the right of an `&&`, a conditional's true arm, or a comprehension's element after its own `if`. A `!=` or `not` test, an `else` arm and the code after an `if` body that ends in `continue` pick nothing. So a filter that drops the file's name stays allowed. The name is read by its spelling, with no scope. A prefix test (`startswith`, `endswith`) is text only in code that hands no variable to a file call. A variable file call is a call argument, not a string literal, with a read, write or unknown mode. A JS arrow function is no such argument. A python read or write method on a receiver that is not a literal `Path` is one too. A prefix test finds names that later code can open by another name (`found = f`, a bound list, a `continue` on its negation, a JS `.filter(...).forEach(...)`), and the reader does not follow data flow. So any variable file call keeps the literal refused. A pure listing, such as `print([f for f in os.listdir('.') if f.startswith('.env')])`, stays allowed. One exception: a bare name read inside the body of `not f.startswith('.env')`, `!f.startsWith('.env')` or `!(f.startsWith('.env'))`, alone or `&&`-joined with other tests, cannot be that file, so it does not count. The negation must stand once, and the check reads the characters next to it: no `||`, `==`, `|` or `:` beside it, and no second `!(` group around it. Inside an `if` condition, a same-level `||`, `?` or `,` also keeps the literal refused. Outside an `if` condition, no same-level scan runs, so a `?` after it is allowed. Every other use of the file, or a literal whose use is unknown, is refused (`ENV_CODE_REASON`).
- Code behind the runners in guard_core `CODE_RUNNERS` is judged too: `uv run`, `uv tool run`, `uvx`, `poetry run`, `pipenv run`, `pdm run`, `conda run`, `npx`. So is a heredoc written to a file that the same command runs with python or node, `uv run x.py` included. So is a heredoc piped into an interpreter that reads stdin (`cat <<'PY' | python3`). A heredoc piped into an interpreter that has a script word is data, and its lines are read as shell words, as for `python3 x.py <<'EOF'`. `npx -c` hands its string to the shell reader. A quoted body counts as clean code only when it is the code the interpreter reads from stdin and it parses. Any other body keeps its per-line reading. Comments are never read. - Substitutions (`$(...)`, backticks, `<(...)`) are judged as commands of their own, at any depth up to `ENV_MAX_DEPTH` (64). A deeper nest is refused. Each script that `inner_commands` returns (`sh -c`, `eval`, `env -S`, `docker exec`, `su -c`, `find -exec`, ssh) is judged as a command of its own by a recursive `env_refusal`, under the same cap. Not read: `docker run`, `watch`, and `bash --rcfile F -c`. The substitutions in an unquoted heredoc body are judged (`env_heredoc_refusal`). A quoted heredoc body is text for bash, except a python, node, bun or deno body, which is code (above).

Write form. In `judge`, a write tool call (Write, Edit, MultiEdit or NotebookEdit) whose target name is in the scope is refused (`is_env`). It reads the same matcher as the shell form.

Read form. The guard does not judge Read. It returns early for Read and Grep. The settings deny list refuses a Read call on a name that starts with `.env`, at any depth. It refuses an Edit call on the same names. Its `!` carve-outs keep `.env.example` readable and editable. That reading of the `!` carve-outs comes from Claude Code's permission docs. It is not measured.

The printed refusal names no file. It names the shape of the access (`ENV_REDIRECT_REASON`, `ENV_VARIABLE_REASON`, `ENV_RUNNER_REASON`, `ENV_INLINE_REASON`, `ENV_CONTENTS_REASON`, `ENV_DEPTH_REASON`, `ENV_CODE_REASON`, `ENV_TOOL_REASON`) and a remedy (`ENV_ADVICE`). The log holds the file name, for a person to read.

Known false alarms: debt `env-file-rule-false-alarms` (the env-file false-alarm debt). The guard refuses `ag -f` and `ack -f`, where `-f` is a boolean flag, `grep -r --exclude=.env`, and `rg -t py .env`. All four are safe. None reads a file's contents.

Why: the user's own secrets must not enter the session. `.envrc` is in the scope for the same reason. The guard stops Claude's mistakes, not an attacker's form (`guard-guards-mistakes-only`, a guard stops mistakes, not an attacker).

Risk: likely risk (`building-guard-needs-incident`: a guard or check needs a mistake Claude has made or is likely to make in normal work). A session would likely read a `.env` or `.envrc` file while it debugs. No incident is on record. Landed 2026-09-16, the env-file rule. The guard_env module has held the rule since 2026-10-13.
