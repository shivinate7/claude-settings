# The environment file stays unread

## The ruling

No session reads, writes or commits the contents of an environment file. The user manages that file, and its values stay out of the session.

The guard refuses a write tool call that names the file. The settings deny list refuses a Read or Edit call on it. In a shell command the guard refuses only the forms it reads. A runner is read for its child (below). Outside a runner, `bash -c "cat .env"`, `sh -c "source .env && npm test"` and `eval "cat .env"` allow. Lane `env-file-shell-c` owns that gap.

A runner may load the file into its own process with its loader flag. The guard stops node, bun and deno given the file when they run inline code (`-e`, `-p`, `--eval`, `--print`, deno's `eval`) or a script read from stdin (`-`, a pipe, a heredoc, a here-string or a `<` file). That code can print the variables. It does not catch deno's `run -`, which reads stdin after the word `run`.

The guard also stops uv, docker, podman, npm, npx and pnpm given the file when the child command they start prints its environment. It reads these children: `env`, `printenv`, any `python -c`, and inline node, bun or deno code. A `perl`, `ruby`, `awk`, `gawk`, `mawk` or `nawk` child prints when code names the environment (`perl -e 'print %ENV'`, `$ENV{KEY}`, `ruby -e 'p ENV'`, `ENV.to_h`, an awk loop over `ENVIRON`). It also prints when its code holds a shell string that prints: `system("env")`, `exec`, `spawn` or `popen` over a string, a backtick pair, `qx(env)`, `%x(env)`. The code is each perl or ruby `-e` value (also `-ne`, `-pe`), awk's program word or `-e` value, and a here-string (`_script_code`). It is read as the shell hands it on. A script name, its arguments and a file name are not code (`ruby script.rb ENV`, `awk '{print}' ENV.txt` run). A bare word `ENV` is text (`perl -pe 's/ENV/prod/'` runs), except ruby's `p ENV`, where it is the constant. In a ruby string literal it is text (`puts "the ENV var"` runs), and in a `#{...}` it is code. Any child but a shell prints too when a word names `/proc/self/environ`, `/proc/<pid>/environ`, `/proc/$$/environ` or a glob of the pid (`/proc/*/environ`). The exceptions are `ls`, `test`, `[`, `[[`, `echo` and `printf`. A longer name is another file (`/proc/self/environ_x`). A docker or podman `compose config` or `compose convert`, and `docker-compose config`, print the resolved values, so they are children too, unless a listing flag follows (`--services`, `--volumes`, `--profiles`, `--images`, `--hash`, `-q`). A listing flag may be glued to a value (`--hash="*"`). `compose up` is not. A python or shell child with no script word and stdin fed is also stopped. Stdin is fed by a pipe, a heredoc, a here-string or a `<` file. `npx`, `npm exec`, `npm x`, `pnpm exec`, `pnpm dlx` and `bun x` children are read the same way: `npx node -e "..."` is inline code. `bun x` is read only as the exact word `x`, so `bun ./x` is a script. One reader, `_child_starts`, finds the children. One judge, `_child_prints`, reads each.

A wrapper before the child is read through to the command it runs: `timeout <n>`, `nice [-n x]`, `sudo [-E] [-u x]`, `time`, `stdbuf ...`, `env VAR=x`, and `exec`, `command`, `builtin` and `nohup`. `uv run timeout 5 env` is the child `env`. `env VAR=x` with no command prints, so it is the child, and so is `env > out.txt`, where a redirect follows.

A shell string is `sh`, `bash`, `zsh` or `dash` with `-c "<s>"`, or npm, npx or pnpm with `-c "<s>"`. The guard reads the string as the child shell gets it, with one reader of a shell word (`_shell_word`), shared with the perl, ruby and awk code. Pieces quoted apart join: `'it'\''s'` and `'it'"'"'s'` are both `it's`. In double quotes the parent drops the backslash of `\$`, `` \` ``, `\"` and `\\`. It judges it segment by segment, with the same reader as the shell form (`_env_flat`). Each `$(...)`, backtick pair and `<(...)` in a segment is cut out by `_substitutions` and judged as a command of its own, in any quote (`cd "$(env)"`). A body that names an environment file is refused as the shell form refuses it (`echo "$(cat F)"`), while `echo "$(cat README.md)"` runs. A real `#` comment hides its text (`ls # $(env)` runs); a `#` in quotes does not. A line break or `;` starts a segment, and a lone quote does not hide the segments after it. A group or clause word before the command is read through: `{`, `(`, `!`, `if`, `then`, `else`, `elif`, `do`, `while`, `until`. A segment is refused in five cases. A redirect and its target are no argument (`set > f`). It names an environment file as the shell form refuses. Its command is a printing child: `env` or `printenv` (also after a wrapper or a group word, and as a substitution), a nested `sh -c` that prints, any nested `python -c`, or a perl, ruby, awk or `/proc/.../environ` child above. Its command is `set` with no argument. Its command is `export` with no argument or with `-p`, or `declare` or `typeset` with `-p`, or with no name to set (bare, or `-x`). With `-f` or `-F` they print functions only, so `declare -pf` runs. `compgen` prints names, not values, so it runs. Or its command is `echo` or `printf` and it expands a `$` variable. A substitution is no variable: `echo $(date)` and `echo $((1+2))` run, `echo $(env)` is refused for the `env` in it, and `echo $(echo $X)` is refused for the `$X` in the inner echo. A `$` in any other segment is an ordinary argument, so `docker run ... sh -c "cd $APP_DIR && npm start"` runs. Any other string is allowed too, so `docker run ... sh -c "npm start"` runs. A `$( )` in a double-quoted shell string runs in the parent shell, before the runner loads the file, so it sees none of the file's values: `uv run --env-file F bash -c "echo $(printenv HOME)"` runs. An escaped `\$(env)` in the same string runs in the child, so it is refused. ACCEPTED LIMIT (note `env-parent-expansion-is-code`): the parent's output is the child's code, so `sh -c "$(cat script)"` is not read.

A docker or podman child is the `--entrypoint` program, else the word after the image. An empty `--entrypoint ""` is no program. `docker container run` and `podman container run` read as `run`.

Each runner has a list of value flags and a list of bool flags. The docker, uv, pnpm and bun lists are read from the tool's own help (`docker run --help`, `uv run --help`, `pnpm help exec`, `bun x --help`). The npm lists are `npm exec --help` plus npm config flags chosen by hand (`--registry`, `--loglevel`, `--color` and the like). A value flag owns the next word. A bool flag owns none. An npm or pnpm bool also owns a next word that is exactly `true` or `false`, since nopt reads it as the flag's value (`npm exec --dry-run false env` runs env). npm's `--color` is a bool that also owns the literal `always`, so `npm exec --color always env` runs env and `npm exec --color env` runs env. Every `--no-*` flag is a bool unless the value list names it.

Only a flag missing from both lists is read both ways. It may own the next word, so the guard tries that word as the image or child. It then goes on past each option and its possible value, to the next word that follows no such flag (`--foo X --bar alpine env`, `--cap-add X --cap-add Y img env`, `pnpm exec --foo env`). The child of npx, `pnpm dlx`, `npm exec` and `npm x` is found the same way (`npx env`, `pnpm -r exec env`). pnpm's `-r` and `-w` are bools there, and npm's `-w` takes a value. `--` ends a runner's options, so the word after it is the child (`pnpm exec -- env`). A program's own arguments are not tried (`uv run -q pytest -k env`, `uv run --exact pytest -k env`), except after a flag missing from both lists (below) and npm's `-c`. An `npm exec -c` child is its string. Quote marks on a child word are ignored. pnpm reads no flag after `exec`, and `pnpm exec -c echo` fails. The guard still reads a flag there as a flag, so it refuses a form that fails and prints nothing, which costs nothing.

Gaps remain, each a note (`env-script-shell-string-forms`, `env-script-file-unread`, `env-runner-child-runner-unread`). Perl and ruby shell strings are read in the forms above only. The guard does not read a script file, so a script the session wrote can still print the variables. A runner started as a child is not read for its own child (`uv run --env-file F npx -c env`).

Two false alarms remain. A flag missing from both lists may own the next word. After it, `env` or `printenv` as the program's first word or after the program's own option is tried as the child and denies (`uv run --foo pytest env`, `uv run --foo pytest -k env`). A program's `-c` after such a flag reads as pnpm's shell string (`pnpm exec --foo jest -c env`). The guard cannot tell a bool from a value flag (note `env-child-unlisted-flag`). An `echo` or `printf` segment that expands any `$` variable refuses, even one that holds no secret (`sh -c 'echo $PORT'`; note `env-echo-variable-any-name`).

One scope covers every form: a write tool call, a shell command and a Read call. A name is any basename that starts with `.env`, except `.env.example`. The guard's forms read one shared basename matcher in guard_env (`names_env_file`).

Shell form. `judge_shell` calls `env_refusal` and `env_heredoc_refusal`. A name is a word whose basename is in the scope above. A glob that could match a name counts as the name (`_glob_could_name_env`).

- Refused: a redirect onto the file. A shell variable that holds its path, because the guard cannot follow a variable to its use. The file given to a command that is not a runner. Any other command that the guard reads as one that would read, write or commit it.
- Allowed: an existence check (`ls`, `test`, `[`, `[[`). A find that lists a name: a `find` whose name pattern after `-name`, `-iname`, `-path`, `-ipath`, `-wholename`, `-iwholename`, `-regex` or `-iregex` names the file lists its name and reads no contents (`find . -name <file> -print`). That holds while its output goes to the terminal or a commit or pull request message value. It also holds for a pipe chain whose every stage is a filter that runs no command (`ENV_FIND_FILTERS`: `wc`, `sort`, `uniq`, `head`, `tail`, `cut`, `tr`, `nl`). It is refused when the output sits inside any other substitution (`cat $(find ...)`, `<(find ...)`). It is refused when any pipe stage is another command (`| sort | xargs cat`, `| while read f`). It is refused when `>` or `>>` sends the output, or a filter's output, to a file (`> list`). Each of those may hand a name to a command that reads it. It is also refused when the same `find` has `-exec`, `-execdir`, `-ok`, `-okdir`, `-delete`, `-fprint`, `-fprint0`, `-fprintf` or `-fls` (`ENV_FIND_ACTIONS`). A `find` that takes the file as its start path is refused. `echo` and `printf`, where the name is text. The message or body value of `git commit` and `gh pr create`. A runner in `ENV_LOADER_COMMANDS` (node, npm, npx, pnpm, bun, deno, uv, docker, podman, and their variants) given `--env-file` or `--env-file-if-exists`, except that node, bun and deno given the file must run a script file, not inline code or a stdin script. A runner that starts a child command (uv, docker, podman, npm, npx, pnpm) must not start one that prints its environment, or a shell string that does (`ENV_CHILD_REASON`).
- Substitutions (`$(...)`, backticks, `<(...)`) are judged as commands of their own, at any depth up to `ENV_MAX_DEPTH` (64). A deeper nest is refused. The substitutions in an unquoted heredoc body are judged (`env_heredoc_refusal`). A quoted heredoc body is text.

Write form. In `judge`, a write tool call (Write, Edit, MultiEdit or NotebookEdit) whose target name is in the scope is refused (`is_env`). It reads the same matcher as the shell form.

Read form. The guard does not judge Read. It returns early for Read and Grep. The settings deny list refuses a Read call on a name that starts with `.env`, at any depth. It refuses an Edit call on the same names. Its `!` carve-outs keep `.env.example` readable and editable. That reading of the `!` carve-outs comes from Claude Code's permission docs. It is not measured.

The printed refusal names no file. It names the shape of the access (`ENV_REDIRECT_REASON`, `ENV_VARIABLE_REASON`, `ENV_RUNNER_REASON`, `ENV_INLINE_REASON`, `ENV_CHILD_REASON`, `ENV_CONTENTS_REASON`, `ENV_DEPTH_REASON`, `ENV_TOOL_REASON`) and a remedy (`ENV_ADVICE`). The log holds the file name, for a person to read.

Gaps. Each is noted in `docs/debts/notes.md` as a form only an attacker writes (`guard-guards-mistakes-only`). No fix is planned.

- A perl, ruby or awk script read from stdin or a heredoc (`env-script-stdin-code`).
- A quote escape inside a script's code string (`env-script-string-escape`).
- A `$'…'` shell string (`env-ansi-c-string`).
- A backslash-escaped separator in an unquoted `sh -c` word (`env-sh-c-escaped-separator`).

Known false alarms: two open notes in the debt notes. Both hold at this head. Main: code read, not probed.

- Note `env-cwd-prose-false-alarm` (printed text read as a variable): `echo "(cwd=.envs)"` and `python3 -c "print('x (cwd=.envs):')"` are refused. The guard reads `(cwd=.envs)` as a shell variable that holds an env path.
- Note `jq-lone-word-false-alarm` (a lone program word): `jq .envs` and `cat f | jq .environment` are refused. A lone word may be the file, so the guard judges it.
- Note `jq-lone-word-false-alarm` (a value flag before the program word): `jq --arg k v .environment f.json`, `jq --indent 2 .envs f.json` and `yq -o json .envs f.yaml` are refused. The guard does not know that `--arg`, `--indent` and yq's `-o` take a value. So the value is read as the program word, and the real one is judged.

Allowed forms:

- `ag -f` and `ack -f` are boolean flags. They name no pattern file.
- The values of `grep --exclude` and `--exclude-dir`, and of `rg -t` and `-T`.
- A `jq`, `gojq` or `yq` program word, when a file word follows it. A switch such as `-C` does not hide that file word.
- `mkdir` on an env-prefixed folder, such as `mkdir .envs`, reads no contents.
- `cd` and `pushd` into such a folder are refused. The shell keeps its folder between calls.
- `git add` and `cat` on such a folder are refused. The guard cannot tell a folder from a file.
- In each allowed form, the env name is a pattern, an excluding glob, a type name, a program or a folder name. It is never a file that is read.

ag regex:

- Without a hidden flag, ag skips dotfiles, so its file regex is not judged.
- With a hidden flag, the guard judges the regex from `-G` or `--file-search-regex`. `-p` names an ignore-pattern file, judged as a path.
- The guard reads the regex as the shell gives it to ag, in bash or PowerShell. A PowerShell single quote keeps its backslashes.
- The guard tries the regex, bare and with a `./` prefix, on `.env`, `.envrc`, `.env.local`, `.env.production`, `.env.development`, `.env.test` and `.env.staging` (`ENV_SAMPLE_NAMES`).
- It also tries the names the regex could pick, built from its parse tree, with and without the leading dot. A regex that matches one is refused. Examples: `\.env\.prod$`, `env\.prod$`, and `\.env[A-Z]*\.md$`, whose empty repeat picks `.env.md`.
- A POSIX class such as `[[:alpha:]]` or `[[:^alpha:]]` is first written out as ranges.
- A regex with too many shapes is read again in a lean form. Each repeat takes its least count, and each class or dot offers one letter. So `.*a.*b.*c.*d.*e.*f` is judged by the names it can pick.
- A regex is refused when it does not compile, holds an unknown POSIX class, or still has too many shapes in the lean form.

Folder walk:

- With a hidden flag, rg and ag reach each env file in a folder they walk, whatever its name. The hidden flags are `--hidden`, rg's `-.`, and `-u` (`--unrestricted`). ag needs one `-u`. rg needs two.
- rg also walks for any positive `-g` or `--iglob` glob, even with no hidden flag. The walk judges the glob against each env file it finds. Such a glob overrides the ignore rules, and rg enters an ignored folder that the glob picks.
- rg matches a glob with a `/` against the path from the working folder. So `rg -g 'sub/*' K sub` reads each file in `sub`.
- A recursive grep reaches them with no flag. `grep`, `egrep` and `fgrep` recurse with `-r`, `-R`, `-d recurse`, `--directories=recurse`, `--recursive` or `--dereference-recursive`. `rgrep` always recurses.
- The guard refuses a search when a path word is a folder that holds an env file on disk. It also refuses when no path is named, because the working folder is walked.
- For rg and ag, a pipe or `<` into the search clears the no-path case. For grep it does not.
- A folder with no env file stays allowed. So does `rg --files`, which lists names and reads nothing.
- The shell removes the backslash of an unquoted glob, so `--include=\*.md` reaches grep as `*.md`. A quoted `'\*.md'` keeps it, and grep reads it as a literal star.
- grep reads a glob with glibc fnmatch, which negates `[^a]` and reads `[[:alpha:]]` as a class. rg also negates `[^a]`. `_glob_unescaped` writes both out, and every glob reader calls it: include and exclude rules, `--exclude-dir`, and the names `find` prints. Only a leading `!` or `^` negates. The guard reads a POSIX class for rg too, which only picks more.
- Grep decides each file by its last matching `--include` or `--exclude` glob, so an exclude before an include re-includes the env file. An exclude glob or `--exclude-dir` that skips the env file clears the search. `--exclude-dir` skips a folder operand only when its glob matches the operand as typed, whole or a tail after a `/`, as grep 3.11 does. The folder a grep with no path walks is always walked. So are an operand whose last part is `.` or `..` or that ends in `/`, and a folder that xargs or find feeds. The refusal names `--exclude` and `--exclude-dir` as the remedy, and prints no file name.
- `--include`, `-g`, `--glob` and `--exclude-from` stay judged, since each can name the file.
- The walk is `_env_walk`. It expands an unquoted comma brace list, such as `{a,b}`, in each word, as bash does, in a `find` start path too. A word with quotes expands outside the quotes only, so `"su"b/{a,b}` is two paths. It expands a glob in a path word as the shell does, with no dotfile match. A path word that starts with `$PWD`, `${PWD}` or a `pwd` substitution is the working folder.
- For rg and ag with no flag that turns the ignore rules off, an ignored file or folder is not read or counted. The walk does not enter an ignored folder. The list is git's own, read once per walk. grep reads ignored files, so they count for grep. The walk of a folder that `find` prints skips ignored files the same way.
- The ignore rules are off with `-u` (any count), `--no-ignore` and its variants. For ag, `-U`, `-a`, `--skip-vcs-ignores` and `--all-types` also turn them off. A tracked file is never ignored.
- The walk stops at 50000 entries, `node_modules` included. It then refuses with a reason that says the folder is too large to check, never that it holds an env file.
- A folder is always walked, and an env file that an include glob picks is refused at any folder size, whatever its suffix: `--include='*.yaml'` picks an env file that ends `.yaml`. The glob decides only the cap. Past it, a glob that no sample env file name matches, such as `*.py`, is allowed, and any other include glob is refused as too large to check. An rg `-t` type past the cap is refused. The sample-name test is `_glob_could_name_env`, the one home of the question. It reads the glob through `_glob_unescaped`, so `*\.local` is `*.local`.
- A `cd` after `&&` or `||` might not run, so the search is judged in the folder before it and the folder after it. The folder before it is judged only when the search can run without the `cd`: the `cd` follows `||`, or a connector between the `cd` and the search is not `&&` or `|`. A search in a command substitution runs where the segment that holds it runs, so `cd D && x=$(rg --hidden K)` is judged in D.
- `bash -c -- 'STRING'` runs the string after the `--`, as `bash -c 'STRING'` does.
- `git grep` reads its first plain word as a pattern, so an env name in it is text. A path after it stays judged.
- With a hidden flag, rg `-T` excludes only a type. The search still reaches the env file, so a pattern or a path that names one is refused. With `-t`, only a path that names one is refused.

Known limits:

- rg fails closed. An rg flag in neither of its flag tables might take a value, so the guard may walk the working folder too.
- ag and grep do not fail closed. An unknown flag there is read as a switch, so the walk can miss a folder the search reads.
- An rg `!` glob is not read.
- A brace sequence, such as `{a..c}`, is not expanded.
- A literal `cd <dir>` earlier in the command is followed, so the search is judged in the folder it runs in. A `cd` the guard cannot resolve (a variable, `popd`, a folder that does not exist) leaves the walk at the starting folder. Other variables and substitutions in a path word are not resolved. A `cd` after `&&` is judged in its own folder alone when only `&&` or `|` joins it to the search. `test -d D && cd D && rg K` and `test -d D && cd D && echo | rg K` search D alone, since a failed `cd` stops the search too. The guard tries every combination of up to `ENV_SKIP_LIMIT` (6) conditional `cd`s. Past 6, it tries all run, all skipped, and each one skipped alone.
- A string that `bash -c`, `sh -c`, `zsh -c`, `dash -c`, `ksh -c`, `su -c` or `eval` runs is judged as a command of its own, behind a wrapper too. A shell given a script file is not looked into.
- Accepted limit: past the cap, an rg `-g` or `--iglob` glob, or a grep `--include` glob, that matches none of the sample env file names, such as `*.py`, is allowed. A name with an env stem and a `.py` suffix would match that glob and is read, out of the walk's sight. Under the cap the walk sees it. `find . -name '*.py' | xargs rg K` also reads a file named `.env.py`, at any folder size, out of the walk's sight. Its `-name` shortcut reads `*.py` as naming no env file. Past the cap, the walk still judges each folder that a `-name` glob matches in a folder it lists. Each is walked under its own cap, but the walk stops at a printed folder too large to walk. That folder, and one the walk does not reach, is judged by its name alone, so an env file below it is read unseen.
- A search in a heredoc body is not walked.
- The walk sees a search behind a subshell paren, a `{ ...; }` group, `command`, `env`, `nice`, `sudo`, `doas`, `nohup`, `exec`, `stdbuf`, `setsid` or `xargs`.
- `env -C DIR` and `env --chdir=DIR` start the walk in DIR. `sudo -D DIR` does not: the walk starts in the folder the command runs in, so DIR is read only if that folder holds it.
- `find ... -exec`, `-execdir`, `-ok` and `-okdir` run a search that gets each name find prints. The walk judges it as it judges a search behind `xargs`: the env file find names is refused, and a folder find prints is read whole when the search reads folders. A find whose every alternative that runs the program has a `-name` or `-iname` glob before it that no env file name fits (`-name '*.py' -exec grep K {} +`) names no env file, so it is judged as such a find is behind `xargs`. A `find -type d -exec grep -r K {} +` hands each folder it prints to a search that reads folders whole, so the walk reads the start folders whole, with or without a `-prune` in front (the start folder is printed, and `grep -r` reads the pruned folder below it). That holds only when `-type d` bounds every alternative that runs the program. In `find . -type d -o -type f -exec grep K {} +`, or with a paren group of `-type d` and `-prune` in front of an `-o -type f -exec` branch, the program also gets files, so the usual name and file checks judge it.
- `xargs` with no `-r`, `-I` or `-i` runs its search once on the folder it is in when stdin names nothing, so `find . -name nomatch | xargs grep -r K` walks that folder. A find with no `-name` glob is not known to print nothing.
- A `find` path prunes a folder with `-path`, `-name` or `-type d` tests before `-prune`. A folder so pruned is not walked and does not count toward the cap. A find with a paren, `-depth` or `-delete`, or any other test before the `-prune`, prunes nothing the walk counts. Find reaches an alternative only when each one before it is false, so a `-prune` that follows an alternative with no `-prune` (`-print -o -path ./big -prune`) prunes nothing the walk counts either. When that earlier alternative holds only `-name` or `-path` tests, it shadows the prune for the entries those tests pick and no others: `-name '*.py' -o -path ./big -prune -o -print` still prunes big, which no `*.py` name picks.
- A `find` or `ls -a` piped to `xargs` names the paths the search reads. `ls -a` names the parent folder too. A find expression with `-exec` or `-printf`, or a paren group that holds a print or a program, is not read, so its start folders are walked. A paren group of `-name` tests is one test that narrows the names when every alternative in it names no env file (`\( -name '*.py' -o -name '*.md' \)`). With an explicit `-print`, only the branches that hold one are judged, and `-maxdepth` and `-mindepth` limit the walk. rg reads a file it is named whatever its `-g` globs, so a file that find names is refused for rg. grep applies its `--include` and `--exclude` globs to a file it is named. It matches each glob on the whole path find prints and on each tail after a `/`. So a file that find names is refused for grep unless those globs leave it out. `ls -a` before `xargs grep` is judged the same way, so `--include='*.py'` allows it. Where find may print a folder and the search reads folders (`grep -r`, or rg with a hidden flag, a `-g` glob or a `-t` type), the walk reads that folder whole, narrowed by the search's own `--include` or `-g` globs and `-t` type. Otherwise only the printed files are judged. A `-name` glob picks which folders find prints. With no `-name` glob, find prints every folder within its `-maxdepth` and `-mindepth` limits.
- Known limit: `find . -type f ! -name '.env*' | xargs grep K` is still refused, because the word check on the env-shaped word is kept.
- `-mindepth` filters which paths find prints. A file above that depth is not named, so it is not read.
- An ignore file other than the checkout's own is not read. So a search of a folder with an env file is refused, even when such a file skips it.
- Accepted limit: a regex with no `.env` prefix of its own, such as `prod$`, is judged on the sample names only. Rewriting `\.py$` as the names it could pick would refuse every extension filter.

Why: the user's own secrets must not enter the session. `.envrc` is in the scope for the same reason. The guard stops Claude's mistakes, not an attacker's form (`guard-guards-mistakes-only`, a guard stops mistakes, not an attacker).

Risk: likely risk (`building-guard-needs-incident`: a guard or check needs a mistake Claude has made or is likely to make in normal work). A session would likely read a `.env` or `.envrc` file while it debugs. No incident is on record. Landed 2026-09-16, the env-file rule. The guard_env module has held the rule since 2026-10-13.
