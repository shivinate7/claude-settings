# The environment file stays unread

## The ruling

No session reads, writes or commits the contents of an environment file. The user manages that file, and its values stay out of the session. The guard refuses a shell command that would do any of those, and a write tool call that names the file. The settings deny list refuses a Read or Edit call on it. A runner may load the file into its own process with its loader flag. A runner prints nothing, so no value reaches the session.

One scope covers every form: a write tool call, a shell command and a Read call. A name is any basename that starts with `.env`, except `.env.example`. The guard's forms read one shared basename matcher in guard_env (`names_env_file`).

Ruling: owner, Queue item 159 answer a, 2026-11-02 00:56 CST. Reason: `.envrc` often holds exported secrets. That is the likely risk named below.

Shell form. `judge_shell` calls `env_refusal` and `env_heredoc_refusal`. A name is a word whose basename is in the scope above. A glob that could match a name counts as the name (`_glob_could_name_env`).

- Refused: a redirect onto the file. A shell variable that holds its path, because the guard cannot follow a variable to its use. The file given to a command that is not a runner. Any other command that would read, write or commit it.
- Allowed: an existence check (`ls`, `test`, `[`, `[[`). `echo` and `printf`, where the name is text. The message or body value of `git commit` and `gh pr create`. A runner in `ENV_LOADER_COMMANDS` (node, npm, npx, pnpm, bun, deno, uv, docker, podman, and their variants) given `--env-file` or `--env-file-if-exists`.
- Substitutions (`$(...)`, backticks, `<(...)`) are judged as commands of their own, at any depth up to `ENV_MAX_DEPTH` (64). A deeper nest is refused. The substitutions in an unquoted heredoc body are judged (`env_heredoc_refusal`). A quoted heredoc body is text.

Write form. In `judge`, a write tool call (Write, Edit, MultiEdit or NotebookEdit) whose target name is in the scope is refused (`is_env`). It reads the same matcher as the shell form.

Read form. The guard does not judge Read. It returns early for Read and Grep. The settings deny list refuses a Read call on a name that starts with `.env`, at any depth. It refuses an Edit call on the same names. Its `!` carve-outs keep `.env.example` readable and editable. That reading of the `!` carve-outs comes from Claude Code's permission docs. It is not measured.

The printed refusal names no file. It names the shape of the access (`ENV_REDIRECT_REASON`, `ENV_VARIABLE_REASON`, `ENV_RUNNER_REASON`, `ENV_CONTENTS_REASON`, `ENV_DEPTH_REASON`, `ENV_TOOL_REASON`) and a remedy (`ENV_ADVICE`). The log holds the file name, for a person to read.

Known false alarms: two notes remain open in `guard_env.py`, and both are refused on main as well. `env-cwd-prose-false-alarm`: `echo "(cwd=.envs)"` and `python3 -c "print('x (cwd=.envs):')"` are refused though they only print text. `jq-lone-word-false-alarm`: a lone `jq .envs`, `jq --arg k v .environment f.json`, `jq --indent 2 .envs f.json`, `yq -o json .envs f.yaml` and `cat f | jq .environment` are refused though the program word is text. The guard allows `ag -f` and `ack -f` (a boolean flag), and the values of `grep --exclude` and `--exclude-dir`. It also allows the values of `rg -t` and `-T`, a `jq`, `gojq` or `yq` program word such as `.envs`, and `mkdir` on an env-prefixed folder. It refuses `cd` and `pushd` into such a folder, because the shell keeps its folder between calls. In each allowed form the env name is a pattern, a glob that excludes, a type name, a program or a folder name, and never a file that is read. With a hidden flag, ag reads dotfiles, so the guard judges its file regex. The hidden flags are `--hidden`, `-u` and `--unrestricted`. The regex comes from `-G` or `--file-search-regex`. The guard reads the regex as the shell gives it to ag, in bash or PowerShell (a PowerShell single quote keeps its backslashes). It tries the regex, bare and with a `./` prefix, on `.env`, `.envrc`, `.env.local`, `.env.production`, `.env.development`, `.env.test` and `.env.staging` (`ENV_SAMPLE_NAMES`). It also tries the names the regex could pick, built from its parse tree, so `\.env\.prod$` is refused. A regex that matches one of them is refused. A POSIX class such as `[[:alpha:]]` is first written out as ranges. A regex is refused too when it does not compile, holds a negated or unknown POSIX class, or has too many shapes. Accepted limit: a regex with no `.env` prefix of its own (`prod$`) is judged on the sample names only. Reading `\.py$` as every name it could pick would refuse every extension filter. Without a hidden flag, ag skips dotfiles, so its file regex is not judged. With a hidden flag, `rg` and `ag` reach each env file in a folder they walk, whatever its name. A recursive grep (`-r`, `-R`, `-d recurse`, `--recursive`, or `rgrep`, also as `egrep` and `fgrep`) reaches them without a flag. The guard refuses the search when a path word is a folder that holds an env file on disk. It refuses too when no path is named, because the working folder is walked. For `rg` and `ag` a pipe or `<` into the search clears that case, and for grep it does not. A folder with none stays allowed, and so does `rg --files`, which lists names and reads nothing. A grep `--exclude`, `--include` or `--exclude-dir` glob that skips the env file clears the search. The grep refusal names `--exclude` and `--exclude-dir` as the remedy, with no file name, since the printed reason names no file. The walk is `_env_walk`. It does not resolve a variable or a glob, follow a `cd`, read a `.gitignore` or a `-g '!...'` exclusion, or judge a heredoc body. It stops at 50000 entries and refuses. `git grep` reads its first plain word as a pattern, as `grep` does, so an env name in it is text. A path after it stays judged. For rg with a hidden flag, `-T` excludes only a type and the search still reaches the env file, so a pattern or a path that names one is refused. With `-t`, only a path that names one is refused. A `jq`, `gojq` or `yq` program word is skipped only when a file word follows it, and `-C` and other switches do not swallow that file word. It still refuses `git add` and `cat` on such a folder, on purpose: the guard cannot tell a folder from a file, and a file inside may hold the secrets. `--include`, `-g`, `--glob` and `--exclude-from` stay judged, since each can name the file.

Why: the user's own secrets must not enter the session. `.envrc` is in the scope for the same reason. The guard stops Claude's mistakes, not an attacker's form (`guard-guards-mistakes-only`, a guard stops mistakes, not an attacker).

Risk: likely risk (`building-guard-needs-incident`: a guard or check needs a mistake Claude has made or is likely to make in normal work). A session would likely read a `.env` or `.envrc` file while it debugs. No incident is on record. Landed 2026-09-16, the env-file rule. The guard_env module has held the rule since 2026-10-13.
