# Every PR opens as a draft, and CI skips drafts, except the touched tests

## The ruling

Owner, 2026-10-10 and 2026-10-13: every PR opens as a draft, and CI skips draft PRs. Lane PRs stay drafts. Only one integration PR per batch goes ready, and its run is the batch's only CI run (`git-integration-branch-merge`).

Owner ruling Q2 (when a lane PR goes ready), 2026-11-12 09:44 CST. The coordinator relayed it at 09:50 CST. A lane may move its PR from draft to ready once, after its last review and lane lint. Never per push. A PR that will not merge never goes ready.

State: Q2 is target, not live. That is the lane's reading of timing, since the owner's words give no timing. Until the cutover to per-lane merges (decision `all-repos-switch-together`), a batch still makes its one integration PR ready. That run is the batch's only CI run (`git-integration-branch-merge`). The 2026-10-13 ruling on that point is superseded at the cutover.
Until the cutover, every repo batches, except degen and home. Degen and home are switched to per-lane merge on the stable branch (ruling `own-degen-home-switch-now`, degen and home switch now), and the other child repos wait for the drain.

One exception, owner, item 400 a, 2026-11-08 06:08 CST: "A draft-only job runs just the test files a lane touches, on Windows and macOS." Lane lint runs on Linux only, so a Windows-only red (T11b of the map skill, batch run 42449331095) first showed in a batch and dropped a lane.

- Guard rule `draft-pr` refuses `gh pr create` without `--draft` or `-d`. It reads `sh -c` scripts, command substitutions and subshells. The last `--draft`, `-d` or `--draft=X` wins. A value is true only in gh's ParseBool true set (1, t, T, TRUE, true, True).
- The guard also refuses the MCP tool `mcp__github__create_pull_request` unless its input has `draft: true`.
- `checks.yml` runs on `opened`, `synchronize`, `reopened` and `ready_for_review`. The `scope` job skips when the PR is a draft. Each other job needs `scope`, so each skips too. Push to main, schedule and manual runs are unchanged.
- The `concurrency` group holds the PR draft state (`format('{0}-{1}', github.ref, github.event.pull_request.draft)`), so a draft run replaces only draft runs and a ready run only ready runs. Turning off cancel for drafts is not enough: GitHub keeps one pending run per group and replaces it even with `cancel-in-progress: false`. Snippet 4 of skill ci-hygiene carries the same expression.
- `lane-touched-tests.yml` is the exception. It runs on `opened`, `synchronize`, `reopened` and `converted_to_draft`, and every job's `if:` needs a draft, so a ready PR runs nothing in it. `.github/scripts/touched-tests.py` lists the test files the diff touches: a test file, its sibling test, the map skill's tests, a tests folder's tests. A `.ps1` selects its `x.test.ps1` and `x-*.test.ps1`. A `mods/<mod>/` file selects that mod's `*.test.mjs`, `*.test.js` and `check.mjs` files. It also writes `commands_windows` and `commands_macos`, the interpreter each listed file's `checks.yml` run line starts with. The selector exits 1 when a run line chains something before the test path, as in `cd a && node t`, or puts an env prefix before the interpreter. It also exits 1 on a flow-style step, a one-line `steps:` list and a `defaults:` block. A trailing backslash joins the next line to its run line, and in a powershell step so does a trailing backtick. It prints each touched test it does not run: HEAVY (the suites the batch shards) and NEEDS_SETUP (a browser, or one OS). Each other test runs on an OS only when a job of `checks.yml` at HEAD runs on that OS and names it, by its path or through `.github/scripts/mod-tests.sh` (the mod tests and the map skill's tests; table RUNNER_SCRIPTS). The lists come from `checks.yml`, not a hand list, so a test the batch runs on Linux alone runs on neither OS here, and is printed "no CI job runs it". A `checks.yml` the hand parser cannot read (a job with no plain runs-on, or a runner it cannot place) exits non-zero, as does an unreadable diff. Job `run` runs each system's list on windows-latest and macos-latest, each file with the interpreter its `checks.yml` run line starts with. That is the selector's `commands_windows` or `commands_macos` for that system. Only `sh`, `bash`, `node`, `node --test`, `python` and `python3` run, as an argument list and never through eval. Any other command is printed, and the file is red. Each file keeps its own exit code and reads no stdin. A `*.test.ps1` runs in its own step with `shell: powershell`, the form of the `pointer-windows` job. That step runs only `powershell` or `pwsh`, with fixed arguments and stdin closed. It uses the node and python the runner image and setup-python give, with no setup-node, as `checks.yml` does. The workflow is not in `checks.yml`, not in `all-jobs-passed` and not a required check. `lint/test_touched_tests.py` runs in the `checks` job.
- Until the cutover, the exception never runs on the integration PR. That PR is a draft too. Its draft run would run every lane's tests on the batch head. A red there would sit on the head the merge tool reads. The `touched` job's run step selects nothing, and says why, when `github.head_ref` starts with `batch-`, as `mutation_report` in `ci-scope.sh` does. A red draft check on any other head blocks the merge tool on that head until a push, because it reads check runs per commit. Until the cutover, a batched lane never merges on its own head, so the integration branch is a new head. A lone lane is its own integration PR (skill `ci-hygiene`, step 8). Its red needs a push: a real red is a real Windows or macOS failure, and a cap hang clears with a push.
- Cost of that exception: one run per lane push, and only a push that touches a test starts the `run` jobs (unmeasured). Run times and caps are in the `lane-touched-tests` rows of decision `ci-job-caps` (proof run 42480074302, one touched test); the jobs queued 2 s each (created to started). Runner minutes are free here (public repo). Queue cost, a sample of 4, not 10: the newest ready pull_request runs of `checks.yml` that ran jobs (runs 42456407663, 42458595807, 42474374623, 42476066761); the 800 newest pull_request runs held no more (not pinned). They ran 3 macOS jobs at once and 5 to 6 Windows jobs at once, longest queue 3 s. GitHub's limit is 5 concurrent macOS jobs on the Free, Pro and Team plans (Enterprise 50). All standard and larger runners share it. The limit on all jobs is 20, 40 or 60 (docs.github.com/en/actions/reference/limits, read 2026-11-08). So a batch plus 2 draft `run` jobs on macOS fills the 5 slots, and a third draft job would queue. A draft run can delay a batch's macOS job by up to one draft macOS job when 3 or more draft jobs hold slots as the batch starts. Unmeasured: the account's plan (the API returned `plan: null`) and draft runs that overlap a real batch. The run with the map skill's tests is in `ci-job-caps`.
- The merge tool never merges a draft pull request. On a draft, `--confirm` is the records page step and stops before any claim, wait or merge (`records-index-at-merge`). It reads the draft state at the start and again under the merge lock.
- A job skipped by `if:` reports as passing, unless an `all-jobs-passed` rollup needs it (skill ci-hygiene, "Before you skip a required job"). A draft needs no check, because GitHub does not merge a draft. Marking it ready fires `ready_for_review`, with the same scoped range as a `synchronize` run (`.github/scripts/ci-scope.sh`). A skipped draft run satisfies each required check (`main-branch-protection`, the one home of required-check state). The merge tool refuses a head whose checks all skipped.

Why: a draft run that arrives while a ready run is in progress cancels it, and a pending ready run is replaced. Pushes to a PR branch also spent CI on commits known to be red.

Limits:

- The guard does not judge a `gh api` POST to the pulls endpoint, or `hub pull-request`. Each can open a non-draft PR.
- A short-flag cluster such as `-dt x` is refused, a rare false alarm.
- A pull request that turns draft during the merge wait is not stopped.
- Unmeasured: that `ready_for_review` starts `checks.yml` (it comes from GitHub's documented behavior), and the saving in runs.
