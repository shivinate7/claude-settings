- What a try is. A tool call whose result has an error flag or an exit code above zero. An HTTP 4xx or 5xx counts only in such an error result: a status quoted in the output of a call that worked is no failure. A loose word such as refused in the output of a call that worked is no failure either. A relayed agent result counts when its text names the route, and its HTTP 4xx or 5xx counts, since a relay has no exit of its own. A local `git merge` is no try of pr-merge: a failed merge of a branch does not show that the PR cannot be merged. A github-reach try is any `mcp__github__` tool, any gh call, curl, wget or httpie to github.com, or git fetch, push or ls-remote. A call to the repo's merge tool (`merge`, also as `~/.claude/bin/merge`) is a try of pr-merge. So is a call to a command or script whose name holds the act word as a whole part (open-pr.sh, create-pr, push.sh, merge): it is a try of that act. A script run through bash, sh, zsh, python or node counts the same. For make, the first plain argument names the target, with no run: `make push`. Yarn and pnpm take the script name with or without run: `yarn push`, `pnpm run push-docs`. Npm takes it only after run: `npm run push-docs`. Each is a try of push. The PR word may come first (pr-open.sh, gh-pr-create.sh). An interpreter may carry a version (python3.12). The value of a runner flag is skipped, as in `make -C dir push`. A bare `npm push` is no try, since npm has no push command: only npm run names a script. pushd is no push. A try read from a script name backs a claim only when the line names the script, as a whole token. A name that is only the act word (merge, push) must sit in a backtick span. So a failed `echo {} | python3 hooks/guard_merge.py` backs no merge claim that does not name guard_merge.py, and a failed `merge 12` backs "I couldn't merge PR 12: `merge 12` exited 1." The words "the merge tool" also name the merge tool, so "I couldn't merge PR 12: the merge tool exited 1." is backed by it. A script named for a test is no try: its name starts with test- or test_, or holds -test, _test or .test (test_merge.py, test-push.sh).
- What cancels a try. A later call that works cancels an earlier failure only for the same act, program, verb and target. The target is the PR number the call names, wherever it sits among the flags (`gh pr merge --squash 12` and `gh pr merge 12 --squash` are one target), else the first plain argument. A PR's URL names its repo and its number, and a --repo qualifies a number the same way, so `gh pr merge https://github.com/o/r/pull/12` and `gh pr merge --repo o/r 12` are one target. A call with no repo is another target than either: `gh pr merge 12` is not cancelled by a success on the URL of o/r PR 12, and `gh pr merge --repo other/x 12` is another target than `gh pr merge 12`. A create names no PR. Its target is its --head branch, else the branch an earlier `git checkout` or `git switch` in the same command moved to, else unknown. A success for branch b2 does not cancel a failed create for b1. A call that names no target (a flagless create, a merge with no PR) is keyed by its own arguments. So an identical retry that works cancels its failure, and a call with other arguments cancels none: a success of `gh pr create --base main` does not cancel a failed `gh pr create --draft`. A gh pr call with no arguments and an act verb has no identity and cancels nothing. The act verbs are create, merge, close, comment, ready and edit. A bare `gh pr view` or `gh pr list` is no act and cancels as any call does. A call with `--dry-run` never counts and never cancels. A claim in the past tense (could not, was not able, was unable to) passes when each failed try of the act has a later call of the same target that worked: "I could not push at first; I rebased and pushed." A failed try is kept per act, not per PR. So an open failure for another PR keeps the past-tense rescue off, but it still backs the claim: a line that names its check passes, as in "I could not merge PR 12 at first: `merge` exited 1." while PR 13's failed merge stays open. A present claim (cannot) still blocks after that success, unless an open failure of the act backs it and the line names its check. The success of another act rescues nothing.

So "I can't open the PR because CI is red." blocks. The states of CI, checks or the batch run: is, are, was or were red, failing, running, pending or in progress, with still allowed before the state. ## Backing form

A definitive claim in prose carries one of these backings:

- `(KIND source)`, with KIND from `PREMISE_KINDS` (the kinds list in `hooks/precompact_handoff.py`). The weak kinds `notes` and `assumed` do not back a claim.
- `(route <id>)`, citing a route row.
- `(test path::name)` or `(read path:line)`. Either backs a claim only if the file exists at head.

A code span used as a claim's subject still counts as a claim. A claim with no backing is unbacked.

## STALE005: a capability stated without a backing

STALE005 (the route-claim check) reports a sentence that states a capability by route with no backing. The unit it judges is a sentence in a paragraph the range touches, not a changed line. It is report-only until it measures 10% or fewer false alarms over 20 real hits. Then it refuses. Source for the threshold: coordinator pick Q3 (the threshold question), 2026-11-06 11:47 CST, process-only.

UNKNOWN and HISTORY rows are skipped, and so is a row with no rev (read lint/prove_route_judge.py:39-40, :115-116).
