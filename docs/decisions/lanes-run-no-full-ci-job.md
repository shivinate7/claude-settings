# A lane never runs a full CI job

## The ruling

Owner, 2026-10-27 (waiting page item 27, option a): a lane runs only the suites its change touches. It never runs a whole CI job locally, `bin/ci-job` included. The batch's integration CI run is the only full run (`roles-each-layer-proves-once`, each layer proves a change once). `bin/ci-job` stays, as a tool any session may run on demand. One exception: a lane runs `merge --lane-lint <pr>` before it hands off, and the batch runner runs it again before the join. `merge --lane-lint` runs `bin/ci-job checks --lint --base origin/<base>` at the lane head. That mode runs only the fast `python3 lint/...`, `python3 actions/...` and `bin/ste-changed` steps, chosen from the step commands in checks.yml. It runs no hook suite and no mutation test. For the STE lint `uses:` action, it runs `bin/ste-changed <base>`. With no `--base`, `--lint` takes `origin/main` and says so, or prints one unknown line and exits 2 when `origin/main` is absent. Why: a no-base run skipped the pull-request steps and read as a pass (incident 2026-10-28, batch 5: the comment narration check then failed in CI). With `--base`, ci-job sets `GITHUB_BASE_REF` in each step, as the runner does on a pull request. A lane that adds a record is therefore not red for its stale records page.

The check (incident 2026-11-01, batches 59 and 60: lane PRs #974, #979, #984, #990 and #1004 joined with shellcheck, ruling kind or STE reds). Both sides run `merge --lane-lint <pr>`, which runs that same `--lint` in a temporary worktree at the lane's head.

- The lane runs it before it hands its PR and head off. A red lane does not hand off.
- The batch runner runs it on each lane head before the join. It refuses a red lane, and that lane fixes and hands off again.
- The batch runner runs it on the batch head (`merge --lane-lint <integration branch>`) before it marks the integration PR ready. A FAIL keeps the PR a draft. A hand list of checks never stands in for this run (coordinator, 2026-11-06 15:29 CST): one missed the comment narration check in batch 36.
- A FAIL refuses. An unknown refuses unless `--lint-unknown-ok "<reason>"` is given, and the reason is logged. A lint timeout (1200 s) is an unknown that `--lint-unknown-ok` does not lift. The lane re-runs it.
- Under a `Merge after: #N` parent, the lint refuses a review range start unless the lane head holds it, it holds each parent's merge base, and it adds no commit. The range must end at the lane head, its branch, or 7 or more hex digits of it (triage, 2026-11-08 09:05 CST).
- No silent pass (owner, 2026-11-07 13:20 CST; definition by the coordinator, 20:35 CST). A `--lint` run that runs no lint CI step is unknown and exits 2. A required CI step is a lint CI step whose `if:` reads true on a pull-request run. When one is skipped, the run is unknown and exits 2. A CI step whose `if:` holds only off a pull request prints `skipped` and does not fail. The PASS line names each skipped CI step. Plain ci-job runs keep their verdicts.

Cost: one ci-job run (about 550 s to 660 s, 4 runs on 2026-11-01) and one worktree per call. It runs once at hand-off, once per lane at the join, and once on the batch head before ready. It writes one ci-job log, and keeps no other file.

The ready checks (incident 2026-11-07 05:28 CST, q_max batch 1064): the batch went ready without its check-invariants step and was red in CI on a bare decision cite. One CI cycle was wasted. A repo names the steps that must pass before a draft goes ready in `merge.readyChecks`, a list of step names of its checks job, in `.github/stamp.json`. The draft step (`merge <pr> --confirm` on a draft) runs `bin/ci-job checks --step NAME ... --base origin/<base>` on the tree it would push, before any push and before the ready mark. It does this on every path: the default base, another base, and a Record-claim head. A FAIL or an unknown stops the step with the step lines and the log. Nothing is pushed and the PR stays a draft. No flag lifts it. A repo with no list runs no ready check, and the step prints one line saying so. Cost: one ci-job run and one worktree per draft-step ready. Its time is unmeasured for a step subset. Known bypass: a session that marks the PR ready by MCP or `gh pr ready` without running the draft step skips the checks.

Why: a full local run per lane proves again what the batch run proves, and costs a lane its time. A fixture that copies a changed file is caught by the batch run, and the fixtures now copy what git tracks, so a new shared module no longer breaks them.
