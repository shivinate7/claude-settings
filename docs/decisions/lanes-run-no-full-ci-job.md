# A lane never runs a full CI job

## The ruling

Owner, 2026-10-27 (waiting page item 27, option a): a lane runs only the suites its change touches. It never runs a whole CI job locally, `bin/ci-job` included. The batch's integration CI run is the only full run (`roles-each-layer-proves-once`, each layer proves a change once). `bin/ci-job` stays, as a tool any session may run on demand. One exception: a lane runs `merge --lane-lint <pr>` before it hands off, and the batch runner runs it again before the join. `merge --lane-lint` runs `bin/ci-job checks --lint --base origin/<base>` at the lane head. That mode runs only the fast `python3 lint/...`, `python3 actions/...` and `bin/ste-changed` CI steps, chosen from the CI step commands in checks.yml. It runs no hook suite and no mutation test. `merge --lane-lint` adds one run of a CI step's command when the diff touches the mutation-test files (see the mutation run below). For the STE lint `uses:` action, it runs `bin/ste-changed <base>`. With no `--base`, `--lint` takes `origin/main` and says so, or prints one unknown line and exits 2 when `origin/main` is absent. Why: a no-base run skipped the pull-request steps and read as a pass (incident 2026-10-28, batch 5: the comment narration check then failed in CI). With `--base`, ci-job sets `GITHUB_BASE_REF` in each step, as the runner does on a pull request. A lane that adds a record is therefore not red for its stale records page.

The check (incident 2026-11-01, batches 59 and 60: lane PRs #974, #979, #984, #990 and #1004 joined with shellcheck, ruling kind or STE reds). Both sides run `merge --lane-lint <pr>`, which runs that same `--lint` in a temporary worktree at the lane's head.

- The lane runs it before it hands its PR and head off. A red lane does not hand off.
- The batch runner runs it on each lane head before the join. It refuses a red lane, and that lane fixes and hands off again.
- The batch runner runs it on the batch head (`merge --lane-lint <integration branch>`) before it marks the integration PR ready. A FAIL keeps the PR a draft. A hand list of checks never stands in for this run (coordinator, 2026-11-06 15:29 CST): one missed the comment narration check in batch 36.
- A FAIL refuses. An unknown refuses unless `--lint-unknown-ok "<reason>"` is given, and the reason is logged. A lint timeout (1200 s) is an unknown that `--lint-unknown-ok` does not lift. The lane re-runs it.
- No silent pass (owner, 2026-11-07 13:20 CST; definition by the coordinator, 20:35 CST). A `--lint` run that runs no lint CI step is unknown and exits 2. A required CI step is a lint CI step whose `if:` reads true on a pull-request run. When one is skipped, the run is unknown and exits 2. A CI step whose `if:` holds only off a pull request prints `skipped` and does not fail. The PASS line names each skipped CI step. Plain ci-job runs keep their verdicts.

Cost: one ci-job run (about 550 s to 660 s, 4 runs on 2026-11-01) and one worktree per call. It runs once at hand-off, once per lane at the join, and once on the batch head before ready. It writes one ci-job log, and keeps no other file.

The mutation run: a head whose diff touches `hooks/mutate_*.py` or `hooks/mutate_*.mjs` (the mutation-test files) also runs the one-line `run:` of the CI step "Guard mutation test" in the CI job `checks-mutate-guard`. The command is read from the head's checks.yml, and the cap is that job's `timeout-minutes`. It runs after a passing lint, or after an unknown lint that `--lint-unknown-ok` lifts, in the lint's own worktree. It prints wall time and killed, survived and unknown mutant counts. Unknown mutants are the table's crashed column (a timeout lands there) or the tally line's wrong-cause count. It FAILs on any survivor; on more than `MUTATE_UNKNOWN_MAX` (5) unknown mutants, since a flaky mutant or two is noise and a harness that cannot run reads hundreds; on a run past the cap; on no readable report at any exit; and on an `UNKNOWN` row, a file that read no mutant. A readable report is judged by its counts at any exit code, since the real command exits 1 on any wrong-cause mutant. `--lint-unknown-ok` never lifts this FAIL.

Mistake it guards: the mutation-test change that timed out on every target. A PR that changed `hooks/mutate_*.py` joined a batch with no CI-sized mutation run. Its control run (GitHub Actions run 42620238014) hit 670 of 694 mutants unknown, and one batch run was lost.

Cost: an untouched diff adds one `git diff --name-only` and no run. A touched diff adds one run of that command, about 11 to 16 min locally (builder's figure; unmeasured on CI), and no worktree. Tests: `merge/test_lane_lint.py`, about 0.1 s per touched case with a stub.

The ready checks (incident 2026-11-07 05:28 CST, q_max batch 1064): the batch went ready without its check-invariants step and was red in CI on a bare decision cite. One CI cycle was wasted. A repo names the steps that must pass before a draft goes ready in `merge.readyChecks`, a list of step names of its checks job, in `.github/stamp.json`. The draft step (`merge <pr> --confirm` on a draft) runs `bin/ci-job checks --step NAME ... --base origin/<base>` on the tree it would push, before any push and before the ready mark. It does this on every path: the default base, another base, and a Record-claim head. A FAIL or an unknown stops the step with the step lines and the log. Nothing is pushed and the PR stays a draft. No flag lifts it. A repo with no list runs no ready check, and the step prints one line saying so. Cost: one ci-job run and one worktree per draft-step ready. Its time is unmeasured for a step subset. The run passes `--pinned`. Incident 2026-11-08 15:13 CST: the ready check ran q_max's harness from the local copy. So a skill bump on main blocked q_max before its pin moved. Under `--pinned` a `code-check` or `zizmor` step pinned as `<owner>/claude-settings/actions/<name>@<40-hex>` runs from a `git archive` of that commit. A sha the clone lacks is fetched by sha. A pin that cannot be fetched, archived or read reads unknown, never a pass. The ste-lint step stays local: a stale ste-lint pin still exits 3 with its remedy (decision `action-pins-follow-sessions`, CI pins follow the session's tools). A non-sha ref, a local `uses:`, `--lint`, `--plan` and a run without the flag are unchanged. Cost: at most one fetch and one archive per distinct sha per run. The export is deleted at run end. A fetch keeps its objects and `FETCH_HEAD` in the clone it exports from (beside `ci-job`, else the pointer checkout). Named limits: the `uses:` owner is not checked. A quoted or uppercase 40-hex pin runs the local copy. A kill by merge's timeout leaves at most one export per distinct sha in the temp folder. A fetch that fails for network or auth reads unknown with the pin remedy. Known bypass: a session that marks the PR ready by MCP or `gh pr ready` without running the draft step skips the checks.

Why: a full local run per lane proves again what the batch run proves, and costs a lane its time. A fixture that copies a changed file is caught by the batch run, and the fixtures now copy what git tracks, so a new shared module no longer breaks them.
