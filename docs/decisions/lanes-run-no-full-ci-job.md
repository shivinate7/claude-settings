# A lane never runs a full CI job

## The ruling

Owner, 2026-10-27 (waiting page item 27, option a): a lane runs only the suites its change touches. It never runs a whole CI job locally, `bin/ci-job` included. Until the cutover (decision `all-repos-switch-together`), the batch's integration CI run is the only full run. After it, main's run after each merge is the full run (`roles-each-layer-proves-once`, each layer proves a change once). `bin/ci-job` stays, as a tool any session may run on demand. One exception: a lane runs `merge --lane-lint <pr>` before it hands off, and the batch runner runs it again before the join. `merge --lane-lint` runs `bin/ci-job checks --lint --base origin/<base>` at the lane head. That mode runs only the fast `python3 lint/...`, `python3 actions/...` and `bin/ste-changed` steps, chosen from the step commands in checks.yml. It runs no mutation test. It runs a CI step that holds a `python3 hooks/test_*.py` or `python3 merge/test_*.py` line, whole, as CI runs it. It does so only when the one selector (`hooks/mutate_guard.py --lint-suites <base>`) picks that suite for a file of the lane's diff. The selector follows imports and path reads: a suite is picked for a change to any module that a module it loads imports, or a file it reads by path. Job scope is the linted job only: a picked suite in another job's CI step prints one `not run` line naming that job and its suites, and runs nowhere here. A picked suite that fails is a FAIL. A line before the suite that fails, so the shell never reaches it, is an unknown. A selector that cannot run, or runs past its 60 s limit, is an unknown, exit 2. Cost, per `--lint` run: a selector process (about 7 s, measured 2026-11-13 on this tree), plus a shell process per picked CI step, which runs that step's suites. A diff that touches no file a suite loads picks no suite, so it costs only the selector. A picked set grows with the module; debt `lane-lint-hub-cost` holds the counts per module, the checks job's total and the selector's breakdown. The time per suite is unmeasured; the run stays inside `LINT_SECONDS` in `merge/merge.py` or ends unknown (debt `lane-lint-hub-cost`). For the STE lint `uses:` action, it runs `bin/ste-changed <base>`. With no `--base`, `--lint` takes `origin/main` and says so, or prints only an unknown line and exits 2 when `origin/main` is absent. Why: a no-base run skipped the pull-request steps and read as a pass (incident 2026-10-28, batch 5: the comment narration check then failed in CI). With `--base`, ci-job sets `GITHUB_BASE_REF` in each step, as the runner does on a pull request. A lane that adds a record is therefore not red for its stale records page.

The lint run has one mutation-test exception to "It runs no mutation test" above. The one named exception (owner, waiting page item 463 a, 2026-11-09 13:09 CST; the next sentence is a paraphrase in glossary terms, and that item holds the owner's exact words): for a lane that changes the mutation test, its own suite is the mutation job, run before the batch. When a lane's diff touches a file that the code matches as `hooks/mutate_*.py` or `hooks/mutate_*.mjs` (today `hooks/mutate_guard.py`, `hooks/mutate_shared.py` and `hooks/mutate_js.mjs`), `merge --lane-lint` also runs the command of each mutation test shard job, a whole CI step each, on that head (see the mutation test below). `janitor/mutate_sweep.py` and the test files are not in that match, so a diff that touches only them runs no mutation test.

The check (incident 2026-11-01, batches 59 and 60: lane PRs #974, #979, #984, #990 and #1004 joined with shellcheck, ruling kind or STE reds). Both sides run `merge --lane-lint <pr>`, which runs that same `--lint` in a temporary worktree at the lane's head.

- The lane runs it before it hands its PR and head off. A red lane does not hand off.
- The batch runner runs it on each lane head before the join. It refuses a red lane, and that lane fixes and hands off again.
- Until the cutover (decision `all-repos-switch-together`), the batch runner runs `merge --lane-lint <integration PR number>` on the batch head, after the draft step's page push and before it marks the integration PR ready. After the cutover, it runs on each lane PR's head before that PR merges. A ref target posts no comment, so it cannot satisfy the join. A FAIL keeps the PR a draft. A hand list of checks never stands in for this run (coordinator, 2026-11-06 15:29 CST): one missed the comment narration check in batch 36.
- The integration PR call runs the mutation test when the diff touches a mutation test file. On its first call per head, no hand-off PASS comment names the integration PR (see the mutation test below). A re-run on an unchanged head skips it only in a session with the recorded `batch-runner` role (a cloud session), because the first run's own PASS now names it. Any other session runs it again. It prints `mutation test run skipped here: it runs at the lane's hand-off lint` when it skips.
- A PASS on a pull request number posts one comment on it: the marker `<!-- lane-lint -->`, then `PR: #<n>`, `Head: <40-hex head the lint read>` and `Result: PASS`. A FAIL, an unknown and a ref or commit target post nothing. A failed post prints the PASS and a reason line, and exits 0.
- The comment is the proof. In a cloud session, the batch runner's join (`merge <pr> --confirm` on a ready PR) needs it before any lock, claim or push. The join takes the newest lane-lint comment that names the PR's live head. That comment must come from the repo's owner (`author_association` OWNER) and say `Result: PASS`. Any other comment is ignored: an older head, a FAIL, or a non-owner author. `merge --reviewed` reads a done record as `no lint`, `lint fail` or `lint unknown` (a comment with no readable Result). It leaves that record out of the batch line. Both name `merge --lane-lint <pr>`. A failed read of the comments refuses the join as `lane lint unknown`. A PASS for an earlier head also counts when every later commit is a claim. A claim has one parent, a Record-claim trailer, and only record files touched (a stamp kind's folder, or the records page). A claim that rewrites a cite in another file reads as a new head, so the lane lints again. A head pushed after the join's read is refused before any merge call. A cloud-session post on shivinate7/claude-settings reads back OWNER (measured pull request 2382, comment 6732994630, 2026-11-09 05:28 UTC). An org-owned repo or a non-OWNER token stays unmeasured, and refuses every join (fail-closed). (read merge/merge.py::lint_check)
- A FAIL refuses. An unknown refuses unless `--lint-unknown-ok "<reason>"` is given, and the reason is logged. A lint timeout (3600 s) is an unknown that `--lint-unknown-ok` does not lift. The lane re-runs it.
- No silent pass (owner, 2026-11-07 13:20 CST; definition by the coordinator, 20:35 CST). A `--lint` run that runs no lint CI step is unknown and exits 2. A required CI step is a lint CI step whose `if:` reads true on a pull-request run. When one is skipped, the run is unknown and exits 2. A CI step whose `if:` holds only off a pull request prints `skipped` and does not fail. The PASS line names each skipped CI step. Plain ci-job runs keep their verdicts.

The main rule (step cross-measure-main-net, incident 2026-11-10). `merge --lane-lint` first merges every head into `origin/<base>` with `git merge-tree --write-tree`, a ref or commit target too. A conflict is a FAIL that names the base. An unreadable merge-tree is an unknown stop. Why: the check once read only pairs of PRs, so a clash that came through main was blamed on the sibling PR, and a head that conflicted with main passed.

The cross rule. A PR number is also measured against each other open PR of its lane (a body with the same session URL, a draft too) and each PR that `--with` names. Why: two PRs of one lane that clash cannot join one batch unless they stack (PRs 1923 and 2112, batch 68). A stack pair is skipped. A clash counts only when both heads merge clean with the base. Any other clash is a report line after the PASS line, and it names the PR that conflicts with the base.

The order: the stack stop, the base check, the cross-measure, then the ci-job run. An unknown in the first three stops before the ci-job run, and `--lint-unknown-ok` never lifts it. A FAIL in the base check or the cross-measure stops there too, as on main: a counted FAIL never runs the ci-job. One refusal lists every FAIL block of those two checks, with no PASS line and no comment. `--lint-unknown-ok` lifts none of them.

The missing-tree-file stop (incident 02:12 CST Nov 10, 2026, in the lane-lint lane of PR 2379, head eb8defaba: the lint ran the full 1200 s twice and read unknown, and its Python 3.9 floor tests failed with FileNotFoundError for `lint/check_python_floor.py` and `.github/workflows/checks.yml`, though both were on main and on the head; the cause of the missing files is unmeasured). Before any step, a lint worktree that lacks `lint/check_python_floor.py` or `.github/workflows/checks.yml` while the head's git tree holds it is UNKNOWN. It exits 1, like every lane-lint refusal (exit 2 is argparse's usage code), names the file, and `--lint-unknown-ok` never lifts it. Why: the floor step only crashed on the file, and its FAIL blamed the lane for a defect of the worktree. The check reads the head's git tree, so a head that never held the file is not stopped. Cost: one `git ls-tree` of the head. (read merge/merge.py::refuse_incomplete_tree)

Cost: one ci-job run and one worktree per call (unmeasured). The base check adds one `git merge-tree` of the head. The cross rule adds one PR-list read, and two merge-trees for each PR compared (that PR against the base, and against the head), none for a stack pair (unmeasured). A lane with a counted FAIL pays no ci-job run. It runs once at hand-off, once per lane at the join, and once on the batch head before ready (unmeasured). It keeps one ci-job log and no other file at the end. A PASS on a PR number adds one REST POST. The join adds one paged read of the repo's comments, and `--reviewed` adds none: it reads the lint comments from the list it already reads (unmeasured). Run serially on main 0e6509a96, the 93 lint steps took about 1290 s of wall time (1 cloud run, step sum 1315 s, reported by the #2443 lane on 2026-11-10) (not pinned). That passed the 1200 s bound. So `--lint` runs its lint steps at once, up to `CI_JOB_LINT_WORKERS` workers, else the smaller of the CPU count and 4. One worker is the serial run. Install steps, plain runs, `--step` and `--plan` stay serial. With 4 workers the same run took 379.5 s (1 sample, this lane's builder run) (not pinned). With more than one worker it adds one thread per worker, one temp folder, and one temp log per lint step. Temp logs are deleted when ci-job ends. One exception: a log whose copy into the run's log failed is kept, with its folder, and named on stderr. Named limit: a kill by merge's timeout (SIGKILL reaches only ci-job) leaves the temp folder and may leave verdict child processes running.

The mutation test: a head whose diff touches `hooks/mutate_*.py` or `hooks/mutate_*.mjs` (the mutation-test files) runs it, as the command of each CI shard job, one after another (`merge/test_lane_lint.py` pins that a touched `.mjs` file starts it). Main splits the mutation test into three shard jobs: `checks-mutate-guard`, `checks-mutate-guard-b` and `checks-mutate-guard-c`. Each job has one step, "Guard mutation test, shard i/M", with its own `MUTATE_SHARD` env, one-line `run:` and `timeout-minutes`. The lint reads all three from the head's checks.yml, starts each run with that env under that job's cap, and stops before any later shard when one fails or times out. Its FAIL names that job. A shard step that is absent, a job with no one-line `run:` or no `timeout-minutes`, or an env that does not match its step stops the lint before the first run, and the stop names the job or the shard. A head with no shard step and the old step "Guard mutation test" in `checks-mutate-guard` runs once, as before. A rename reads by its old path (`--no-renames`). A merge base that cannot be read is an unknown stop. The clash check before it reads an unrelated history as unknown, so the lint never lists files from a guess. It runs after a passing lint, or after an unknown lint that `--lint-unknown-ok` lifts, in the lint's own worktree. It prints wall time and killed, survived and unknown mutant counts. The caller decides, not the diff. The hand-off `merge --lane-lint` runs it. The batch runner's pre-join `merge --lane-lint` (a recorded `batch-runner` merge role) skips it when a hand-off PASS comment names the live head, and runs it for any other head. CI runs the same job on the batch head. The PR-number call on the integration PR (`merge --lane-lint <integration PR number>`) has no hand-off PASS comment on its first call per head, so it runs it.

It FAILs on any survivor, on any unknown mutant, on a run past the cap, on a command that cannot start, and on no readable report at any exit. Zero tolerance, as in CI (`hooks/mutate_shared.py` run_mutants exits 1 on any survivor, wrong cause or unknown). It FAILs on an `UNKNOWN` row, a file that read no mutant. A readable report is judged by its counts at any exit code. In the table form the unknown count is the crashed column, where a timeout lands. The tally form is the line the job prints, `K of N mutations killed (S survived, W wrong cause, X skipped, U unknown)`; `, U unknown` prints only when U is not 0. The lint reads each count by its label and FAILs on any wrong-cause or unknown mutant. A clean tally at a nonzero exit also FAILs, since CI is red on the exit code. A suite timeout aborts before the tally, so the lint reads no report and FAILs. A command that cannot start (a missing program) prints a FAIL line and no traceback. `--lint-unknown-ok` never lifts a FAIL here.

Named limits:

- The trigger omits the files the mutation test also covers: the guard, config watch, decision watch, ruling home, override, call judge and sim-lease targets, with their test suites. Widening costs 11 to 16 min on every guard edit: a debt, not built.
- The skip at the pre-join lint reads the merge role. A local batch runner records no role, so its pre-join lint always runs the mutation test: the safe direction, one extra run. A failed read of the comments also runs it.
- The lint times the command on the lane machine against the job cap. CI adds setup time, so a run near the cap can pass here and time out in CI.

Mistake it guards: the mutation-test change that timed out on every target. A PR that changed `hooks/mutate_*.py` joined a batch with no CI-sized mutation test run. Its control run (GitHub Actions run 42620238014) timed out on every target: 670 of 694 mutants unknown. One batch run was lost.

Cost: an untouched diff adds one `git diff --name-only` and no run (not pinned). A touched lane pays the shard runs once per hand-off lint, up to three timed runs one after another. A normal lane lint pays no shard run. The batch runner's pre-join lint repeats it only when no hand-off PASS names the live head. The PR-number call `merge --lane-lint <integration PR number>` runs it, so every batch that touches a mutation test file pays up to three more runs at the integration PR's lint (not pinned). Measured on main, 1 run (checks run 43564136731, 2026-11-14, not pinned): job `checks-mutate-guard` took 1266 s of wall time, `checks-mutate-guard-b` 654 s and `checks-mutate-guard-c` 426 s. The first job also holds the progress beat step, which the lint does not run. The three shard steps took 1130 s, 618 s and 400 s, so a lint pays about 2148 s of step time in CI (1 run, not pinned). The lane machine's time for the three is unmeasured. Each shard job has a 60 min cap (provisional, `ci-job-caps`), so the worst case is up to three runs of 60 min. Decision `ci-job-caps` records an older run (42608474160) of the one job, cancelled at the 25 min cap with 616 of 694 mutants killed. Each run is one whole CI step, not a slice of one, and reuses the lint's worktree.

CI runs the job on the batch head, and stays the backstop. Coordinator option a, 08:54 CST Nov 12: the pre-join lint skips the run only when a hand-off PASS names the live head, and runs it for any other head. That skip holds only in a session that has recorded the `batch-runner` merge role, which only a cloud session can record. merge.py passes `pre_join = read_merge_role() == "batch-runner"` to `lane_lint`, which also needs a PR number target and `hand_off_pass`. A session with no recorded role runs the mutation test on every call, a re-run on an unchanged head too. The integration PR's own `--lane-lint <integration PR number>` still runs it, a lane choice pending the coordinator. Tests: `merge/test_lane_lint.py` mutation-test cases, about 0.2 s per lint with a stub (builder's figure).

The ready checks (incident 2026-11-07 05:28 CST, q_max batch 1064): the batch went ready without its check-invariants step and was red in CI on a bare decision cite. One CI cycle was wasted. A repo names the steps that must pass before a draft goes ready in `merge.readyChecks`, a list of step names of its checks job, in `.github/stamp.json`. The draft step (`merge <pr> --confirm` on a draft) runs `bin/ci-job checks --step NAME ... --base origin/<base>` on the tree it would push, before any push and before the ready mark. It does this on every path: the default base, another base, and a Record-claim head. A FAIL or an unknown stops the step with the step lines and the log. Nothing is pushed and the PR stays a draft. No flag lifts it. A repo with no list runs no ready check, and the step prints one line saying so. Cost: one ci-job run and one worktree per draft-step ready (unmeasured). Its time is unmeasured for a step subset. The run passes `--pinned`. Incident 2026-11-08 15:13 CST: the ready check ran q_max's harness from the local copy. So a skill bump on main blocked q_max before its pin moved. Under `--pinned` a `code-check` or `zizmor` step pinned as `<owner>/claude-settings/actions/<name>@<40-hex>` runs from a `git archive` of that commit. A sha the clone lacks is fetched by sha. A pin that cannot be fetched, archived or read reads unknown, never a pass. The ste-lint step stays local: a stale ste-lint pin still exits 3 with its remedy (decision `action-pins-follow-sessions`, CI pins follow the session's tools). A non-sha ref, a local `uses:`, `--lint`, `--plan` and a run without the flag are unchanged. Cost: at most one fetch and one archive per distinct sha per run. The export is deleted at run end. A fetch keeps its objects and `FETCH_HEAD` in the clone it exports from (beside `ci-job`, else the pointer checkout). Named limits: the `uses:` owner is not checked. A quoted or uppercase 40-hex pin runs the local copy. A kill by merge's timeout leaves at most one export per distinct sha in the temp folder. A fetch that fails for network or auth reads unknown with the pin remedy. Known bypass: a session that marks the PR ready by MCP or `gh pr ready` without running the draft step skips the checks.

Why: a full local run per lane proves again what the batch run proves, and costs a lane its time. A fixture that copies a changed file is caught by the batch run, and the fixtures now copy what git tracks, so a new shared module no longer breaks them.
