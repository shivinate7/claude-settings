# A lane never runs a full CI job

## The ruling

Owner, 2026-10-27 (waiting page item 27, option a), for lane heads: a lane runs only the suites its change touches. It never runs a whole CI job locally, `bin/ci-job` included. The batch's integration CI run is the merge check for the full suites (`roles-each-layer-proves-once`, each layer proves a change once). `bin/ci-job` stays, as a tool any session may run on demand. One exception: a lane runs `merge --lane-lint <pr>` before it hands off, and the batch runner runs it again before the join. On a lane head, `merge --lane-lint` runs `bin/ci-job checks --lint --base origin/<base>`. That mode runs only the fast `python3 lint/...`, `python3 actions/...` and `bin/ste-changed` steps, chosen from the step commands in checks.yml. It runs no hook suite and no mutation test. For the STE lint `uses:` action, it runs `bin/ste-changed <base>`. With no `--base`, `--lint` takes `origin/main` and says so, or prints one unknown line and exits 2 when `origin/main` is absent. Why: a no-base run skipped the pull-request steps and read as a pass (incident 2026-10-28, batch 5: the comment narration check then failed in CI). With `--base`, ci-job sets `GITHUB_BASE_REF` in each step, as the runner does on a pull request. A lane that adds a record is therefore not red for its stale records page.

Batch heads: owner ruling fb-1248-1 (2026-11-10 12:48 CST, option a) covers them. The batch form runs only for an integration branch named `batch-` plus digits and nothing more (`batch-73`; `batch-73-fix` is a lane). Normalise the target first, stripping `refs/heads/`, `refs/remotes/origin/` and `origin/`. A bare sha, or a name that does not resolve to a branch, takes the lint route. So does a lane branch such as `batch-push-full-checks`. Every run prints one line naming the route and why. The batch form runs the full checks job, the guard mutation anchor check and the Windows guard slice, run locally before the integration PR goes ready. Lane heads stay as above. The batch form of `merge --lane-lint`:

- Runs every CI step of the checks job through `bin/ci-job`. It also runs the guard mutation anchor check (`python3 hooks/mutate_guard.py --anchors`) and the Windows guard slice (the slice CI step of job `checks-windows-guard`).
- Runs `rebuild_records` in its temp worktree before the checks, so the hook catalog CI step reads a fresh records page.
- Runs `debt_check` on the head.
- Has its own budget, `BATCH_SECONDS`, 3600 s. The lint budget, `LINT_SECONDS`, 1200 s, does not apply. A timeout at this budget is an unknown that `--lint-unknown-ok` does not lift, as a lint timeout is.
- Re-runs each CI step that ends FAIL or UNKNOWN on the head, on `origin/<base>` in a temp worktree. A head FAIL is excused, with the line "red on main too", only when main also FAILs and every failing case name on the head is also a failing case name on main. A failing case name is a unittest `FAIL: <case>` or `ERROR: <case>` line in the CI step's own log section. Otherwise, or when either side gives no case names, the FAIL stops the run.
- An UNKNOWN on the head stops the run, whatever main reads, unless `--lint-unknown-ok "<reason>"` is given (ruling No silent pass, 2026-11-07 13:20 CST). An unknown on main too prints "unknown on main too" and does not lift the stop. Each lift is printed.
- A Retire check (check_debt_retire) that times out at its 600 s cap prints the `Retire-run:` cite remedy, and the run goes on. A Retire check that fails stops the run.

The check (incident 2026-11-01, batches 59 and 60: lane PRs #974, #979, #984, #990 and #1004 joined with shellcheck, ruling kind or STE reds). Both sides run `merge --lane-lint <pr>`, which runs that same `--lint` in a temporary worktree at the lane's head.

- The lane runs it before it hands its PR and head off. A red lane does not hand off.
- The batch runner runs it on each lane head before the join. It refuses a red lane, and that lane fixes and hands off again.
- The batch runner runs `merge --lane-lint <integration branch>` on the integration branch's head before it marks the integration PR ready. That is the batch form, above. A FAIL keeps the PR a draft. A hand list of checks never stands in for this run (coordinator, 2026-11-06 15:29 CST): one missed the comment narration check in batch 36.
- A FAIL refuses. An unknown refuses unless `--lint-unknown-ok "<reason>"` is given, and the reason is logged. A lint timeout (1200 s) is an unknown that `--lint-unknown-ok` does not lift. The lane re-runs it.
- No silent pass (owner, 2026-11-07 13:20 CST; definition by the coordinator, 20:35 CST). A `--lint` run that runs no lint CI step is unknown and exits 2. A required CI step is a lint CI step whose `if:` reads true on a pull-request run. When one is skipped, the run is unknown and exits 2. A CI step whose `if:` holds only off a pull request prints `skipped` and does not fail. The PASS line names each skipped CI step. Plain ci-job runs keep their verdicts.

Cost: one ci-job run and one worktree per call. A lane runs it at hand-off and once per lane at the join. The batch runner runs the batch form once, on the integration branch's head before ready. That run covers every checks-job step, so it costs more than a lint run. Its wall time and file count are unmeasured. Its budget is 3600 s. A lint run keeps one ci-job log and no other file at the end. Run serially on main 0e6509a96, the 93 lint steps took about 1290 s of wall time (1 cloud run, step sum 1315 s, reported by the #2443 lane on 2026-11-10). That passed the 1200 s bound. So `--lint` runs its lint steps at once, up to `CI_JOB_LINT_WORKERS` workers, else the smaller of the CPU count and 4. One worker is the serial run. Install steps, plain runs, `--step` and `--plan` stay serial. With 4 workers the same run took 379.5 s (1 sample, this lane's builder run). With more than one worker it adds one thread per worker, one temp folder, and one temp log per lint step. Temp logs are deleted when ci-job ends. One exception: a log whose copy into the run's log failed is kept, with its folder, and named on stderr. Named limit: a kill by merge's timeout (SIGKILL reaches only ci-job) leaves the temp folder and may leave verdict child processes running.

The ready checks (incident 2026-11-07 05:28 CST, q_max batch 1064): the batch went ready without its check-invariants step and was red in CI on a bare decision cite. One CI cycle was wasted. A repo names the steps that must pass before a draft goes ready in `merge.readyChecks`, a list of step names of its checks job, in `.github/stamp.json`. The draft step (`merge <pr> --confirm` on a draft) runs `bin/ci-job checks --step NAME ... --base origin/<base>` on the tree it would push, before any push and before the ready mark. It does this on every path: the default base, another base, and a Record-claim head. A FAIL or an unknown stops the step with the step lines and the log. Nothing is pushed and the PR stays a draft. No flag lifts it. A repo with no list runs no ready check, and the step prints one line saying so. Cost: one ci-job run and one worktree per draft-step ready. Its time is unmeasured for a step subset. The run passes `--pinned`. Incident 2026-11-08 15:13 CST: the ready check ran q_max's harness from the local copy. So a skill bump on main blocked q_max before its pin moved. Under `--pinned` a `code-check` or `zizmor` step pinned as `<owner>/claude-settings/actions/<name>@<40-hex>` runs from a `git archive` of that commit. A sha the clone lacks is fetched by sha. A pin that cannot be fetched, archived or read reads unknown, never a pass. The ste-lint step stays local: a stale ste-lint pin still exits 3 with its remedy (decision `action-pins-follow-sessions`, CI pins follow the session's tools). A non-sha ref, a local `uses:`, `--lint`, `--plan` and a run without the flag are unchanged. Cost: at most one fetch and one archive per distinct sha per run. The export is deleted at run end. A fetch keeps its objects and `FETCH_HEAD` in the clone it exports from (beside `ci-job`, else the pointer checkout). Named limits: the `uses:` owner is not checked. A quoted or uppercase 40-hex pin runs the local copy. A kill by merge's timeout leaves at most one export per distinct sha in the temp folder. A fetch that fails for network or auth reads unknown with the pin remedy. Known bypass: a session that marks the PR ready by MCP or `gh pr ready` without running the draft step skips the checks.

Why: a full local run per lane proves again what the batch run proves, and costs a lane its time. A batch head is different. Its full checks ran only in CI, after the batch was built, and three misses came from that. Batch 71: the shared-names test (test_shared_names) went red in the full checks job, so the batch was dropped and rebuilt. Batch 72: PR 2550 had a stale guard mutation anchor (job `checks-mutate-guard`), and PR 2551's Retire check ran over 600 s at merge. CI caught the batch 72 misses late. The batch form runs the checks for each of these before ready. A fixture that copies a changed file is caught by the batch run, and the fixtures now copy what git tracks, so a new shared module no longer breaks them.
