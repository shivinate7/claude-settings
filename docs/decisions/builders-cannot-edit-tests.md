# Builders cannot edit tests

## The ruling

A builder that cannot pass a test must not delete, skip or rewrite it. A green run must mean the code is right. The guard stops mistakes, not an attacker (`guard-guards-mistakes-only`). The reviewer reads every diff.

Judge the result, not the commands. The act is a test path in a change the builder made (`predicate-is-the-act`), not `rm`, `mv`, `sed -i` or a redirect. `hooks/guard.py` reads that change at three points. A fourth point reads a builder's shell command, as an early warning:

- A builder's `git commit` and `git push` (PreToolUse, Bash and PowerShell). A test change refuses with `builder-diff`. The refusal names no path and gives the undo route: restore a changed test file, delete a new one. No override lifts it.
- A builder's SubagentStop. A test change refuses the first stop with `builder-diff`. A second stop (`stop_hook_active`) is allowed and logs `role-diff-unresolved`, so an agent that cannot fix its tree never loops.
- A write tool call (Edit, Write, MultiEdit, NotebookEdit). This is the early warning, by path. It refuses. Every path field the call carries is judged, and every refusal runs on all fields before any ask, so a decoy field cannot hide a refused path.
- A builder's Bash or PowerShell call that writes a test path. It refuses with `builder-test-edit`, the same reason as the write tool. The shell check below says what it reads.

An unreadable state logs `role-diff-unread` and is allowed. A second stop with an unreadable state logs `role-diff-unresolved`.

## What the builder wrote

`own_changes` in `hooks/guard.py` reads the HEAD reflog, and judges only what the builder made:

- **Refused.** Each commit the builder made (`commit`, `commit (amend)`, `commit (merge)`) that HEAD still holds, against its first parent. A merge commit is measured against git's own merge of its parents (`git merge-tree`), so only what the builder resolved or added counts. A test path that both sides changed and the builder resolved is refused, whichever side it kept. A write after a finished rebase is refused too, such as main's bytes written back over a test file the rebase replayed (coordinator, 2026-11-01 23:10 CST). Also the working tree and its untracked files against HEAD. While a merge is in progress, they are measured against git's own merge of HEAD and MERGE_HEAD.
- **Logged only.** A replay the builder resolved or chose: a hand-resolved cherry-pick, a revert, a rebase squash, fixup or continue. The working tree while a replay is in progress (a cherry-pick, revert, squash or rebase). A path that a rebase replayed and that holds the upstream side again, as the builder left it during the rebase (a conflict it resolved to the upstream side).
- **Not read.** A plain cherry-pick, rebase pick or `am`, a clean merge, a reset, a checkout and a pull. Each brings other people's commits.

**Known gap.** A squash merge or a `cherry-pick -n`, once committed, is a plain own commit: git removes its marker at the commit. Its test change is refused at push and stop.

**Cost.** Git reads only, plus the objects `merge-tree` writes. No timer and no long-lived process. Each commit, push and stop costs one reflog read, three rev-parse calls, one diff and one untracked list. Commits of the builder's own add one rev-list, and one parent read and one diff each. A merge commit or a merge in progress adds one `merge-tree`. `rev-parse` runs on each refused test-author product write, and `merge-tree` runs once per such write while MERGE_HEAD exists. Each rebase in the reflog adds one ancestry check, and two diffs while HEAD holds it. A log line is written only for an offence, a logged change or an unread state. `merge-tree --write-tree` needs git 2.38 or newer: older git reads a merge as unread.

**Measure.** `GUARD_FAMILY=builder-refuse hooks/test_guard.py`: 128 of 128 `builder-refuse` cases pass on this tip.

## Roles

The payload must carry an `agent_id`. The main session, reviewers, Explore, and a session started with `--agent builder` (no `agent_id`) stay allowed.

- `builder`: refused at commit, push and stop when the diff holds a test path. The write tool and the shell check refuse it too. A test conflict mid-merge is refused. The route is `git merge --abort`, then report to the orchestrator, who hands the whole merge to a test-author.
- `test-author`: the inverse. Logged when the diff holds anything but a test path, test config, a dev dependency list or a whole workflow test step (`author-diff`). Never refused at commit, push or stop.
  - Merge route (owner, 2026-11-08 10:05 CST, waiting-page item 420, pick a, roadmap commit a0ca78420): a test-author owns a whole merge that conflicts in a test file and a product file. The route needs a test path or a mutation test (`AUTHOR_MUTATION_TESTS`) conflicted in the same merge, and covers conflicted product paths only. The mutation-test case rests on item 447 a (owner, 2026-11-08 17:19 CST: the three mutation tests are test content only a test-author edits), which makes the route follow that ruling. While MERGE_HEAD exists, the write tool allows a product path that `git merge-tree` of HEAD and MERGE_HEAD left conflicted. A path that merged clean, or is not in the merge, stays refused (`test-author-scope`). A conflicted workflow, test config or manifest keeps its content check. In its own merge commit, and in the working tree during the merge, such a product path is no `author-diff` offence. A merge that conflicts in no test path and no mutation test is judged as on main. Reason: a builder that keeps one side of a test conflict whole drops the other side's tests. This ruling refuses that, whichever side it kept. So no other role could commit the merge. This route is a named exception to the ruling "a repo changes to fit a shared tool, never the tool to fit a repo" (owner, item 420 a).
- `record-writer`: may change only `*.md` files: records, README, CLAUDE.md-style docs, agent files, skills and output styles. It never changes product code, tests, CI or config. The write tool refuses any other path (`record-writer-scope`). At commit, push and stop, a diff that holds one is logged only (`writer-diff`).
  - Reason: a role name is only a label on the spawn. With no path limit, a Haiku `record-writer` is a Haiku builder under a new name, and the floor means nothing (`agent-model-cap`).
- `designer`: at commit, push and stop, an offence is logged only (`designer-diff`).
- Each write refusal names no path. It says to report the needed change, and the orchestrator assigns it to another role (`git-remedy-never-names-target`).
- The orchestrator gives a test to a test-author, before or after the build. The builder reports the test change it needs and never writes it (`agents/builder.md`).
- A refusal is final: an agent never writes a refused path another way. The write tool refuses by path. At commit, push and stop, a builder's test change is judged on the builder's own change, so a test file written by shell is refused there too. Other refused paths rest on prose only (owner), in `agents/builder.md` and `agents/test-author.md`. A test-author's shell write of such a path is logged only (`author-diff`), in debt `refusal-route-around-guard` (no guard refuses a test-author that routes around a refusal).

**Test paths and test config.** The guard's own suites (`hooks/test_guard.py`, `lint/test_*.py`) are test paths. A test-author changes them. The three mutation tests (`hooks/mutate_guard.py`, `hooks/mutate_shared.py`, `janitor/mutate_sweep.py`) are test content too: a builder never changes them, a test-author does (owner ruling, 2026-11-08 17:19 CST, waiting-page item 447 a).

- A builder change to a test-runner config file that ADDS a line disabling tests counts as a test change.
- A test-author owns test config files and `requirements-dev.txt`. Two files are partly owned: `package.json` (only `devDependencies`, `jest` and the test scripts) and `pyproject.toml` (only the `[tool.pytest*]` sections).
- A builder may add a dependency or a dev dependency.
- A test-author owns a CI step that only runs a test suite. In `.github/workflows/*.yml` or `*.yaml`, it may add or remove a whole test-run step. The step holds only the keys `name`, `if`, `run`, `shell`, `working-directory` and `timeout-minutes`. Its one `run:` is a single line: an optional interpreter (`python`, `python3`, `node`, `bash`, `sh` or `pwsh`), a test path, and arguments that disable no test. No shell operators, `$(` or backtick. The write tool refuses any other workflow change by a test-author (`test-author-scope`), and commit, push and stop log it (`author-diff`). `workflow_test_steps_only` in `hooks/guard.py` judges it, reading `workflow_changed_lines`.
- A builder keeps every other workflow edit, and may add a test step or move one. Its change counts as a test change (`builder-test-edit`) when it does one of three things. It adds a test-disabling flag or name on a line that names a test runner or runs a test path. It adds `continue-on-error: true` or `if: false` under a test-run step. It drops a test path that the workflow ran before. `workflow_builder_refused` in `hooks/guard.py` judges it, through `workflow_disables_tests`, `workflow_disables_step` and `workflow_drops_tests`; the first reads `workflow_changed_lines`. The builder is not refused for the whole file, because CI work (lint and build steps) is a builder's.

**False alarms pinned** (`guard-that-cries-wolf-is-spent`). A builder may still do these:

- Rename or delete product files, and add a dependency or a script to a manifest.
- Read tests, and keep test changes that the branch inherited or that main brought in a merge. Keeping them needs no edit. A merge conflict in a test file is not the builder's to resolve: resolving it chooses what the test checks, so the orchestrator hands the whole merge, product conflicts too, to a test-author (the merge route under Roles). The refusal names the test-author route in one sentence, and the next says a merge conflict in a test file takes the same route.
- Use a name that only looks like a test, such as `src/contest.py`.
- Write a file in no repository, such as a probe in the session scratchpad, from a call that runs in a repository. A path with no enclosing checkout is no test of the repo. A test path in any repository stays refused, also one in a different repository. A call that runs in no repository still judges the path by its shape.
- Write a document in a `spec` folder, such as `docs/spec/api.md`. `spec` is a test folder for code and fixtures only. A `.md`, `.mdx`, `.markdown`, `.txt`, `.rst` or `.adoc` file there is a document. `spec/foo_spec.rb` and `src/x.spec.ts` stay refused.

## The shell check

The shell check does not replace the act. The act stays a test path in the builder's change. The shell check flags common mistake forms first. The diff log at commit, push and stop catches every other form. Recovery stays allowed: `git checkout -- <test>` and `git restore` are not read as writes.

- Reads: a redirect, `tee`, `sed -i` or `cp` onto a test path (`_shell_write_hit` in `hooks/guard_frozen.py`, with `command_position`). It also reads a python or node heredoc body, or a `-c` or `-e` script, that opens a test path for write (`interpreter_write_hit`, same module). Only this check also reads a script file that a python or node command runs by name (`interpreter_write_hit` with `script_files=True`). The other-checkout rule does not, and it spawns no more than before. The file is read from disk (first 256 KB). A python file longer than that is judged by the longest run of whole lines from its start that parses. The scan tries at most `_PY_PREFIX_TRIES` parses. When none parses, it is no hit. The string-literal fallback for an unparsable body is never used on a cut file. Each heredoc of the same command that writes it before the run is read too, an append (`>>`, `tee -a`) or a second body included: each body is judged as a heredoc body is. `__file__` (python) and `__dirname` / `__filename` (node) are the script's own path and folder, so `dirname(__file__)/../tests/x` is a test path. A temp folder is no repo path: python's `mkdtemp` and the like, and node's `os.tmpdir()`, or `fs.mkdtempSync` given a prefix under it, held in a name or as the first piece of `path.join`. Nothing under it is judged. A node `path.join` whose first piece the scan cannot tell is not judged; `process.cwd()` is the cwd, so a join from it is. A folder, a missing or an unreadable file is no hit. Both use the Edit path's predicate (`builder_test_path`, in `hooks/guard.py`). The shell reading also follows a path that a command feeds to a writer (`read_fed`, `_fed_command`). It reads these feeds: the roots of `find` piped to `xargs` (appended, or replacing the `-I` string). It reads `{}` in `find -exec` and `-execdir`. It reads the list of a `for` loop in place of `$v`, `"$v"` and `${v}` in its body. It reads a `$( )` or backtick substitution as the roots of its inner command. A root is a `find` word before its first `-`, `(` or `!`, a grep or rg word after the pattern, or a non-flag word of any other command. A `-name` or `-path` value is never a root. A `while read` loop and `find -delete` are not read. Only `builder_shell_test_hit` asks for `read_fed`; rule 7c (`builder-test-edit`) and the never-lifted check (`never_lifted`) both call it. A pipe at a line's end feeds the next line. A pipeline that ends in a count (`wc`, or `grep -c` with no root of its own) feeds no roots. It only adds refusals to main's reading, except that a `cp` source that is a whole substitution (`$( )` or backticks, quoted or not) is a read. A substitution anywhere else in a `cp` keeps main's reading: in the destination, after or glued to `-t` or `--target-directory`, or glued to other text, as in `tests/$(...)` or `/tmp/$(basename tests/a.py)`.
- A sed script is not a file, except the words it writes or runs: its `w` and `W` file, its `e` command, and the `w` flag of `s`, on every `sed` and `gsed`, with or without `-i` (see below). So `x=$(cat tests/a.py); sed -i "s/N/$x/" src/app.py` is allowed. A variable used as the target (`sed -i s/a/b/ $f`) still counts.
- The shell check also refuses these forms, which main allows. `sed` and `gsed` (GNU sed on macOS): `--in-place`, and `-i` in a cluster of short flags (`sed -Ei`, `-ni`); a flag is read as a word, so `--in-place` inside a quoted pattern (`sed -n "/--in-place/p" tests/a.py`) is text. A test named by a sed script's `w` or `W` command, or by the `w` flag of `s`, is refused, with or without `-i` (`sed -i 'w tests/a.py' src/app.py`, `sed -n 'w tests/a.py' src/x.py`). The file it names counts as written (`_sed_script_targets`). A sed `e` command is judged as a shell command. When each command in it is a printer (`echo`, `printf`, `cat`, `grep`, `wc`, `jq`), its words are read: `sed -n 'e cat tests/x' src/x.py` is allowed. Its redirects still count. Otherwise every word of it counts as written, with or without `-i`: `sed -i 'e touch tests/x' src/app.py` is refused. Every other script word stays text. The git-feed rule: `git ls-files` and `git grep -l` fed to a writer (`git ls-files | xargs sed -i s/a/b/`) read their pathspecs as roots, and a call with none reads as a `.` root, below. A redirect and its target (`2>/dev/null`, `&>x`, `>x`, `2>&1`) are not pathspecs, and nor is the value of `-x` or `--exclude`. A pathspec that is a glob (`'*.py'`, or any word after `--` that holds `*`, `?` or `[`) is refused when a test path under the folder matches it. It is read from disk, as a `.` root is. A leading `./` is dropped. A folder pathspec reads as `<folder>/*`, so `git ls-files hooks` is refused when `hooks` holds a test; one with no test under it stays allowed (`src`, `'src/*.py'`). A git exclusion (`:!`, `:^`, `:(exclude)`) with a plain path drops that path from the walk: the path, the paths under it, or the paths a glob matches (`_excluded_pathspec`). The exclusions count only when every pathspec of the listing is one. `git ls-files ':!tests' ':!test_top.py' | xargs sed -i ...` is allowed when no test is left. With an include too, the exclusions are ignored: `git ls-files '*.py' ':!tests'` is refused while a `*.py` file under `tests/` is a test. Any other pathspec that starts with `:` or holds a backslash reads as the whole `.` root, so it is refused when the checkout holds any test (`_git_listing_roots`, `_pathspec_roots`, `_glob_root`). A shell glob file word of `sed -i`, `perl -pi`, `tee` or a `cp` destination expands from disk through the same reader (`sed -i s/a/b/ hooks/*.py`, `tee hooks/*.py`, `cp src/x.py hooks/*.py`). It keeps `*` inside one path segment, as the shell does. It is refused when a test matches (`_shell_glob_test`). A brace list is expanded first (`hooks/{test_a,guard}.py`, up to 256 words; a `{1..3}` sequence is not). A quote that wraps only literal text is removed (`"hooks"/*.py`); a quoted glob character is text. A word with `$`, a backtick, a backslash or a leading `-`, `~` or `:` is not expanded. A `for` list item is read the same way, so `for f in hooks/*.py; do sed -i s/a/b/ "$f"; done` is refused. A folder root other than `.` that a writer is fed from is read from disk as a `.` root is (`grep -rl old hooks`, `find hooks`, `git -C hooks ls-files`). It is refused when the folder holds a test. A brace list of folder roots is expanded first, with the same expander (`grep -rl old {docs,hooks}`, `_brace_words`). The folder must be a plain path inside the checkout: a relative one, an absolute one, or a `..` one after a `cd` that resolves inside it (`cd docs && grep -rl old ../hooks`). A root outside the checkout, and a word with `$`, `~` or a glob, are not read (`_folder_root`, `_dot_roots`; debt note `pwd-home-folder-roots`). A `find -name GLOB` or `grep --include=GLOB` filter limits the walk to files whose name matches it, so `find hooks -name 'guard*.py'` names no test. A `find -not -name GLOB` or `find ! -name GLOB` filter, and a `grep --exclude=GLOB` filter, leaves out the files whose name matches GLOB, so the walk names no test that GLOB matches. `-not -path` and `! -path` (`find`) drop the files whose path as `find` prints it matches: `./tests/*` for `find .`. A `find -maxdepth N` drops a file under N or more folders of the walked folder, so `find . -maxdepth 1` names only the files directly in it. N is read only as a whole number, the largest wins when it is given twice, and `-mindepth` is ignored, so it never narrows the walk. A `find` with `-o` or a group reads no filter. Nor does one with a `-not` or `!` that is not followed by `-name` or `-path`. A filter value with `$`, a backtick, `{` or `\` reads no filter either (`_name_filters`). `**` reads as one `*` (debt note `globstar-double-star`). `perl -pi`, `perl -i` and `-i` at the end of any cluster of perl flags that take no value (`-0777pi.bak`). A mark glued to other text in a fed command (`xargs -I{} cp {} {}.bak`, `find tests -exec cp {} {}.bak \;`): it is read twice, as `ROOT.bak` for a root that is a file, and as `ROOT/x.bak` for a root that is a folder. A `.` or `./` root reads the tree from disk, top down, in the folder the segment runs in. So does a `git ls-files` or `git grep -l` with no pathspec of its own (`grep -rl old . | xargs sed -i s/a/b/`, `find . -name 'test_*.py' | xargs sed -i s/a/b/`, `find . -exec sed -i s/a/b/ {} +`). If that tree holds a test, the root is put as the first test path found. A `.` root that holds no test stays allowed, and so does one fed to a reader. The walk skips hidden folders, `node_modules`, `venv` and `__pycache__`, and stops after 20000 files; a tree that large with no test found early reads as holding none. A glob is tested against each name before the test predicate runs.

- Cost: no process, no file written, no timer. A builder's shell call that runs python or node by a file name reads that file once, at most 256 KB. A python file over that size is parsed at most `_PY_PREFIX_TRIES` times. Any `sed`, `perl`, `tee` or `cp` segment with a glob word walks the tree for that word, read-only ones included. A `.` root, a folder root, or a folder or glob pathspec walks the tree under its folder once per word, to its first matching test or 20000 files. A walk costs 20 to 40 µs per matching file, because the test predicate runs on each match. A narrow glob takes 0.15 to 1.9 ms; a broad one such as `*.md` takes about 4.5 to 4.8 ms, and a folder root with no test, `docs`, took 12 ms. A `find` root walks even when no writer follows it (`find docs -name '*.md'` took about 10.7 ms, against 0.19 ms on main), and so does a fed `grep` over `docs` (about 11.1 ms). A 20000-file tree takes 0.8 s per word. A word with no glob and no folder pathspec reads nothing. Nested `for` loops multiply words: 4 loops of 12 items take about 2 s (debt note `fed-loop-word-cost`). The scan runs inside the guard hook that already runs for a builder's shell call. `ast` is imported only when a python body is read. A refusal writes its one guard.log line, as every refusal does. A scan error in the python or node reader is no hit. Any other scan error ends the judge: the guard logs `guard-crash` and allows the call.
