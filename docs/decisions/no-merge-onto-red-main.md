The red-main check: the merge tool refuses `merge <pr> --confirm` while the base branch's latest completed run has a red job. The preview prints the same verdict on its `<base> run:` line.

- Judged: per workflow file and per event group, on the base branch. The groups are in one file, `actions/ci-alarm/events.json`, which the CI alarm reads too. Its keys are the judged events. Its values are the groups. `push` and `workflow_dispatch` (`gh workflow run`, the tool's own remedy) form one group. `schedule` is its own group. For each file and group, the newest completed run decides, except an empty run (the next bullet). So a green push or dispatch run that ran a check clears an older red push or dispatch run. A newer schedule run clears an older red schedule run. A newer first run still in progress waits its turn. A re-run in flight is not: GitHub keeps the run id and sets `run_attempt` above 1, and the run under it may be red. So when the newest run of a file and group is a re-run not yet completed, that group is UNKNOWN, never green. The refusal says to wait for the re-run to finish, then run again. A run of any other event, such as a Pages build, is not judged. Runs are keyed by workflow file, not by name, so a rename inside the file keeps one verdict. A run whose workflow file is gone from the base is not judged, because no new run will ever replace it. One page of 50 runs is read. A group with no run on that page is not judged.
  - An empty run with no evidence is no verdict. A completed `success` run of the push group (push or dispatch) is empty when no job of it concluded `success` except the bookkeeping jobs `scope`, `push-skip` and `nightly-skip`. A push can run no check: `push-skip` skips the whole run. `ci-scope.sh` sets every scope flag on for any event but a pull request. So no push run has every flag off today, and the no-evidence branch is defence in depth. An empty run with no evidence says nothing about an older red run. An empty run counts as a verdict only with evidence: its `push-skip` job is `success` and its `scope` job is `skipped`. That is the path where `push-skip.py` found the push tree equal to a `batch-*` pull request head whose `all-jobs-passed` passed. Only a push run can carry it; a dispatch runs no `push-skip` job. An empty run with no evidence is skipped, and the group's newest run that is not empty decides, so an older red run stays red. A group with no such run on the page keeps its newest run. A schedule run is judged as it is. The one home of the test is `actions/ci-alarm/clear_rule.py` (`empty_without_evidence`), which the CI alarm calls too. A failed jobs read of a candidate is UNKNOWN. Ruling: owner, 2026-11-12 21:44 CST, relayed by the coordinator at 21:46 CST.
  - A failed run R with at least one red job is cleared by a run N of another group of the same workflow file. All of these must hold:
    - N is newer than R.
    - N is the verdict run of its own group: its newest completed run, or when that run is empty with no evidence, the newest run that is not.
    - N's conclusion is `success`.
    - Every job name in R that may run in N appears in N, compared exactly, with conclusion `success`. A skipped job in N is not a pass. A job of R that is not red in R may be left out. It is left out when its job-level `if:` has a top-level `&&` conjunct `github.event_name == 'X'`, X not N's event, so it cannot run in N. The one home of this rule is `actions/ci-alarm/clear_rule.py`, which the CI alarm calls too. So a newer green push run that ran those jobs clears a red nightly, because `all-jobs-passed` and `ci-done` are pull_request-only. An empty push run clears nothing. A red job is never left out. A test inside `||`, a `!=`, an `if:` that cannot be parsed, or a job name that maps to no job keeps the job needed. A name that maps to two jobs maps to none. The file is read at N's head, one read per candidate N, and only when N passed every red job of R. A red job that N lacks or did not pass is red with no read. A failed read is UNKNOWN. Ruling: owner, 2026-11-04 15:21 and 15:27 CST, in chat to the coordinator.
  - Otherwise the groups stay separate. A green run of one group never hides a failed run of another. Reason (roadmap step `ci-alarm-reads-by-event`): two events can run different job sets, so a green nightly must not clear a red push whose jobs it did not run.
  - A cancelled R with no red job is cleared by such an N too, when R's commit is older than main's head. That reads as: N's `head_sha` differs from R's. Runs on main start at its head, and N is newer, so R's commit is no longer the head. No extra read is made. Here each job R ran (conclusion not `skipped`) must be in N, compared exactly, with conclusion `success`. Each job R skipped must be in N by exact name, with any conclusion. A cancelled R with no jobs stays UNKNOWN. A cancelled R on main's head stays UNKNOWN, unless a re-run of it passes.
  - No other run is cleared across groups. A run that ended `failure` with no red job stays red, as the "did not succeed" bullet below says: no jobs (`startup_failure`), jobs that all passed, or only cancelled or skipped jobs. A cancelled N, or one in progress, clears nothing.
  - The CI alarm (`actions/ci-alarm/alarm.sh`) follows the same rule for a red run, so a failure run the merge tool calls clear is not red. Its cap end still alarms, as a cap-only alarm (owner, page item 549 a, 12:07 CST Nov 12). A cleared run with no cap end stays quiet. A cap end in a cancelled run alarms even when the merge tool calls that run clear: the alarm's cancelled loop applies no clear, and `base_state` does (owner, 2026-11-11 11:53 CST). A job cancelled at its own job-level `timeout-minutes` (a cap end) wakes in every run it sits in, and a failure run that is not cleared is red by its conclusion. Every cap end on main lands as a wake on the merged pull request that holds the run's commit. It opens no issue and appears in no issue (owner R53, 13:07 CST Nov 12; coordinator pick, 13:12 CST Nov 12; owner, page items 549 a and 588: every cap end alarms). The alarm calls `actions/ci-alarm/wake.sh` once per run attempt with a cap end: SHA is the run's head commit and KEY is `cap:<run id>:<attempt>`. The wake text names every cap job of that attempt. The repeat memory is the hidden marker `<!-- main-alarm:KEY -->` in the wake's comment. A cap end already reported is not reported again (coordinator ruling, 12:58 CST Nov 12), while a cap end in a later attempt of the same run still wakes. A run whose commit has no pull request merged into main cannot be woken. Once every attempt was handled, the alarm step prints its verdict. It then exits non-zero and names the run id and attempt (debt note `cap-wake-needs-pr`). The alarm judges every cancelled run and every failed run in the 100-run window, not only the newest of a group (coordinator pick, 12:26 CST Nov 12). It reads each earlier attempt of a cancelled, failed or succeeded re-run too. The job ran at least the cap. The cap is read from the workflow file at the run's head. A job with no job-level cap has GitHub's default, 360 minutes. The wake text names each cap job, its cap, the minutes and the run id. The step prints `alarm` when only a cap end is named, and `red` when a failure run that is not cleared is named. The wake text opens with "CI job hit its time cap on <branch>: <job>", naming the first cap job of that attempt, and then names the rest. A red run still opens its issue, titled "CI red on <branch>", through `actions/ci-alarm/issue.sh`. The issue body names the red runs and holds no cap-end line, and a cap end beside a red run still wakes. A job cancelled under its cap stays quiet. An unreadable cap, a null `started_at`, or a cancelled run or an earlier attempt of it with no jobs is unknown, never red and never clear. A group whose newest run is a re-run in flight (attempt above 1) is unknown too. It raises no alarm unless a cap end or a red run is named elsewhere. Roadmap step `main-job-cap-alarm` holds the build.
- Red: a job whose conclusion is `failure`, or any value GitHub adds later (`Host.classify`). A job cancelled at its cap (timed out), a cancelled job and a skipped job are not red. The merge gate leaves a run with no red job and at least one job timed out at its cap out of red and out of unknown (`base_state`). The CI alarm wakes the pull request of the run for such a job, in a cancelled run, a succeeded re-run, or a failure run, cleared or not. A failure run that is not cleared is red by its conclusion.
- A run that did not succeed and has no red job: a timed-out job explains it, so it is not red. A cancelled run is UNKNOWN, unless the cross-group clear above clears it. The refusal, the unknown detail and the preview line name the run. They name its own re-run, `gh run rerun <id>`, only when its `head_sha` is the head_sha of the newest run on the page read (any status, any judged event). Runs on the base start at its head, and a re-run tests the run's own commit. A cancelled run on an older commit keeps its line with no remedy. A red verdict names a cancelled run beside it the same way. A run with a red job and a re-run in flight get no remedy. It is never swapped for an older run: on the base, `judge_runs`'s twin rule would reach across commits. Any other conclusion is red, such as `startup_failure` from a broken workflow file that runs no job. The tool sees a failed run and no reason for it, so it treats the run as red.
- The refusal names each red job, the run id, its head and its URL.
- Unknown: a read of the workflow files, the runs or the jobs that fails is UNKNOWN, never green or red. Unknown refuses, as the silent-undo check does.
