# No batch merges onto a red main

## The ruling

The red-main check: the merge tool refuses `merge <pr> --confirm` while the base branch's latest completed run has a red job. The preview prints the same verdict on its `<base> run:` line.

- Judged: per workflow file and per event group, on the base branch. The groups are in one file, `actions/ci-alarm/events.json`, which the CI alarm reads too. Its keys are the judged events. Its values are the groups. `push` and `workflow_dispatch` (`gh workflow run`, the tool's own remedy) form one group. `schedule` is its own group, because a nightly and a push can run different job sets. For each file and group, the newest completed run decides. So a green push or dispatch run clears an older red push or dispatch run, and a newer schedule run clears a red schedule run. A run of any other event, such as a Pages build, is not judged. Runs are keyed by workflow file, not by name, so a rename inside the file keeps one verdict. A run whose workflow file is gone from the base is not judged, because no new run will ever replace it. One page of 50 runs is read. A group with no run on that page is not judged.
- Cleared across groups: a red run is also cleared by the newest completed run of another group of the same file. That run must be newer and must have run every job the red run ran, each with conclusion `success`. A name listed twice passes only when every listing is `success`. The red run's jobs are those not skipped. A red run with no such job is never cleared. Names match exactly, so `checks` never stands for `checks-macos`. The newer run may run more jobs. So a green dispatch with the same jobs clears a stale red schedule run, and a green nightly that skipped a push-only job never clears a red push run. A newer run that is cancelled, red or still in progress clears nothing. One home picks the candidate run and judges the job sets, `candidate()` and `clears()` in `actions/ci-alarm/clears.py`, which the merge tool and the CI alarm both call.
- Red: a job whose conclusion is `failure`, or any value GitHub adds later (`Host.classify`). A job cancelled at its cap (timed out), a cancelled job and a skipped job are not red.
- A run that did not succeed and has no red job: a timed-out job explains it, so it is not red. A cancelled run is UNKNOWN. It is never swapped for an older run: on the base, `judge_runs`'s twin rule would reach across commits. Any other conclusion is red, such as `startup_failure` from a broken workflow file that runs no job. The tool sees a failed run and no reason for it, so it treats the run as red.
- The refusal names each red job, the run id, its head and its URL.
- Unknown: a read of the workflow files, the runs or the jobs that fails is UNKNOWN, never green or red. Unknown refuses, as the silent-undo check does.
- The way out is `--base-red-ok "<reason>"`. It is a reason flag, like `--undo-check-unknown-ok`, not the owner's `override`. Claude can type it with no owner present. Use it for the batch that carries the fix, or when the owner accepts an unknown read. The tool prints the verdict and `--base-red-ok, reason: <reason>`. A blank reason lifts nothing.

Why: Oct 13 to 14, 14 main runs in a row were red, and batch merges kept landing on top. Main's latest run was not green for 311 of 366 hours. Each merge onto a red main hides the next defect and makes the repair lane longer (roadmap step c166, from plan c95-step2-escapes, option C's brake).

Why the cross-group clear: on 2026-11-02 at 00:01 CST the check refused a joyous merge on schedule run 40323547948, from Oct 26 on old main, with job readme-links red. Dispatch run 41397308885 of the same workflow file on current main ran the same jobs and passed. With groups kept apart, that stale red blocked every joyous merge until the next nightly run.

- Risk: named incident, the Oct 13 to 14 red episode. Landed 2026-10-28. The cross-group clear: named incident, the joyous stale schedule red of 2026-11-02. Landed 2026-11-02.
- The owner's `override` prompt does not reach this check. The override check has one home, `refuse()` in `hooks/guard_core.py`. The merge tool runs after the guard, and decision owner-override lists the `bin/merge` shim as outside every override. The tool also cannot tell a session's run from its agent's, and a one-act override must not reach an agent.
- Check: `merge/test_merge.py`, class `RedMainBrake` and `GhHalf.test_a_red_main_run_read_through_gh_refuses_the_merge`. The CI alarm's groups and cross-group clear: `actions/ci-alarm/test_action.sh`.
- Cost: at each `--confirm` and each preview, the merge tool makes one `git ls-tree` of the base and one `actions/runs` read (one page of 50). It adds one jobs read for each judged run that did not succeed. It adds one more for each newer run of another group that could clear it. The CI alarm adds one `gh api --paginate` jobs read (every page) for each red run that has a candidate and for each candidate. It also adds one short `python3 clears.py` process for each such red run and each candidate, inside its scheduled job. Its files go in one temp folder that it removes at the end. The merge tool starts no process, writes no file and keeps no timer.
