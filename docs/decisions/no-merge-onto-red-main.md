The red-main check: the merge tool refuses `merge <pr> --confirm` while the base branch's latest completed run has a red job. The preview prints the same verdict on its `<base> run:` line.

- Judged: per workflow file and per event group, on the base branch. The groups are in one file, `actions/ci-alarm/events.json`, which the CI alarm reads too. Its keys are the judged events. Its values are the groups. `push` and `workflow_dispatch` (`gh workflow run`, the tool's own remedy) form one group. `schedule` is its own group. For each file and group, the newest completed run decides. So a green push or dispatch run clears an older red push or dispatch run, and a newer schedule run clears an older red schedule run. A newer first run still in progress waits its turn. A re-run in flight is not: GitHub keeps the run id and sets `run_attempt` above 1, and the run under it may be red. So when the newest run of a file and group is a re-run not yet completed, that group is UNKNOWN, never green. The refusal says to wait for the re-run to finish, then run again. A run of any other event, such as a Pages build, is not judged. Runs are keyed by workflow file, not by name, so a rename inside the file keeps one verdict. A run whose workflow file is gone from the base is not judged, because no new run will ever replace it. One page of 50 runs is read. A group with no run on that page is not judged.
  - A failed run R with at least one red job is cleared by a run N of another group of the same workflow file. All of these must hold:
    - N is newer than R.
    - N is the newest completed run of its own group.
    - N's conclusion is `success`.
    - Every job name in R that may run in N appears in N, compared exactly, with conclusion `success`. A skipped job in N is not a pass. A job of R that is not red in R may be left out. It is left out when its job-level `if:` has a top-level `&&` conjunct `github.event_name == 'X'`, X not N's event, so it cannot run in N. The one home of this rule is `actions/ci-alarm/clear_rule.py`, which the CI alarm calls too. So a newer green push run clears a red nightly: `all-jobs-passed` and `ci-done` are pull_request-only. A red job is never left out. A test inside `||`, a `!=`, an `if:` that cannot be parsed, or a job name that maps to no job keeps the job needed. A name that maps to two jobs maps to none. The file is read at N's head, one read per candidate N, and only when N passed every red job of R. A red job that N lacks or did not pass is red with no read. A failed read is UNKNOWN. Ruling: owner, 2026-11-04 15:21 and 15:27 CST, in chat to the coordinator.
  - Otherwise the groups stay separate. A green run of one group never hides a failed run of another. Reason (roadmap step `ci-alarm-reads-by-event`): two events can run different job sets, so a green nightly must not clear a red push whose jobs it did not run.
  - A cancelled R with no red job is cleared by such an N too, when R's commit is older than main's head. That reads as: N's `head_sha` differs from R's. Runs on main start at its head, and N is newer, so R's commit is no longer the head. No extra read is made. Here each job R ran (conclusion not `skipped`) must be in N, compared exactly, with conclusion `success`. Each job R skipped must be in N by exact name, with any conclusion. A cancelled R with no jobs stays UNKNOWN. A cancelled R on main's head stays UNKNOWN, unless a re-run of it passes.
  - No other run is cleared across groups. A run that ended `failure` with no red job stays red, as the "did not succeed" bullet below says: no jobs (`startup_failure`), jobs that all passed, or only cancelled or skipped jobs. A cancelled N, or one in progress, clears nothing.
  - The CI alarm (`actions/ci-alarm/alarm.sh`) follows the same rule for a red run, so it opens no issue for a run the merge tool calls clear. It never alarms on a cancelled run.
- A push run that succeeded with every job but `scope` skipped ran no suites (judged from job conclusions). It reads green only when a green pull-request run of the same workflow file and tree (`head_commit.tree_id`) is among the newest 100 successful pull-request runs. Otherwise the newest older run of its file and group that ran its suites stands for it, with its own verdict. With none on the page, the read is UNKNOWN, never green. Ruling: coordinator, 2026-11-13 16:06 CST.
- Red: a job whose conclusion is `failure`, or any value GitHub adds later (`Host.classify`). A job cancelled at its cap (timed out), a cancelled job and a skipped job are not red.
- A run that did not succeed and has no red job: a timed-out job explains it, so it is not red. A cancelled run is UNKNOWN, unless the cross-group clear above clears it. The refusal, the unknown detail and the preview line name the run. They name its own re-run, `gh run rerun <id>`, only when its `head_sha` is the head_sha of the newest run on the page read (any status, any judged event). Runs on the base start at its head, and a re-run tests the run's own commit. A cancelled run on an older commit keeps its line with no remedy. A red verdict names a cancelled run beside it the same way. A run with a red job and a re-run in flight get no remedy. It is never swapped for an older run: on the base, `judge_runs`'s twin rule would reach across commits. Any other conclusion is red, such as `startup_failure` from a broken workflow file that runs no job. The tool sees a failed run and no reason for it, so it treats the run as red.
- The refusal names each red job, the run id, its head and its URL.
- Unknown: a read of the workflow files, the runs or the jobs that fails is UNKNOWN, never green or red. Unknown refuses, as the silent-undo check does.
- The way out is `--base-red-ok "<reason>"`. It is a reason flag, like `--undo-check-unknown-ok`, not the owner's `override`. Claude may type it with no owner present (owner ruling, Cockpit item 178 a, 2026-11-03 22:31 CST: "Claude may type both, with a logged reason"). Live now: use it only for the batch that carries the fix, or for an unknown read whose cause the reason names. Rule git-never-merge-failing-ci holds for every other batch. Target, after act 3 of R42 part 2 (pull request 2889) lands: use it for a revert PR of a breaking merge too, and the rule holds for every other PR. The tool prints the verdict and `--base-red-ok, reason: <reason>`, and writes `Reason flag: --base-red-ok: <reason>` to the merge commit message. A blank reason lifts nothing.
