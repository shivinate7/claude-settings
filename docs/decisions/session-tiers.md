- **Who starts which session** (owner, 15:18). The coordinator is the one session that starts other sessions. It starts triage and the batch runner together, as a trio, before any lane. This refines the triage-first ruling below.
  - Before it starts a fix lane for a red CI case, the coordinator runs `merge --touches --run <failed run id>` (or `--case <failing case name>` and `--file <failing file>`, repeatable) and reads each open PR it names. A PR that already touches the case gets the fix, or the coordinator waits on it; no duplicate lane starts. Incident: main run 42559512356 went red at 02:52 CST Nov 9 in two brief-destructive-git cases, and #2390, already open, fixed them; the duplicate lane cost PR #2407 (roadmap step `red-fix-finds-open-pr`). The clear line ("no open pull request touches them") prints only when every read succeeded and nothing is unknown. Otherwise it prints `unknown` and exits 1, never "none". A failed read prints only `unknown`; the other causes list the matches too. These cases are unknown:
    - A read that failed.
    - A `--run` whose failing lines give no case and no file at all. Pass `--case` or `--file`.
    - A `--run` with a failed job whose own log gives no case and no file, an empty log too. The all-jobs-passed rollup job is skipped.
    - A `--run` with a failed job that has a failing line naming no case or file (a unittest summary line apart).
    - A `--run` with a job that is not success, skipped, neutral or failure, such as timed out, cancelled or still running.
    - A patch-less changed file, only while a case is queried and that PR has no match. Its line says `unknown: file PATH has no patch to read`. `--file` alone is fine beside a patch-less file.
  - Limits. A case matches only when its text sits whole in one `+` line; a case a `--run` names also matches a context line. A name built from pieces or with escapes never matches. A `--case` matches a context line only when a `--run` names the same case. `--file` finds a fix elsewhere, in guard or product code or far from the case line. `--run` finds it only when a failing line names its file, or the case name is on a `+` line or in the patch's context lines. `--file` is an exact path after normpath: no rename's previous name, no directory, no backslash path. A failing line whose reason spans lines may keep a partial `  (note` in the case.
  - Cost per call: the open-PR list in pages, one call per 100 PRs (unmeasured). One file read (its pages) per open PR (unmeasured). For `--run`, the jobs read in pages, one call per 100 jobs, and one log read per failed job but the rollup (unmeasured). No file, process or timer.

## How it works

Mechanics that carry out the rulings above. They are not owner rulings.

- **Role tags** (coordinator, 2026-10-28; cloud tags optional, owner, 2026-11-10 14:29 CST, G6). Each session the coordinator starts carries these two tags, beside any others such as `cs-step:<step>`.
  - `cs-build:<tier>`, one of `coordinator`, `triage`, `batch-runner`, `arbiter`, `lane`. The consultant is not a tier here: the owner starts it, so no coordinator sets its tag.
  - `cs-repo:<owner>/<name>`, the repo it builds. It must be the full owner/name, never the short name. A roll-out lane also carries the starting repo's tag, beside its target's. Guard rule `lane-repo-tag` enforces it on a lane `create_session`.
  - `cs-topic:<slug>`, the one topic a lane holds (rule `lane-one-topic`). The coordinator sets it on each lane at `create_session`. Each step the lane takes gets its own `cs-step:<slug>` tag, at `create_session`, or by `set_session_tags` when the step is added.
- **Role proof** (owner, 2026-11-10 14:29 CST, G6: "yes cloud tags can be optional agreed", "local sessions do have sesion id yes"). A session proves its role from one roster that local and cloud both read: the Standing sessions list on the roadmap branch. Cloud tags are optional. Local sessions have a session id, so the split is chosen, not forced. Not built: the live-coordinator check, the session-start line and the merge guards still read the `cs-build` tags.
- **Live-coordinator check.** A session that would act as coordinator reads every page of `list_sessions`. It looks for one session with both tags whose `session_status` is not archived. That session is the active coordinator.
  - The `tags` filter of `list_sessions` errors inside a session, so the check filters the rows itself.
  - `list_sessions` leaves out runs a scheduled task started. The check misses a coordinator started that way.
- **Session start** (lane L3). In a cloud session (`CLAUDE_CODE_REMOTE=true`), or in a session whose `CLAUDE_CODE_REMOTE_SESSION_ID` is set, `hooks/session_start.sh` prints one fixed line, in any working folder, git or not. The line tells the session to read its own record with `get_session`, and gives the check above.
  - The hook cannot read the role itself. `get_session` and `list_sessions` are MCP tools only, and a hook never calls the sessions API with a token.
  - A session with neither value prints no line. A local lane with an own id needs the line, so that the load brake can read its own record (decision `machine-load-brake`, the machine-load brake).
  - Cost: at most two env reads in the hook already running. No network, no new process, no timer, no file written. `hooks/test_session_start.py` proves the line prints once in cloud or with an own id, in a git folder or not, and never with neither.

## Why

- Coordinators share a scarce machine by talking to each other (14:59).
- The batch runner leaves the coordinator with lane state only. The coordinator then talks with the owner (15:11). The coordinator never merges, so it stays focused on being coordinator (owner, 2026-11-01 21:34 CST).
- A wrong-session line saves context in the role that should do the work. It also teaches the owner the setup (15:12).
- No coded overlap guard. A false "done" fails at merge, because the merge tool reads GitHub's head and CI (15:01).
- A lane on one topic does the work it was started for. Unrelated work sent to an idle lane is the failure the owner reported (owner, 2026-11-03 16:36 and 16:40 CST).
- The guard compares two written slugs, the brief's `Topic:` and the `cs-topic` tag. It guesses nothing from prose (rule `lane-one-topic`).
