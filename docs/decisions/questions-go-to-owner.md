# Questions go to the owner

## The ruling

Owner, 2026-10-26: a session with a question brings it to the owner. The question names what the session does meanwhile, or that it waits. The session keeps working on what does not depend on the answer.

- **Take a pick that can be undone** (roadmap step c102, take undoable picks; 2026-10-27). A question whose pick rule `parallelism-keep-going` lets the session take with no question is not asked. The session takes the pick and names it under Done. That rule holds the exceptions: a pick that cannot be undone, a change to the owner's goal, work in another repo, and a wait for the owner's grant that another rule makes. Incident: a mailaudit report asked "link the waiting page now with a folder move, or later"; later changed nothing and could be undone. The Stop reply judge (`hooks/reply_judge.py`) notes such an Input Needed item and never blocks (decision `reply-judge-samples-never-refuses`).
- **A picture in each option** (owner, 2026-10-27 12:10 CDT): "Some of your questions on your artifact need pictures. You should in general put a mockup image inside each option card on the waiting page first. No links to folders." A decision whose options differ in how something looks carries one mockup per option, shown inside that option's card, before it is added. Every option carries one, and the page warns on an option without one (owner, 2026-10-27 23:40 CDT). A tap on the picture opens the viewer (owner, 2026-10-27 12:13 CDT). A link to a folder or another artifact does not count. Skill `waiting-page` ("Add a design") holds the format.
- **Read standing grants first** (owner, 2026-10-27 15:51 CDT; roadmap step c148, port keeps behaviour). Before it asks, a session reads the repo's CLAUDE.md for standing grants. A grant the owner gives in chat lands in the repo's CLAUDE.md or the merge tool's config, never only in a hand-off. Incident: an orchestrator asked the owner to merge in a repo with a standing merge grant. Record `port-keeps-behaviour` holds the rule for a port.
- **No outside advisor.** The terminal advisor (a session named `advisor-` and a short suffix, started from its own config folder on Windows) is retired. No rule, hook or report label sends a question to it.
- **The built-in advisor.** `advisorModel` in `settings.json` stays. It is a second opinion that a session calls on its own work, and it sees only that session's conversation. It answers no question for the owner and decides nothing, so it lifts no guard and grants no override.
- **The waiting page** (owner, 2026-10-26). One page per repo or project holds every item waiting on the owner, from every session (ruling 1a). A save by the owner on that page counts as the owner's grant for the item it answers (ruling 2a). The terminal question box stays (ruling 3a). Under the owner's 2026-10-28 15:10 CDT ruling, the box no longer links the page: the box opens before any item exists. Skill `waiting-page` holds the protocol.
- **Chat first, then the page** (owner, 2026-10-28 15:10 CDT; roadmap step c202, chat first; it corrects his 15:06 note). A session that talks with the owner asks in chat first, his "fast lane" (15:07). Chat is the reply, or the box where rule 3b allows one. If he has not answered in chat after 5 minutes (his number, waiting page item 52), the session sends the question to the page's writer, and the writer adds the item. When he answers in chat, the session still sends the question and the answer to the writer. With no item yet, the writer writes it closed, with the answer and its time in `context`. With an open item, the writer adds the answer and its time to `context`, and the owning session routes and closes it. The owning session then files the answer to its home and writes `receipts/<id>`, as "Route and close" step 1 says. The writer never writes receipts. So every question and answer ends in the page's record. "Never chat only" means that, not that both are posted at once. A lane has no chat with the owner, so it is not changed: its question still goes in its report. No timer counts the 5 minutes, per rule `outcomes-mechanize-rules` (no timer). The session checks the age of its open chat questions at each wake. Gap: a session with no wake after 5 minutes, such as one in an open box with nothing running, sends the question only when the owner answers or it wakes.
- **No box while work runs** (ruling 3b, which narrows 3a). Owner, 2026-10-26, waiting page item 30: questions should not hang, so the session "gets back to orchestrating". Triage read that as this design, on roadmap step c84; the owner asked for the outcome, not this text. While an agent, a lane or a background command of this session runs, or starts in the same response, the session opens no question box. It asks in its reply, keeps orchestrating, and reads the answer at its next turn. Under the owner's 2026-10-28 15:10 CDT ruling, the page gets a question only after 5 minutes in chat. With nothing running, the box stays. Why: a box stops the session until the owner answers, and its running work does not stop. A UI session waited on a box while its agents ran on, filled the disk and crashed. Its brake ran only once the owner answered. A timer that expires the question is out: rule `outcomes-mechanize-rules` (no timer) refuses it, and a hook cannot close a box already on screen. A repo with no page asks in the reply or the box only.
- **A lane never writes the waiting page.** A lane is a background agent or a lane session that ends. It has no wake after it ends, so it cannot read its answer, and two writers clash on the design republish. A lane puts its question in its report. The orchestrator writes the item with itself as `owner`, and routes the answer to the lane or its next try. The spawn judge (`hooks/call_judge.py`) flags a brief that tells a lane to write an item, and passes one that forbids it.
- **Each page has one writer, and the writer ranks.** In a repo the writer is the orchestrating session that owns the page. In a project with a triage thread it is triage. The page names it in `meta/page` as `writer`. Every other session sends its question to the writer, which writes the item. A lane's question goes in its report, and reaches the writer through its orchestrator. `owner` stays the session that asked. The fact tiers stay the base and are never written by hand. Inside a tier the writer sets `rank` (an integer, lower first), judged against every open item on the page. It re-ranks when it adds, updates or closes an item. A close by another session needs no re-rank. The writer re-ranks at its next add or update. The page sorts by `rank`, then by age for items without one. A group sits at its best member's rank.
- **The page runs main's code** (owner, 2026-10-29 14:47 CDT; roadmap step wp-republish-on-template): a live page ran old page code, because its writer kept the live page's code and swapped only the mockups. "ensure u and all my other repos know to do that proactively." The writer checks its page against `skills/waiting-page/page.html` on claude-settings main at each wake, and every republish is main's page with the live `designData` kept. `skills/waiting-page/stale_pages.py --page` is the one check. It runs on demand at a wake, with no timer.
- **Answer on the page, not in a comment thread** (owner, 2026-10-28 02:44 CDT): "you don't reply in just Claude replies for the waiting on you artifact (given that artifacts can be torn down and remade) instead you gotta just revise the questions with whatever your reply adds". A session answers a comment on the waiting page by rewriting the item it is about, never by a thread reply: a rebuilt page drops its threads. The session says in one line in the session what it changed.
- **Owners read their own answers** (owner, 2026-10-26). Each waiting item names its owning session. That session reads, routes and closes the item at each wake. No session relays an answer.
- **The report.** The labels are Done, Deviations, Input Needed, Next. `lint/report_guard.py` refuses any other label.
- **The message check.** The two judges in `hooks/sendmessage_state.py` treat every receiver as a peer.
