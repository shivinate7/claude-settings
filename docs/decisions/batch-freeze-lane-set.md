# A batch's lane set freezes when its build starts

## The ruling

The batch runner freezes a batch's lane set when the build starts.

- A release or a drop that arrives after the build starts goes to the next batch. It never causes a rebuild. The one change after the freeze is the drop of a red run's blamed lane.
- The next batch builds and runs on top of the batch in CI. While its head holds the running batch's head, the merge brake lets the running batch merge (decision `no-merge-during-batch-ci`, the contains rule). A drop changes the running batch's head, so the next batch is built on the new head before that merge.
- A red run drops the one lane that blame names (one search per lane merge commit, pull request 2358), and any lane that depends on it, as step 8 already said. A lane red on form is dropped the same way, with no fix-and-re-merge. CI restarts at once. No lane that stays is linted again. Each lane was linted at hand-off and once at the join, before the build, and the batch head once, before ready.
- The batch is built as a draft. The batch-head lane lint runs, then the integration PR goes ready, with no rebuild between (decision `draft-until-reviewed`). A draft run skips every job, so a draft batch is never rebuilt only to close it.

- A lane's push to its own branch is refused while an open, ready pull request on the default branch holds that branch's remote tip in its head. A moved head breaks the batch's confirm (guard rule `push-batch-held`, step `lane-push-frozen-in-batch`). The tip is the clone's `refs/remotes/origin/<branch>`. The refusal wins over the agent-branch ask. Its remedy is to wait for the batch to merge or drop the lane. New work goes in a new lane. A list or compare that cannot be read allows the push and logs `push-batch-unread`. A forced push, a push that moves nothing and a lane with no remote tip are not judged here.
  - A tip the default branch already holds (merged) is allowed with no GitHub call. Four more forms cannot be read, and each allows the push with one `push-batch-unread` line: a `$NAME` destination or source, a glob destination (no glob matching is built), a destination no read names (push.default=matching, a detached HEAD), and a default-branch read that cannot answer. A push that names no remote goes where git sends it: `branch.<cur>.pushRemote`, else `remote.pushDefault`, else `branch.<cur>.remote`, else origin. A delete part of a push is no move (`HEAD:lane :old` judges `lane`). `--all` judges each local branch whose remote-tracking ref differs.
  - Cost, measured 2026-11-09 on the test fixtures with a stand-in `git` that logs each spawn and a counted fake `gh` (one push each, 1 ready holder or 2 ready pull requests): one non-forced push to a lane that moves a tip starts 7 guard `git` processes (2 `rev-parse` of the tip and source, 3 default-branch reads, 1 `merge-base --is-ancestor`, 1 `rev-parse --is-shallow-repository` when the answer is no). That count holds with `origin/HEAD` set. With it unset the defaults read as main and master, and the same push starts 8 processes. With 2 ready pull requests and no hold, 3 `gh` calls (the open list, then one compare each). A merged tip stops after the `merge-base` and makes no `gh` call. `--all` adds one `git for-each-ref`, and re-reads the default-branch reads for each moved branch. Each `gh` call also starts its own `git remote -v` and `git config` (2 more processes per call, counted by the Round 1 reviewer on a push with many ready pull requests: 9 `gh` calls, 18 processes; the fake `gh` here cannot show them). One 25 s deadline (`MERGE_READ_TIMEOUT`) bounds all `gh` reads of a push: past it the push is allowed and logs `push-batch-unread`. A push with no remote argument reads that remote from one `git config --get-regexp`. The push-stray-branch check reuses it in the same hook process. The current branch comes from the bare-destination read already made. A bare push starts no process it did not start before: the spawn-count case for a bare push (`symbolic-ref` 2, `config` 2) is unchanged. No call for a push of main, a dry run (`-n`, `-nu`, `--dry-run`) or a read verb. No file is written except the one log line on an unread. No timer, no long-lived process.

Tool check: the merge tool enforces three parts of this freeze, and no more. It does not stop a hand edit of the branch or the PR body: the next `--batch-build` run rebuilds the branch from the block. `merge --batch-build NAME PR...` builds the integration branch `batch-NAME` as a draft and writes the frozen lane set into the integration PR body; a changed set is refused. `merge --batch-build NAME --ready` runs the one batch-head lane lint, then the repo's ready checks, then records the head that passed. It does not mark the integration PR ready: the tool sends no GraphQL, so it names the route, and the batch runner marks it. It lints again when the head moved since the last lint, even on a PR that is already ready. A FAIL of the lint or of a ready check stores each lane it names in the block (`Blamed:`). `merge --batch-build NAME --blame PR --run URL` stores the blame of a red CI run. It stores it only when the run is completed, failed, and on the batch PR's current head, and PR is a frozen lane. `merge --batch-drop NAME PR` takes off only a stored-blamed lane and its dependents, and refuses any other lane with the next batch as its route. A drop rebuilds `batch-NAME` from the frozen set and runs no lane lint. It asks the host to return a ready PR to draft. The tool sends no GraphQL, so the host cannot do that, and the head then needs `--ready` again. The owner's 20:31 CST ruling above put the check in the merge tool.
