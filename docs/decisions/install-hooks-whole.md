# An install never shows a session a half-copied hook

## The ruling

No running session judges a call with a missing, short or mixed set of hook files.

- A cloud install stages the whole shipped set as one generation, then switches to it with one rename. The generation is the folder `installs/<id>/` under the config folder. It holds each landed folder, the generated `settings.json`, and the guard set. A guard file carries this run's id in `INSTALL_ID`. The guard set is the folder `hooks/guard.d/<id>/` inside the generation.
- The run builds the generation as `installs/<id>.tmp`, then renames it to `installs/<id>`. A copy that fails at any point removes the stage and leaves the old generation whole. The run exits 1 and writes no install record.
- One rename switches the install. The link `.cs-current` names the live generation. The run makes a new link at a temp name, then renames it over `.cs-current` (`mv -fT`, else `mv -fh`, the idiom of `point_at` in `merge/install_from_main.sh`). A failed rename leaves `.cs-current` as it was and removes the stage and the links this run made. A run never uses `ln -sfn` on a live link.
- Each landed file, each skill folder, `hooks/guard.d` and `settings.json` is a link through `.cs-current`: `<config>/hooks/guard.py` links to `<config>/.cs-current/hooks/guard.py`. A link target names no generation, so a refresh writes no link for a name that already has one. A new name gets its link before the switch, and it dangles until the switch. `settings.json` is the last link made. The first install has no `.cs-current`: it switches right after staging, then makes the links.
- A refresh retires the entries main stopped shipping after the switch, through the install manifest. The install record is written last, and only when the run had no failure. A run that fails writes no record, so the stale-copy check retries.
- A generation retired more than one hour ago is removed after a good switch, never the current one. The switch touches the outgoing generation first, so its mtime counts from its retirement, not from its creation. The age is the rule, not "keep the previous one": a CI wake runs up to 3300 s on the files it started with.
- A process keeps to one generation. Each hook, lint and janitor script resolves its own path with `realpath`, so a sibling import or read after a switch reaches the files it started with. A hook started before a switch imports the old sibling after it. `hooks/guard.py` finds `guard.d/<id>/` inside its own generation, and the guard checks `INSTALL_ID` as before.
- Named exception: a skill that is a real copied folder from an older cloud install cannot become a link by rename, because a rename cannot replace a non-empty folder. The run removes our own copy (its tree hash matches the recorded copy or the source) and links the name. A hand-edited copy goes to `backups/skills` through `backup_skill` first. That skill has a short gap, once. A name that already links is never touched. A real folder `hooks/guard.d` from an older install is left in place and not linked, because a guard process of the old install may still load from it. Its entries older than one hour are removed.
- A landing records the tree hash of each shipped skill in `backups/skill-copies/<name>`. A refresh, before the switch, hashes each skill of the live generation. A skill that matches neither its record nor the new source is a hand edit: it is copied to `backups/skills/<name>.<time>`, and the live folder stays whole. An unedited skill gets no backup; runtime files (`__pycache__` folders, `*.pyc` files) are not part of the hash (decision `copy-mode-overwrites-no-backup`).
- The first move from an install made before generations (copies, no `.cs-current`) switches first and then links name by name, so for that moment the files are a mix of old and new. Later refreshes have no such moment.
- A refresh that fails after a skill's one-time copy-to-link move leaves that skill missing until the next good run, because the abort removes its link.
- Local installs are unchanged. A local install links each file into the clone (or the pinned checkout `<clone>-live`, `merge-reinstalls-from-main`) and writes each non-guard file through a temp name in the same folder (owner ruling 2026-10-15). In link mode, the first move from a plain `<clone>-live` directory leaves that path absent for a moment.
- No moment may leave a hook file, `CLAUDE.md`, `settings.json`, `agents`, `lint` or `skills` missing, except the skill exception above. A folder swap of `hooks` is out, because it leaves `hooks` absent for an instant.
- The guard checks the `INSTALL_ID` of the modules it loaded. On an import failure, a load failure or a stamp mismatch, it waits in short steps for about 5 s and loads again. After the wait it fails closed with guard-crash, never open. This wait stays in the guard.
- One install runs at a time (owner ruling 2026-10-15). One lock file serves every installer path: `install.sh`, `install.ps1` and the post-merge hook that `install.ps1` writes.
- Each installer path logs a start line and an end line. Each line carries a unique install id and the pid.

Why: a post-merge hook that copied in place gave every session's Bash call guard-crash for a few seconds (arbiter rulings 2026-10-14 03:41 and 03:50 CDT). A cloud refresh that replaced files one by one left a session a mix of old and new files for the whole copy.

- `lint/report_guard.py` loads its helper modules from `hooks/guard.d/<id>/` first, then the flat `hooks/`. It resolves its own path with `realpath`, so in a cloud install `hooks/` is the generation's folder. It reads the id from that folder's `guard.py` stamp (`INSTALL_ID`) with one bounded regex read of the file head, once per run at load, even when question_form re-imports report_guard. No stamp, no folder or an unreadable file: flat only. A module the stamped folder lacks (override, local_time, route_match, reply_judge, call_judge, decision_watch, _nowindow) loads from the flat copy, so a half-installed folder can still mix for those; `lint/test_report_guard_stamped.py` pins the fall-through. Open note: copies under `guard.d/<id>/` resolve `__file__` paths there (hooks/guard.py, question_form.py, guard_merge.py); no report_guard call reaches them, so no verdict changes today. Cost: one bounded file read per run, no process, no file written (unmeasured). `lint/test_report_guard_stamped.py` pins it; the cost tests in `lint/test_report_guard.py` and `lint/test_report_guard_handoff.py` pin the opened-file set to the transcript and `hooks/guard.py`. Ruling: coordinator, 2026-11-09 12:46 CST (roadmap step `report-guard-stamped-copy`).

Cost: each cloud install copies every landed file once into the generation, makes one link per new name, one link rename for the switch and one `find` of `installs/`. It touches the outgoing generation once and removes each generation retired more than one hour ago. It hashes each shipped skill twice (the live copy before the switch, the new one after it); one pass over the 202 shipped skill files took about 450 ms (440 to 478 ms, n=5 runs, sha256 through `find`, Linux), so a refresh adds about 0.9 s. It writes one record file per skill. It starts no timer and no long-lived process. The copy time and the disk a generation holds are unmeasured. The disk holds about the shipped set once more for each generation of the last hour.

Proof: `hooks/test_refresh_whole.py` pins these claims. A failed copy and a failed switch leave the old install whole. No skill read misses a file during a switch. A hook keeps its generation. The guard set sits behind `.cs-current`. Names stay short under a long home path. The age prune works. `settings.json` is a link. No rename leaves a missing hook. The record is renamed last.
