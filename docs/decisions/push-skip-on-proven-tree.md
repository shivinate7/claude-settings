# A push to main skips its checks when a passing PR run already covered its tree

## The ruling

Owner, item 729 a (relayed by the coordinator, 2026-11-13 12:29 CST), extended by ruling `own-769-a-narrowed-pr-push` (owner, 16:03 CST, "main skips the whole run after a passing PR run"): the `push-skip` job skips a push to main in one case. The pushed commit's tree equals the head tree of a merged PR that the commit belongs to, and that PR's run passed. The PR is a `batch-*` integration PR or a single lane PR. In a passing run, `all-jobs-passed` and every suite job succeeded. A suite step that scope skipped (a narrowed run) does not stop the skip. A records-only run also passes (owner item 857 b, 19:48 CST Nov 15): `scope` and `all-jobs-passed` succeeded and every suite job was skipped. The rollup passes an all-skipped run only when scope's `records_only_skip` is true, and the REST jobs read has no job outputs, so the rollup is the readable proof.

- The decision's one home is the shared action `actions/push-skip` (`push-skip.py` beside its `action.yml`). `checks.yml` calls it, and child repos pin it by SHA. The suite jobs are read from the calling repo's own workflow (the jobs its `all-jobs-passed` needs, minus the jobs `nightly-skip`, `push-skip` and `scope`), through `lint/all_jobs_passed_rules.py` from the action's own checkout. A pin carries its readers.
- Skip: the tree of a `batch-*` head whose ready run passed every suite job. Or the tree of a merged lone-lane head whose newest `checks.yml` run is a completed pull request run that concluded success or cancelled, with `all-jobs-passed` and every suite job succeeded. A cancelled run counts because the cancel-on-close workflow cancels a closed pull request's unfinished runs, and that cancel can land after every job passed. Skipped steps inside a succeeded job are no gap. A records-only run is proven on both paths: every suite job skipped, `scope` and `all-jobs-passed` succeeded. A failed, cancelled or missing suite job, or an `all-jobs-passed` that is not success, is still a gap. So is a run still in progress, or a failed run, whatever its jobs read.
- Run the Linux fast jobs: a direct push, an admin merge with no green run, a tree mismatch, and a red, draft, in-progress, other-head or other-workflow run. Any read error or unknown state does the same and says "unknown". Each skip=false prints one reason line: a tree mismatch names the pull request number and both short trees, and the other refusals name the branch and the state that refused, or that no pull request covers the push. A `schedule` or `workflow_dispatch` run never skips and runs every job (the action reads `EVENT`).
- The daily run can skip (`nightly-skip`, `.github/scripts/nightly-skip.py`). It skips only when (a) the newest completed schedule run of `checks.yml`, other than this run, is green, and no other daily is still going; and (b) no push run on main was created after it, and the newest push run, if any, is at this run's head. A push run created after it gives `skip=false`, proven or not (owner ruling Q5 a, 13:44 CST Nov 23). With no push run since, it skips when the daily's own head is this run's head: that daily ran every slow leg for it. Every other case gives `skip=false`: a red, cancelled or running daily, a head mismatch, a push runs page of 100 that does not reach the green daily, more than 100 push runs since it, and any read error. A failed read is unknown, and the daily runs everything. The log says "unknown" or the reason. The jobs read of the newest push run since the daily, read only when that run completed with success, says in the log whether `push-skip` proved that run. It never changes the answer. The daily fires only on a day main moved (owner pick on item 893, relayed 14:14 CST Nov 15). The daily prints `range: <green daily head>..<this head> (<N> merges)` to its log and step summary. When the push read is a full page that never reached the green daily, it prints `at least N merges`, since N is then a floor. With no green daily it prints `range: unknown (no green daily)`.
- Ruling 176 b (owner, 2026-11-12 21:45 CST) kept the push suites until this repo changes the red-main check. This record is that change.
- Item 880, the ask to free runner slots (owner page, 11:53 CST Nov 15; relayed by the consultant, 12:06 CST: "go further than this, free as many slots as u can, if stuff can be ran later that works for me"): a push to main runs the Linux fast jobs only. Every Windows job, every mutation job and `mutation-report` take `github.event_name != 'push'` as a job-level `if`, as the macOS jobs do (R61, one macOS run per batch). The daily schedule run and a manual run start them. The slow legs are the Windows jobs, the mutation jobs (`checks-mutate-guard`, `-b`, `-c` and `mutation-report`) and the macOS jobs: every job gated `github.event_name != 'push'`. Linux fast is every other job that starts on a push: `checks`, `checks-hooks`, `checks-rest`, `checks-merge-install`, `checks-install-checkout` to `-3`, `checks-merge-git`, `checks-guard` to `-4`, `checks-shoot` and `checks-waiting-page`, with `nightly-skip`, `push-skip` and `scope`. It excludes the rollup jobs `all-jobs-passed` and `ci-done`, which run on pull requests only and never on a push. This is the default reading, and the owner may narrow it. A pull request still runs every job, so `all-jobs-passed` still needs them (its rule accepts the push guard on a listed job). Exception: the macOS jobs (`shell-macos`, `checks-macos`, `checks-macos-b`) start on a manual run, and on a daily that runs (`nightly-skip` skips the daily when main has not moved since the last green daily), not on a pull request or a push (owner, 01:33 CST Nov 16: "turn off all mac runs for now"); `all-jobs-passed` does not need them, and its `scope-skips` input is gone. <!-- glossary-ok: `checks-waiting-page` is the CI job's own name in checks.yml -->
- Departs from: the no-nightly ruling of decision `test-strategy-reset` (owner, 22:19 CST Nov 12). It adds one daily schedule, `47 8 * * *`, and the skip job is live again. The grant is the consultant's reading of item 880, not an owner-typed line; the owner may withdraw the schedule. It replaces the earlier run-in-full design for a day main did not move (item 893).
- Red daily (lane pick, not owner-typed, 12:26 CST Nov 15; the owner may reverse it; lane `push-daily-slow-legs`): a red daily turns main red as a red push run does. `actions/ci-alarm/clear_rule.py` is the one home and is unchanged. A newer green run clears it only when its jobs include every red job of the daily with success, since a `!= 'push'` conjunct keeps a job needed. A Linux-only push run never clears a red daily, and a green manual run, which runs every job, does.
- `stable` follows each green push run of main, and a green `schedule` run moves it too (owner, 12:59 CST Nov 16: "Just keep stable matching main for now then if that's easiest" and "keep that as a match every time main merges stable goes ahead too"; `actions/stable-mover/run.sh`, reading `RUN_EVENT`). A green Linux-only push run moves it, since the mover reads no job of the run. A green manual run moves nothing (lane pick, not owner-typed, 12:26 CST Nov 15; the owner may reverse it: a manual run may not be the daily's head).
- Another daily still running blocks the skip (lane pick, not owner-typed, 12:26 CST Nov 15; the owner may reverse it).

How the red-main check still sees a test-red main (`no-merge-onto-red-main`):

- A skipped push run reads green only because a tested-green tree is on main. The run it rests on passed on that exact tree, with the suites its diff touched.
- A red PR run, a direct push, an admin merge, a tree mismatch and a read error all run the Linux fast jobs on the push. A red Linux job makes the push run red. Main then reads red, and each merge prints its red tests (decision `no-merge-onto-red-main`: a PR may merge onto a red main; UNKNOWN still refuses).
- A red Windows or mutation suite does not show on a push, since a push never starts those jobs. It shows at the next daily (Risk A).
- A skipped push run clears no red nightly. It has `push-skip` success and `scope` skipped, with every suite job skipped, and a skipped job is no pass. Test: `merge/test_merge.py`, class `RedMainBrake`, `test_a_red_nightly_stays_red_under_a_newer_push_run_that_the_proven_skip_skipped`.

Why: every merge to main re-ran suites that a passing PR run had passed on the same tree, which cost Windows and macOS minutes and delayed the next merge. A tree equal to a tested-green tree has no new behaviour to test.

- Risk: accepted (owner reading of 16:03 CST). A red from an untouched suite shows at the next daily that runs, since a narrowed PR run does not run it and main skips.
- Risk: `stable.yml` moves `stable` on each green push run of main, a skipped push run included. After a narrowed PR run, `stable` can advance with no suite run on main. The proven PR run is the accepted evidence.
- Risk: a push run on main after the green daily blocks the daily skip, proven or not (owner ruling Q5 a, 13:44 CST Nov 23). A PR run narrows its Windows scope, so the daily runs every Windows shard for a push that moved main. That net catches a Windows break an import caused. Not built, a follow-on: skipping when every Windows shard ran in a proof of main's current tree.
- Risk A (item 880, named limit): a push whose tree no PR run proved (main moved after the green PR run, or a direct push) now runs Linux only. Its Windows and mutation jobs run at the next daily, up to about 24 h later, and that daily covers a range of up to the day's merges. Main is not red until then, and `stable` moves on the Linux-only push run, so it can pass a head whose Windows or mutation leg would fail (owner, 12:59 CST Nov 16, "for now"). Measured: of the 5 red main push runs on Nov 13-15, ids 43348145389, 43558136662, 43531841828 and 43697537113 failed on Windows jobs only, and 43509070895 failed on the Linux `checks` job. So 4 of 5 would now show up at the daily, not on the push, and 1 still shows on the push. Owner item 880 accepts the latency; the owner may narrow it.
- Risk B (item 880, named limit): a red daily has no revert route. `merge/merge.py` `blames()` never blames a schedule run, so `revert_proven` never lifts it. A green `workflow_dispatch` run of a fixed head clears the daily. But the next push becomes the newest head-group run, and the red returns (`actions/ci-alarm/clear_rule.py`), so each later merge needs its own dispatch until a green daily. `clear_rule.py` stays as is. Follow-up lane to propose: let a red daily blame the merges since its green head.
- Risk C (item 880, named limit): the red-main read can lose a red daily. `merge/merge.py` judges only the newest 50 runs on main, and filters them after the fetch.
  Pushes average 22 a day (37 on Nov 14). So a red daily can leave that window after about 16 to 27 hours.
  Main then reads green while the Windows leg is still red. This change does not touch the read.
  Unknown: the fetch composition, that is, whether `stable` `workflow_run` runs count in the 50.
  Follow-up step: `red-main-reads-back-to-daily`. The red-main read looks back to the newest daily by its own query. `red-daily-blames-merges` (Risk B) is already filed.
- Risk D (item 880, named limit): none now. The mover reads no job of the run, so a green Linux-only push run moves `stable` and ends green, with no red `stable` workflow run.
- Risk: accepted (coordinator, 16:37 CST Nov 13, reviewer-recommended). A skipped push run reads as evidence for the red-main check after a narrowed PR run too. So a revert whose PR run scoped out the broken suite can clear a red main. That suite is never re-run. A revert usually touches the broken paths, so the suite usually runs. Filed as note `push-skip-narrowed-clears-red-main`.
- Risk: accepted (consultant's pick, 08:39 CST Nov 15, not owner-typed; rulings r42 and `merge-needs-current-base`: main moves with no merge queue, and a PR head need not hold the main tip). The skip fires only when main has not moved since the PR's last proven head. A merge commit whose tree is main plus the PR head matches no PR run, so that push runs the Linux fast jobs. Read: main run 43687922099 (merge `36feed970`) pushed tree `9fa9c73ea412`, and PR 3435's head `0eda7cfb0` had tree `6b73a24d15b8`, because PRs 3438 and 3451 merged after that head. Its push-skip job said `skip=false`. A tree no PR run proved needs its own main run. How often main moves first is unmeasured: the eight runs before it were not read.
- Risk: a PR run re-run after a push cannot change that push's decision. The push reads the newest run at push time.
- Risk: accepted (owner, 2026-11-14 15:02 CST, ruling own-830-c, the records-only CI skip; owner item 857 b, 2026-11-15 19:48 CST, "Overrule: the ruling reopens", holds it again in full). For a pull request run of a push whose only change is docs/records.md after a fully green head, CI scope turns off the job and suite flags. Those flags cover the macOS, Windows, pointer, guard, shoot, mutation and sweep work. CI scope also turns off the mutation report. A records-only change skips every suite job and the `checks` lint job, and the all-jobs-passed rollup passes. CI scope (`.github/scripts/ci-scope.sh` and `green-head.sh`) makes the skip. That run rests on the earlier head's run, not on its own tree; the two trees differ by docs/records.md. A main push after a records-only head skips because the records-only run rests on the green head's proof. The gain is unmeasured.

Cost (unmeasured): a push makes a PR list read and a workflow file read. Each batch head adds a commit read and a check-runs read. A lone-lane head with the push's tree adds a commit read, a runs read and a jobs read (unmeasured). No file written, no process kept.

Cost of the daily (item 880): at most one scheduled run per day, in the one workflow, with no other timer or process. It runs every job at most once a day, and skips when `nightly-skip` finds main has not moved since the green daily. Reads per daily: one schedule runs read, then push runs pages back to the green daily (five pages at most). A day main did not move adds no jobs read: the head compare decides, the daily skips, and it costs about nothing. A day main moved adds at most one jobs read: the newest push run since the green daily, when that run succeeded, for the log only. At least 101 push runs since the green daily, or any failed read, makes the daily run everything. A push run starts only the Linux fast jobs, so it no longer starts the Windows or mutation runners. The stable mover reads no job. No file written.
