# An agent outside its home tree must stop

## The ruling

Each session writes only inside its own checkout. An agent whose worktree is gone must stop and report. A top-level session whose worktree is gone makes a new one before it writes. `hooks/guard.py` rule 0 holds all three parts and runs before every other rule.

Why, seven events:

- An agent resumed after the harness removed its worktree (folder and branch) ran in the shared checkout and killed another process. Date not recorded.
- Incident 2026-09-06, a write into another checkout: a session wrote into a different checkout of the same clone. `worktree-home` judges only isolated agents, so it could not see a top-level session or one started in `.claude/worktrees/<x>`.
- Banchi notes-folder refusal, 2026-10-27 (outbox `banchi-guard-shared-notes`, Banchi's guard blocks shared notes): Banchi's own guard clause `tree` in `scripts/guard-shell.py` refuses every write outside the checkout, so it refused `~/Library/Application Support/Claude-Work/side-session-notes/`, where the Claude app keeps side-session notes. A folder in no checkout must stay writable.
- Scratchpad linked checkout, lane `cc-update-behavior-diff`, 2026-11-01 22:00 CST, after a resume: `other-checkout` refused its write into a linked checkout inside its own scratchpad.
- Scratchpad linked checkout, coordinator, 2026-11-01 23:28 CST: `cd <scratchpad>/wt-notes && git branch --show-current && mkdir -p docs/plans/trial-briefs && cp <scratchpad>/trial/brief.md docs/plans/trial-briefs/q.md && git add ... && git commit ...` was refused on the `mkdir` and `cp` inside the `cd` chain. `cd <scratchpad>/wt-notes && git add` and `git commit` alone pass on main, as does `git -C <scratchpad>/wt-notes`.
- Scratchpad linked checkout, triage 5, 2026-11-01: a `cd` into its roadmap linked checkout in its scratchpad, then a heredoc write, was refused.
- Scratchpad linked checkout, coordinator, 2026-11-02 00:05 CST: an absolute `cp <scratchpad>/trial/brief.md <scratchpad>/wt-notes/docs/q.md`, with no `cd`, and the Write tool were refused.

The `cd` act landed 2026-11-01, after two named incidents. (1) Banchi PR #1003 round 3 (2026-11-01): the shared guard let `cd <other checkout>` through. It also let `cd <other> && npm run build | make up | npm install | touch | mkdir` through. So banchi could not drop its own `tree` clause. (2) Banchi D179 (an absolute-path `cd` prefix wrote about 1,500 lines into the main checkout), 2026-11-01. Coordinator ruling, 2026-11-01 19:40 CST: a main session's `cd` into an agent worktree to inspect it is refused too. The remedy is `git -C <dir>` or `git show`. Coordinator ruling, same time: `pushd <dir>` reads as a `cd`.
Risk: incident (2026-09-06). `other-checkout` landed 2026-10-28. ### `worktree-home`: an agent stays in its recorded home

- **The home record.** A call whose payload carries a valid `agent_id` (`AGENT_ID`, the pattern `janitor/agent_end_reap.py` validates) and whose `cwd` sits inside `<primary>/.claude/worktrees/agent-<agent_id>` writes that path to `<git-common-dir>/agent-homes/<agent_id>`. The common directory is shared by every worktree and outlives any one removal. The orchestrator's payloads carry no `agent_id`. An agent's branch is `worktree-agent-<agent_id>`.
- The write is fail-open. A failed write (a read-only `.git`) leaves that agent unguarded. That is the ceiling.
- **No record.** An `agent_id` that never resolves to a home, with a `cwd` not in the worktree shape, is a non-isolated agent. This part allows it.
- **Bash and PowerShell:** the payload `cwd` is not inside the recorded home. This covers a home folder that is gone. A Git Bash `cwd` in the `/c/...` form is read as `C:\...`. One exception: a lone move back into the home is allowed (`cd`, or in PowerShell `Set-Location`, `sl`, `chdir`, `pushd`), with the home path as its only argument and no separator.
- **Write, Edit, MultiEdit and NotebookEdit:** the target is under the primary checkout but outside the recorded home. One exception: a target strictly inside the caller's own `agent-<its agent id>-<suffix>` red-run folder passes, never the folder root (see `other-checkout`, the write exemption).
- **No override lifts it** (`owner-override`, owner 2026-10-18 18:37 CDT).

### `other-checkout`: no session writes into, or `cd`s into, another checkout

- **Who.** Every session: the top-level session, a session started in `.claude/worktrees/<x>`, and every agent.
- **The act.** A write whose resolved target sits in a checkout of the clone other than the checkout that holds `cwd`. The checkouts are the primary and each linked worktree. A nested worktree under `<primary>/.claude/worktrees/` owns its own files; the deepest checkout that holds a path owns it. So primary to nested worktree, worktree to primary, and worktree to sibling are refused. A write inside the call's own checkout passes.
- **The `cd` act.** A Bash or PowerShell segment whose own command word is `cd`, `pushd` or `Set-Location`, with a target in a checkout other than the one that holds `cwd`. The target resolves against the folder the previous `cd` left (`dir_before_segment`). An absolute target resolves after any move, tracked or not. A bare `pushd` and `pushd +N` / `-N` name no folder, and `popd` is not tracked. `pushd -n` only adds to the stack, so it is no move. Bare `cd X`, `cd X && <anything>`, a relative climb and a subshell `(cd X && make)` are all refused. Heredoc bodies are dropped first and the read is per segment (`_cd_targets`, as `_run_dir` reads), so a `cd` in a quote, a comment or a heredoc body is text. The act is judged before the write scan, and the write scan still runs after it. The refusal text names no path. Its remedy: stay in your own checkout, and read another with `git -C <dir>`, `git show` or a path.
- **`cd` exemptions.** Each skips the `cd` act only, never the write scan. (1) The target is inside the caller's recorded agent home: the recovery `cd` that `worktree-home` allows. (2) The target is inside the recorded home of a session with no `agent_id` (`session-home`). (3) The caller has an `agent_id` and the target is at or inside `<primary>/.claude/worktrees/agent-<its agent id>-<suffix>`, the test-author's red-run folder. The id and its dash match whole, so a sibling whose id starts with it is refused.
- **The write exemption: the caller's own red-run folder.** A write strictly inside `<primary>/.claude/worktrees/agent-<its agent id>-<suffix>` passes `other-checkout` (a shell write such as `cd <red> && echo x > f` or `cp t.py <red>/`, a Write, an Edit) and the Write-target check of `worktree-home`. One matcher, `_own_red_run`, serves this and exemption (3). It anchors on the primary checkout alone, so a folder under a linked worktree gets nothing. The id and its dash match whole, and paths compare case-folded. **The folder root stays protected:** a Write on the root, `rm -rf <red>`, `mv <red> x`, and `cd <red> && rm -rf .` are refused, because removing a worktree by hand is refused (below). The one verb that may name the root is `cp` (`RED_RUN_ROOT_VERBS`), in any position, so `cd <red> && cp -r . <home>` passes too. A sibling agent's red-run folder, the prefix trap `agent-<id>b-red`, the primary, and a call with no `agent_id` stay refused. A delete through an interpreter (`python -c`) is not seen, the ceiling below.
- **Outside the clone passes.** A scratchpad, `~/.claude`, or a notes folder such as `~/Library/Application Support/Claude-Work/side-session-notes/` is in no checkout, unless a `git worktree add` put one there. A linked checkout in this session's own scratchpad (`under_session_scratchpad`, the payload `session_id`) passes for a top-level call only. A call with an `agent_id` keeps the refusal: an agent shares its session's id, and `worktree-home` judges no shell target, so without the `agent_id` test an isolated agent could newly write into the session's scratchpad linked checkout. A linked checkout in another session's scratchpad, or a missing or invalid session id, is refused as before. Whether a resumed session's payload id equals its old scratchpad's id is unmeasured.
- **A separate clone of the same repo.** A write target, a shell write target or a `cd` move in a separate clone is refused as a write into another checkout. A stat walk finds the nearest `.git` entry above the path. The path is in a separate clone when that entry is not a checkout of this clone and has another git common dir. It must not sit inside the own checkout (a submodule) or above it (a dotfiles repo at `~`). Its `origin` URL must name the same repo. The URLs are read as files from each clone's `config` and compared by their last two path parts (`owner/repo`), so https, ssh and proxy forms match. A local-path origin matches when it resolves to the other clone. An unreadable or missing origin is unknown and passes. A clone under the temp folder (`tempfile.gettempdir()`) passes, which covers every scratchpad. Same repo only (coordinator ruling, 2026-11-02 10:06 CST): a clone of another repo passes, because a session's normal cross-repo work goes there and no incident names it.
- **A cwd stranded in a separate clone.** The home clone is the one that holds the hook's `CLAUDE_PROJECT_DIR` (Claude Code hooks docs; unmeasured live). When cwd sits in a separate clone of it, every write inside cwd's clone is refused. So is a git verb that changes files (`SESSION_HOME_GIT_VERBS`, read as `session_home_git_hit` reads it). From any cwd, `git -C <separate clone>` with such a verb is refused too; `git -C <dir> log` and `show` pass. A `cd` back into any checkout of the home clone passes, and reads pass. An unset `CLAUDE_PROJECT_DIR`, or one in no clone, is unknown and passes.
- **The common git directory passes.** `<primary>/.git` is shared by every checkout, so a linked worktree may write `.git/info/exclude`.
- **Removing a worktree by hand is refused.** `rm -rf .claude/worktrees/<x>` from the primary is a write into another checkout. The refusal names `git worktree remove` and the janitor sweep, the proper tools.
- **Tools.** Write, Edit, MultiEdit and NotebookEdit targets, and the shell write targets that frozen-path reads (`_shell_write_hit`: a redirect, a mutating command, `sed -i`). A `cp` source is a read in any segment, a loop body included, and stays one when the DEST is one quoted variable (`"$f"`); an `mv` source is judged. A relative shell target resolves against the folder a leading `cd` moved to (`dir_before_segment`), or against `cwd` when that folder cannot be told. A shell read, or a git command run with `-C` into another checkout, is no write here.
- **Ceiling.** A target named through a variable the scan cannot resolve, or `$(...)`, is not seen, as for frozen-path. A heredoc body stays in the shell scan. A quoted python body leaves it only when three things hold. (a) The command, bodies stripped, is one segment: the python header with plain flags, and no other line. (b) Its parse tree names none of `_PY_RUNS_TEXT`. One call is cleared: `subprocess` running python on a `.py` script, no shell, literal or a top-level name bound once. A node `-e` list is read in every list literal, except a direct argument of `print` or of a `json.dumps` held by a statement. (c) Each file it writes has a literal name ending in one of `_PY_TEXT_EXTENSIONS`: `.json`, `.md`, `.txt` or `.csv`. A pipe, a redirect, `;`, `&&`, a substitution, a group, a loop or a function breaks (a), since a shell may run what the body prints. When that scan finds nothing, `interpreter_write_hit` adds the literal-path writes of a python, node, perl or ruby body, and it only adds refusals. A perl or ruby body is read for `open` with a write mode, `File.write`, `File.open`, a copy or a rename. A perl `s#…#…#` is not read: the scan takes its `#` for a comment opener. A perl `-i` edit is read like `sed -i`. A `cp` into an unresolved variable target is not seen. Not seen either: a delete from a body (`os.remove`, `rmtree`), a path it builds at run time, a perl or ruby `-e` script, an `open` whose path is a call such as `Path(...)`. The `cd` act does not read these. `cd "$VAR"`, `cd -`, a bare `cd`, `popd`, `sl`, `chdir`, `Push-Location` and `bash -c '...'`. `$(cd ...)` and backtick substitution. A glob target (`../lane-[b]`). A target made earlier in the same command (`mkdir -p X && cd X`). A relative `cd` after a move it cannot read (`cd "$HOME" && cd ../x`) is not read either, nor a relative `cd` after a `cd` whose target is missing at check time. A `cwd` in no checkout has no "other" checkout, so its `cd` passes. `touch` and `mkdir` are not in the mutating-command list, so a direct `mkdir <other>/x` with no `cd` passes (a debt note).
- **Cost.** At most one `git worktree list --porcelain -z` per call. A Read or Grep spends none. A shell command spends none unless it holds a `>`, a mutating command, `sed` or `perl` once redirects onto a stream (`2>&1`) or `/dev/null` are dropped. Only the gate `interpreter_may_write` adds a case: a heredoc or inline script that holds `open` for writing, `write_text`, `write_bytes`, `shutil.copy`, `shutil.move`, `os.replace`, `os.rename`, a node write, or a perl or ruby write. A call whose `cwd` has no `.git` at or above it spends none (a stat walk). A shell command with no `cd`, `pushd` or `Set-Location` word adds no cost. A `cd` walks up from its target by stat to the nearest `.git` entry. The same entry as the cwd's, or none (a folder in no checkout), spends nothing. Only a different `.git` entry spends the one list. A git verb that changes files spends the list only when it can reach another clone. That is a cwd stranded in a separate clone of the `CLAUDE_PROJECT_DIR` clone, or a `-C` or `cd` folder whose nearest `.git` entry is not the cwd's. A target or move under a `.git` entry that is not a checkout of this clone also reads up to four small files (a `.git` file, `commondir`, two `config` files); no git is spawned for them. No file, log or process is added. `worktree_home_cross_checkout_cost_case` counts the spawns.
- **An owner override lifts it.** The owner may mean the write. It has its own rule id so that `worktree-home` stays outside every override.

### `session-home`: a top-level session whose worktree is gone makes a new one

Owner ask, 2026-10-29 16:49 CDT: a resumed top-level session whose worktree was removed ran in the primary checkout. Risk: likely (owner-reported). Landed 2026-10-29.

- **The record.** A call with no `agent_id` whose `cwd` sits in `<primary>/.claude/worktrees/<name>` writes that path to `<primary>/.git/session-homes/<session_id>`, only when the record is missing or differs. A call with an `agent_id` never writes it: agents share the session's `session_id`. A call whose `cwd` sits in an agent's worktree, `<primary>/.claude/worktrees/agent-<agent_id>`, never writes it either: that is the session inspecting an agent's tree.
- **A deliberate exit clears it.** An ExitWorktree call with no `agent_id`, from any `cwd`, deletes a record whose folder still stands. ExitWorktree is in the guard's PreToolUse matcher for this reason. An ExitWorktree while the record is lost clears nothing.
- **The write is atomic.** A temp file in the same folder, then a rename, so no reader sees half a path.
- **The act.** No `agent_id`, a non-empty record whose folder is gone, `cwd` in the primary checkout, and one of:
  - a Write, Edit, MultiEdit or NotebookEdit target, or a shell write as `_shell_write_hit` reads it, in the primary checkout or under the lost home path;
  - a git command run in the primary that changes its files or branch: checkout, switch, pull, merge, commit, rebase, restore, reset, stash, cherry-pick, revert, am, apply. The owner's ask is "refuse writes in the primary checkout", and these write it.
- **Passes.** A target under `<primary>/.git/`, or outside the clone. Read, Grep, and a shell call that writes no file (`git fetch`, `git status`, `git log`, `git diff`, `git branch <name>`, `git worktree add`), so recovery never depends on the lost state. A git command run with `-C` in a live worktree. A git command whose folder is a shell variable (`cd "$WT" && git commit`, `git -C "$WT" commit`): the folder is unknown. A write inside a new worktree, which also rewrites the record.
- **No record passes.** A fresh session, and one that never entered a worktree, are unchanged.
- **Resume notice.** `hooks/session_start.sh`, on `source` `resume` with a record whose folder is gone, prints one line: make a new worktree with the EnterWorktree tool before any write. EnterWorktree branches from origin's default branch by default (`worktree.baseRef` "fresh").
- **The refusal** names EnterWorktree, never the lost path (`git-remedy-never-names-target`).
- **An owner override lifts it** (`owner-override`). A top-level session is the owner's own, so the owner may mean the write.
- **Cost.** No git spawn beyond what the call already spends: the primary is found by path shape and a stat walk. Files written: one record per session that entered a worktree, rewritten only when its worktree changes, deleted at ExitWorktree. Nothing else deletes it. `session_home_*_case` counts the spawns.
- **Premises.** ExitWorktree reaching PreToolUse is read from the docs, unmeasured live (debt exit-worktree-hook-unmeasured). A resume keeps the `session_id` unless `--fork-session` is passed (CLI reference, read; unmeasured live). A resume whose worktree is gone starts in the folder Claude was launched from (worktrees docs, read).
- **Limits.** A visit to a non-agent lane tree records it as home (debt session-home-lane-visit). A session whose `cwd` is in no checkout, which then runs `cd <primary> && <write>`, is not judged. A lane lost before its first guarded call (Read and Grep only) left no record. A git command inside `bash -c` or `sh -c`, and `submodule update`, `read-tree` or `checkout-index`, are not read. A `git` word left unquoted in another command (`echo git commit`), and `git apply --check`, are refused. A worktree removed by hand with `git worktree remove`, without ExitWorktree, leaves the record: primary writes are refused until a new worktree or an override. A cloud container reclaim gives a fresh clone with no record, so a resumed cloud session is allowed in its fresh, unshared primary.

### All three parts

- **Read and Grep** are always allowed, so a session can still report (`verification-recovery-independent-of-state`).
- **The refusal** never names the target or the home (`git-remedy-never-names-target`). The matched detail goes to the log.
- **Unreadable is not a hit.** No git, no common directory, an unreadable record, or a `cwd` in no checkout allows (`verification-report-unknown-reads`).
- **The predicate is the act** (`predicate-is-the-act`). The rule reads `agent_id`, `cwd` and the write target.
