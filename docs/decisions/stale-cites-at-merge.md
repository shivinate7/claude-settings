# A PR that removes a name also fixes each prose line that names it

## The ruling

The ste-lint CI step refuses a pull request that leaves stale prose of one kind. The kind is a tracked Markdown line that names a repo file or a Python name bound at module level that the same PR deleted, renamed or moved. `lint/stale_cites.py` is the check. `actions/ste-lint/run.sh` runs it in scope `changed`, before the markdown-only exit, so a code-only PR is checked too. Every repo that pins the ste-lint action gets it when its pin moves.

Owner, 2026-11-01 16:30 CST, in chat to triage: "make it a standing thing that stale prose never makes it anymore".

- Codes: STALE001, a path the range removed. STALE002, a name cited as "`file.py` `name`" (backticked name) or "(file.py name)" on one line, where `name` was bound in that file at base and is not bound at head. A bare word after a path is never a cite. Python is read with `ast`, and module-level names come from py-facts `defined_names` (`skills/plain-english-map/scripts/lib/py-facts.py`, the one home). A name counts when a module-level def, class, assignment or import binds it, also under a module-level if or try. A def directly in a module-level class counts too. A def nested in a function does not. A name that moved but is still bound in the file (`f = h`, a re-import) is not removed. JavaScript and shell names are not checked. A cite of a name in such a file (`.mjs`, `.js`, `.cjs`, `.ts`, `.sh`) that the range touched prints `stale-cites: unknown, <md path>:<line> ...` and keeps the exit 0, never a pass and never a finding. Only a run that already reads Markdown prints it, so touching such a file adds no git start and no Markdown read. STALE004, a value cite, has its own item below.
- Scope, coordinator picks of 2026-11-03 19:48 CST: the pointer plan's steps L1 to L5 are in scope. A cite of a value matches the code as written. Python only, and JavaScript reads "unknown". A reverse list (code that nothing in prose cites) is report-only, never a finding, the same form as decision `claude-md-change-is-flagged` (a CLAUDE.md change is reported, never held).
- STALE004, a value cite: one backtick span `file.py: NAME = literal`. It reads the value grammar of MAP9 (`VALUE_CITE_RE` in `skills/plain-english-map/scripts/map-check.mjs`). The grammar is copied into Python because the ste-lint action runs Python only. A span with no file is no cite here. It fires in three cases only. The PR changed the value and the cite still equals the base value. The PR removed the name from the file and the cite equals the base value. Or the PR added the line and the cite is not the value at head, even when no literal changed. A second copy of a line already wrong at base is an added line: lines are counted, not looked up. A line the PR rewords counts as added, so an already-wrong value cite on it fires. A line already wrong at base and left alone never fires. A `.py` value is the module-level literal that py-facts `answer` reads: a value `ast.literal_eval` accepts and JSON can hold. A JSON value is not read. A cite of one in a file the range touched prints `stale-cites: unknown`, as a cite of a `.mjs`, `.js`, `.cjs`, `.ts` or `.sh` value does. It prints only in a run that already reads Markdown. A lone `.json` touch reads no Markdown. `skills/plain-english-map/tests/value-cite-parity.json` holds the two grammar copies together, and both suites read it.
- Readers: `scan()` runs a list of readers (`READERS` in `lint/stale_cites.py`), one per code. A later code (STALE003 flags) adds one entry. A mark `<!-- ste-disable-line STALE004 -->` leaves a value cite line out, and its unknown too.
- Only names the range removed count. A line already stale at base, for a name the range did not touch, never fires. So the check is never red on work the PR did not do.
- A path matches only at a path boundary. `mods/session-board/hooks/lib.mjs` does not match `hooks/lib.mjs`.
- Left out: `docs/records.md` (generated at merge), each file `.ste-lint-exclude` names, and a line marked `<!-- ste-disable-line STALE001 -->`, `STALE002` or `STALE004`. A record that names a removed file on purpose takes the mark.
- Each Markdown file is read as committed at head, never from the working tree, through the same `git cat-file --batch` process. A byte that is not UTF-8 reads as a replacement character and the file is still checked.
- A base that does not resolve (a shallow clone with no history) is unknown, not a finding. The check prints `stale-cites: unknown, ...`, names fetch-depth 0, and exits 0, so a repo that pins the action and checks out shallow is not red at its pin move (owner-lane call, 2026-11-01).
- `FAIL=false` is honored: the findings print and the step exits 0.
- Findings have their own exit path. The STE split script makes a finding on an untouched line report-only, and every stale line is untouched by design.
- A touched `.py` file that does not parse at base or head is unknown the same way: `stale-cites: unknown, <file> ...`, and it alone keeps the exit 0.
- Cost, per ste-lint changed-scope run (each PR CI run and each `bin/ste-changed` call): one `python3` start. Git starts 3 (`rev-parse`, `merge-base`, `diff`) when the range removes or renames no path and touches no `.py` file. A touched `.py` or `.md` file adds one `git cat-file --batch`; a range that touches neither still starts 3, a lone `.json` touch included. A removed path or name, or a changed literal, adds `ls-tree`, so 5 at most. A changed literal is a module-level name of a touched `.py` that holds a literal at base and, at head, holds a different literal or is gone. A change to or from a call, or any value that is no literal, is no literal change. Each Markdown file is read once. Every tracked one is read when something was removed or a literal changed. Otherwise only the Markdown the range touched is read, and no `ls-tree` runs. A touched `.py` file also loads the py-facts script once, in-process (importlib, no start, no `.pyc`). It writes no file and starts no lasting process. `CostTests` in `lint/test_stale_cites.py` proves it.

## Kind of staleness

Measured risk, 2026-11-01. A sample on main at 84a56038: tracked Markdown held 1,176 cites that name a repo path, a path with a symbol, or a script flag. One named a function that a PR had moved to another file (`docs/debts/notes.md`, note liveness-windows-arm-unproven: `hooks/guard.py _process_start_ms`, now in `hooks/git_reads.py`). Other dead-looking paths were paths in other repos or runtime paths. The debts folder held no debt on stale prose. Notes: stash-export-comment-stale (a stale code comment) and layout-no-such-kind (a "none yet" line).

Not covered: a claim that is wrong in meaning, such as a "Departs from" line that describes main wrongly (the 2026-11-01 16:23 CST incident). No string match can judge meaning. `hooks/prose_judge.py` judges edits inside a decisions folder only.
