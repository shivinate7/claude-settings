# A PR that removes a name also fixes each prose line that names it

## The ruling

The ste-lint CI step refuses a pull request that leaves stale prose of one kind. The kind is a tracked Markdown line that names a repo file or a Python name bound at module level that the same PR deleted, renamed or moved. A line that cites a script flag the same PR removed from that script is stale too. `lint/stale_cites.py` is the check. `actions/ste-lint/run.sh` runs it in scope `changed`, before the markdown-only exit, so a code-only PR is checked too. Every repo that pins the ste-lint action gets it when its pin moves.

Owner, 2026-11-01 16:30 CST, in chat to triage: "make it a standing thing that stale prose never makes it anymore".

- Codes: STALE001, a path the range removed. STALE002, a name cited as "`file.py` `name`" (backticked name) or "(file.py name)" on one line, where `name` was bound in that file at base and is not bound at head. A bare word after a path is never a cite. Python is read with `ast`. `lint/stale_cites.py` `names_in` walks each module-level statement, also inside a module-level if, try, with, for, while or match, never inside a def or class. In those statements, py-facts `defined_names` (`skills/plain-english-map/scripts/lib/py-facts.py`, the one home) finds each def, class, import and assignment to a plain name. `lint/stale_cites.py` `target_bindings` adds each name in a tuple, list or starred assignment target, a for target, a with-as target and a walrus target. A def directly in a module-level class counts too. A def nested in a function does not. A name that moved but is still bound in the file (`f = h`, a re-import) is not removed. JavaScript and shell names are not checked. A cite of a name in such a file (`.mjs`, `.js`, `.cjs`, `.ts`, `.sh`) that the range touched prints `stale-cites: unknown, <md path>:<line> ...` and keeps the exit 0. It prints only when the range also removes a path, a Python name or a flag, since only then is Markdown read. A range that touches only such files prints nothing and passes, and reads no Markdown. A touched `.sh` file is still read once for its flags (STALE007) through the one `git cat-file --batch`, so it starts the same 5 processes as a touched `.py`. STALE007, a flag cited as `script --flag` inside one backticked code span, where the range removed that flag from that script. A `~/.claude/<path>` cite resolves to `<path>` at the repo root, and a leading `./` is dropped. A bare basename (`stale_pages.py --items`) resolves to the one tracked file with that name at head, and a basename that two tracked files share names neither, so it never fires. A Python flag is an `add_argument` string literal, read with `ast`. A shell (`.sh`) flag is a whole-word `--token` in the file. A flag only named in a docstring or comment was never declared. A span that cites no script (`git push --force`), and a script that never held the flag (a shim whose target holds the flags), never fire. A flag that another touched `.py` file declares as an `add_argument` literal at head, or another touched `.sh` file holds as a whole word, moved there and is not removed. So is a flag that a parent parser declares, touched or not: the script takes `parents=[name()]` from a `from module import name` that names one tracked `.py` file, and that file's def `name` (the whole module when it has no such def) is read at head.
- Flag limits: a shell comment that still names a removed flag passes. An extensionless shell script (`bin/rm`, `bin/sim-test` and others) is never read. A flag that another subcommand of the same file keeps passes. (a) Another touched `.py` that declares the flag at head masks its removal. A batch integration range is likelier to hit this. The lint run on each lane head is the narrower check. (b) An unrelated touched `.sh` with the flag as a whole word, anywhere (help text or a comment too), masks it. (c) A flag moved from a `.sh` into a `.py` parser still fires. The match is same-kind only. (d) A parent parser is followed one level and only through `from module import name`: a parent reached as `module.name()`, a parent of a parent, or a module name that two tracked files share (neither beside the script) is not read, so a flag moved there still fires. (e) A bare basename that two tracked files share is never resolved, even when the range changed only one of them, so that cite passes.
- Test copy: the `argument_flags` copy in `lint/test_stale_cites.py` is a near copy of the reader in `lint/stale_cites.py`. It keeps any string that starts with `-`, where the reader keeps only `LONG_FLAG.fullmatch` matches. A change to one needs the other.
- Scope: built on main are `stale-names-bound` (the removed-name check, STALE002), `stale-flags` (the removed-flag check, STALE007), the Report below, and the opt-in tree mode (the dead-path check STALE003 and the bad-anchor check STALE004; decision `stale-cites-whole-tree`, the whole-tree record). The planned lanes (`value-cites` and the records-only lane) follow `docs/plans/pointer-system.md`. The coordinator's picks of 2026-11-03 19:48 CST set their rules: a value cite matches the code as written, Python only, and a JavaScript value reads "unknown". The reverse list (code that nothing in prose cites) is planned, report-only, never a finding, the same form as decision `claude-md-change-is-flagged` (a CLAUDE.md change is reported, never held).
- Report, step L4 of the pointer plan: the check prints report lines after its findings, and the ste-lint step adds them to its summary under "Stale-cites report". A line starts `stale-cites: report, `. It is never a finding and never changes the exit code, the same form as decision `claude-md-change-is-flagged`. Two halves. The anchor half names each `<!-- rule:id -->` anchor whose sentence changed in a rule file (`RULE_FILES` in `lint/rule_audit.py`), with its `lint/rule_mechanisms.json` row (kind, ref, test). Then it lists this PR's changed files under `hooks/`, `lint/`, `bin/`, `actions/` and `.github/`, or "none". It gives no verdict on whether the guard or check changed. A guard row's logic can sit in any module, so the reviewer judges (orchestrator ruling, process-only, 2026-11-03 20:35 CST). The Home half names each changed non-Markdown file (added, changed, removed or renamed), the decisions whose Home line names it, and the rows whose ref or test is it. Only a real anchor counts: an anchor inside a code span is a mention, never named. A repo with no `lint/rule_mechanisms.json` gets the Home half only, with no error. Named readers: the lane reviewer, who checks that the guard or check behind an edited rule changed with it, and the batch runner, who reads the summary before a merge.
- Report cost: the report adds one `ls-tree` of the decisions folders and the mechanisms file when a non-Markdown file changed. It adds none when the run already listed the whole tree. The decisions folder is the first of `candidates(root, "decisions")` in `lint/layout.py` that holds a file, so a repo not rolled out to the layout is read at `decisions/` or `docs/decisions/`. It also adds one `git cat-file --batch`. That batch reads each decision record whole (a regex takes its Home line) and the mechanisms file once. A changed rule file adds its base and head blobs and the mechanisms file. Its list of changed files comes from the diff the run already read, so an edit to a rule file alone starts 4 git processes (`rev-parse`, `merge-base`, `diff`, `cat-file --batch`). A PR that changes only Markdown outside the rule files adds nothing. A `lint/rule_mechanisms.json` that is not JSON, or whose rules or rows are not objects, prints one `stale-cites: unknown, ...` line naming the file, and the Home half still prints without rows. Any other failed report read prints one `stale-cites: unknown, report not read, ...` line. The exit stays as it was.
- Readers: `scan()` runs a list of readers (`READERS` in `lint/stale_cites.py`), one per check. The later lane `value-cites` adds one entry. The report follows the findings.
- Only names the range removed count. A line already stale at base, for a name the range did not touch, never fires. So the check is never red on work the PR did not do.
- A path matches only at a path boundary. `mods/session-board/hooks/lib.mjs` does not match `hooks/lib.mjs`.
- Left out: `docs/records.md` (generated at merge), each file `.ste-lint-exclude` names, and a line marked `<!-- ste-disable-line STALE001 -->`, `STALE002`, `STALE003`, `STALE004` or `STALE007`. A record that names a removed file on purpose takes the mark.
- Each Markdown file is read as committed at head, never from the working tree, through the same `git cat-file --batch` process. A byte that is not UTF-8 reads as a replacement character and the file is still checked.
- A base that does not resolve (a shallow clone with no history) is unknown, not a finding. The check prints `stale-cites: unknown, ...`, names fetch-depth 0, and exits 0, so a repo that pins the action and checks out shallow is not red at its pin move (owner-lane call, 2026-11-01).
- `FAIL=false` is honored: the findings print and the step exits 0.
- Findings have their own exit path. The STE split script makes a finding on an untouched line report-only, and every stale line is untouched by design.
- A touched `.py` file that does not parse at base or head is unknown the same way: `stale-cites: unknown, <file> ...`, and it alone keeps the exit 0.
- Cost, per ste-lint changed-scope run (each PR CI run and each `bin/ste-changed` call): one `python3` start. Git starts 3 (`rev-parse`, `merge-base`, `diff`) when the range removes or renames no path and changes only Markdown outside the rule files. A touched `.py` or `.sh` file adds one `git cat-file --batch`, which the name reader and the flag reader share, and, through the report, one `ls-tree`, so it starts 5. A removed or renamed path adds `ls-tree` and that `cat-file --batch`, so 5 at most. Each tracked Markdown file is read once. It is read only when the findings have something to look for: a removed or renamed path, a name that a touched `.py` file no longer defines, or a flag that a touched `.py` or `.sh` file no longer declares. A touched `.py` file also loads the py-facts script once, in-process (importlib, no start, no `.pyc`). It writes no file and starts no lasting process. `CostTests` in `lint/test_stale_cites.py` proves it.
- An opt-in whole-tree mode is in stale-cites-whole-tree. The range check here is unchanged.
