# A PR that removes a name also fixes each prose line that names it

## The ruling

The ste-lint CI step refuses a pull request that leaves stale prose of one kind. The kind is a tracked Markdown line that names a repo file or a Python name bound at module level that the same PR deleted, renamed or moved. A line that cites a script flag the same PR removed from that script is stale too. `lint/stale_cites.py` is the check. `actions/ste-lint/run.sh` runs it in scope `changed`, before the markdown-only exit, so a code-only PR is checked too. Every repo that pins the ste-lint action gets it when its pin moves.

Owner, 2026-11-01 16:30 CST, in chat to triage: "make it a standing thing that stale prose never makes it anymore".

- Codes: STALE001, a path the range removed. STALE002, a name cited as "`file.py` `name`" (backticked name) or "(file.py name)" on one line, where `name` was bound in that file at base and is not bound at head. A bare word after a path is never a cite. Python is read with `ast`. `lint/stale_cites.py` `names_in` walks each module-level statement, also inside a module-level if, try, with, for, while or match, never inside a def or class. In those statements, py-facts `defined_names` (`skills/plain-english-map/scripts/lib/py-facts.py`, the one home) finds each def, class, import and assignment to a plain name. `lint/stale_cites.py` `target_bindings` adds each name in a tuple, list or starred assignment target, a for target, a with-as target and a walrus target. A def directly in a module-level class counts too. A def nested in a function does not. A name that moved but is still bound in the file (`f = h`, a re-import) is not removed. JavaScript and shell names are not checked. A cite of a name in such a file (`.mjs`, `.js`, `.cjs`, `.ts`, `.sh`) that the range touched prints `stale-cites: unknown, <md path>:<line> ...` and keeps the exit 0. It prints only when another check in the same run reads that Markdown page (`find_stale` in `lint/stale_cites.py`). A range that only adds or edits such files, and removes no flag, gives no finding and passes. A touched `.sh` file is still read once for its flags (STALE007) through the one `git cat-file --batch`, so it starts the same 5 processes as a touched `.py`. STALE007, a flag cited as `script --flag` inside one backticked code span, where the range removed that flag from that script. A `~/.claude/<path>` cite resolves to `<path>` at the repo root, and a leading `./` is dropped. A bare basename (`stale_pages.py --items`) resolves to the one tracked file with that name at head, and a basename that two tracked files share names neither, so it never fires. A Python flag is an `add_argument` string literal, read with `ast`. A shell (`.sh`) flag is a whole-word `--token` in the file. A flag only named in a docstring or comment was never declared. A span that cites no script (`git push --force`), and a script that never held the flag (a shim whose target holds the flags), never fire. A flag that another touched `.py` file declares as an `add_argument` literal at head, or another touched `.sh` file holds as a whole word, moved there and is not removed. So is a flag that another module declares for the script, touched or not. Two forms are read, each from a `from module import name` that names one tracked `.py` file: `parents=[name()]`, and a call `name(parser)` that passes a parser (a name the script binds to `ArgumentParser(...)`, `.add_parser(...)` or another parser maker). That file's def `name` (the whole module when it has no such def) is read at head. A flag also counts as declared through a loop over a module-level table: `for flag in NAME:` or `for flag, _, text in NAME:` with `add_argument(flag)`, and `add_argument(*NAME)`. `NAME` must be bound once to a tuple or list of string constants, or of tuples of constants. A removed flag that head still names as a string constant, in a form none of these reads, prints `stale-cites: unknown` for its cite and is never called removed. STALE009, a sentence on an added decision-record line that states what code does, with no cite; report only. STALE010, a line the range adds citing a Python name in a tracked or once-tracked top folder, whose file is absent at head or does not bind it; a finding. Both follow decision `record-cites-live-code` (claims about code cite live code names).
- Flag limits: a shell comment that still names a removed flag passes. An extensionless shell script (`bin/rm`, `bin/sim-test` and others) is never read. A flag that another subcommand of the same file keeps passes. (a) Another touched `.py` that declares the flag at head masks its removal. A batch integration range is likelier to hit this. The lint run on each lane head is the narrower check. (b) An unrelated touched `.sh` with the flag as a whole word, anywhere (help text or a comment too), masks it. (c) A flag moved from a `.sh` into a `.py` parser still fires. The match is same-kind only. (d) A parent parser or helper is followed one level, and only through `from module import name`. These are not read: a parent or helper reached as `module.name()`, a parent of a parent, a helper that calls another helper, and a parser passed through another name. Nor is a module name that two tracked files share (neither beside the script), or a table bound twice or built at run time. A flag moved there, and named nowhere in the script as a string constant, still fires. The same flag named as a constant reads unknown. (e) A bare basename that two tracked files share is never resolved, even when the range changed only one of them, so that cite passes. (f) A flag removed from a shared parent that a script includes through `parents=` is recorded under the parent's file only. A prose cite of that flag on the script is not reported.
- Test copy: `argument_flags` in `lint/test_stale_cites.py` is a literal-only copy of the reader `argument_flags` in `lint/stale_cites.py`. It keeps each `add_argument` string literal that starts with `-`, where the reader keeps only `LONG_FLAG.fullmatch` strings. It does not read a module table, a loop over one, `add_argument(*NAME)`, a parent parser, or a helper that takes the parser by position or keyword. Only the reader reads those forms. A case for one uses the copy to pin the literals a fixture declares. It raises on source that does not parse, where the reader returns None. A change to the reader's literal read needs the copy changed too.
- Scope: built on main are `stale-names-bound` (the removed-name check, STALE002), `stale-flags` (the removed-flag check, STALE007), `value-cites` (the value check, STALE008), the Report below, and the opt-in tree mode (the dead-path check STALE003 and the bad-anchor check STALE004; decision `stale-cites-whole-tree`, the whole-tree record). The planned work follows `docs/plans/pointer-system.md`. The coordinator's picks of 2026-11-03 19:48 CST set the value cite rules: a value cite matches the code as written, Python only, and a JavaScript value reads "unknown". The reverse list (code that nothing in prose cites) is planned, report-only, never a finding, the same form as decision `claude-md-change-is-flagged` (a CLAUDE.md change is reported, never held).
- Report, step L4 of the pointer plan: the check prints report lines after its findings, and the ste-lint step adds them to its summary under "Stale-cites report". A line starts `stale-cites: report, `. It is never a finding and never changes the exit code, the same form as decision `claude-md-change-is-flagged`. Two halves. The anchor half names each `<!-- rule:id -->` anchor whose sentence changed in a rule file (`RULE_FILES` in `lint/rule_audit.py`), with its `lint/rule_mechanisms.json` row (kind, ref, test). Then it lists this PR's changed files under `hooks/`, `lint/`, `bin/`, `actions/` and `.github/`, or "none". It gives no verdict on whether the guard or check changed. A guard row's logic can sit in any module, so the reviewer judges (orchestrator ruling, process-only, 2026-11-03 20:35 CST). The Home half names each changed non-Markdown file (added, changed, removed or renamed), the decisions whose Home line names it, and the rows whose ref or test is it. Only a real anchor counts: an anchor inside a code span is a mention, never named. A repo with no `lint/rule_mechanisms.json` gets the Home half only, with no error. Named readers: the lane reviewer, who checks that the guard or check behind an edited rule changed with it, and the batch runner, who reads the summary before a merge.
- Report cost: the report adds one `ls-tree` of the decisions folders and the mechanisms file when a non-Markdown file changed. It adds none when the run already listed the whole tree. The decisions folder is the first of `candidates(root, "decisions")` in `lint/layout.py` that holds a file, so a repo not rolled out to the layout is read at `decisions/` or `docs/decisions/`. It also adds one `git cat-file --batch`. That batch reads each decision record whole (a regex takes its Home line) and the mechanisms file once. A changed rule file adds its base and head blobs and the mechanisms file. Its list of changed files comes from the diff the run already read, so an edit to a rule file alone starts 4 git processes (`rev-parse`, `merge-base`, `diff`, `cat-file --batch`). A PR that changes only Markdown outside the rule files adds nothing. A `lint/rule_mechanisms.json` that is not JSON, or whose rules or rows are not objects, prints one `stale-cites: unknown, ...` line naming the file, and the Home half still prints without rows. Any other failed report read prints one `stale-cites: unknown, report not read, ...` line. The exit stays as it was.
- STALE008, a value cite: one backtick span `file.py: NAME = literal`, the cite grammar of MAP9 (`VALUE_CITE_RE` in `skills/plain-english-map/scripts/map-check.mjs`). The grammar is copied into `lint/stale_cites.py` because the ste-lint action runs Python only; `skills/plain-english-map/tests/value-cite-parity.json` holds the copies together, and both suites read it. A span with no file is no cite here. It fires in three cases only. The range changed the module-level literal and the cite still equals the base value. The range removed the assignment and the cite equals the base value. Or the range added the line and the cite is not the value at head, even when no literal changed. Lines are counted, not looked up: a second copy of a line already wrong at base is an added line, and a line the range only moved is not. A line already wrong at base and left alone never fires. A value is the module-level literal that py-facts `answer` reads (`ast.literal_eval` accepts it and JSON can hold it), compared by value. A head value that is no literal, such as a call, gives no finding. A cite of a `.mjs`, `.js`, `.cjs`, `.ts` or `.sh` value prints `stale-cites: unknown` on an added line always, and on an untouched line only when the whole tree is read and the range touched that file. A JSON value is not read. A `.py` cite the check cannot read is never skipped. On an added line, a value that is no JSON literal (MAP9 reads none) or a path no tracked file has is a finding. A name that holds no literal at head, or a file that does not parse, is unknown. An untouched line prints each of these as unknown, only when the whole tree is read. A cite of a path the range removed is STALE001's. Fenced blocks count as prose. A mark `<!-- ste-disable-line STALE008 -->` leaves a line out, its unknown too.

- Readers: `scan()` runs a list of readers (`READERS` in `lint/stale_cites.py`), one per check. The lanes `stale-flags` and `value-cites` each added one entry. The report follows the findings.
- For STALE001 and STALE002, only the paths and names the range removed count. A line already stale at base, for a path or name the range did not touch, never fires. STALE008 judges an added line, and a line the range leaves when the range changed or removed the literal it cites. STALE009 and STALE010 judge only added lines. Each is the PR's own work, so the check is never red on work the PR did not do. STALE009 and STALE010 follow decision `record-cites-live-code` (claims about code cite live code names).
- A path matches only at a path boundary. `mods/session-board/hooks/lib.mjs` does not match `hooks/lib.mjs`.
- Left out: `docs/records.md` (generated at merge), each file `.ste-lint-exclude` names, and a line marked `<!-- ste-disable-line STALE001 -->`, `STALE002`, `STALE003`, `STALE004`, `STALE007`, `STALE008`, `STALE009` or `STALE010`. A record that names a removed file on purpose takes the mark.
- Each Markdown file is read as committed at head, never from the working tree, through the same `git cat-file --batch` process. A byte that is not UTF-8 reads as a replacement character and the file is still checked.
- A base that does not resolve (a shallow clone with no history: the head resolves, the history does not) is unknown, not a finding. The check prints `stale-cites: unknown, ...`, names fetch-depth 0, and exits 0, so a repo that pins the action and checks out shallow is not red at its pin move (owner-lane call, 2026-11-01).
- A read that cannot run is unknown, never clear (rule `verification-report-unknown-reads`). The check prints `stale-cites: UNKNOWN, <the read>` and exits 2 in five cases:
  1. A head that does not resolve. Its `merge-base` or diff fails while the head is absent.
  2. A base that does not resolve in a full clone. Here `merge-base`, or the diff of a two-dot range, fails. The head resolves, the base does not, the clone is not shallow, and the base is not the first parent of a root commit. A `rev-list` of the head, or a `rev-parse` of the base's stem, that exits non-zero counts too.
  3. A diff that fails while the base resolves (an unreadable head blob).
  4. An unreadable `.ste-lint-exclude`. A dangling symlink and a file that is not UTF-8 are unreadable. A missing file means that there are no excludes. The check reads it before the report, so an add-only range fails too.
  5. A `--tree` line anchor whose cited tracked file has no blob.
- The one carve-out is the shallow-base exit 0 in the base bullet above. It covers three cases:
  - A shallow clone.
  - A base that resolves but shares no history with the head (`merge-base` only).
  - The first parent of a head that is a root commit (a first push to the default branch).
- The base is a stem plus a first-parent suffix (`~`, `^`, `~1`, `^1`, a zero-padded `~01` too). The stem, read with `rev-parse`, must be the head's own commit.
  - Passes: `HEAD~1..HEAD`, `HEAD~1..<sha>`, `HEAD~1...<sha>`, `@~1..HEAD`, `HEAD~01..HEAD`.
  - Stays exit 2: `<another root>^1..HEAD`.
- The extra git starts that tell these apart run only after `merge-base` or the diff failed, so a passing run starts none.
- The count is an upper bound, measured with `GIT_TRACE`:
  - Three-dot path (`a...b`, `merge-base` failed): four starts. `rev-parse --verify` of the head, `rev-parse --verify` of the base twice, and `rev-parse --is-shallow-repository`.
  - Two-dot path (`a..b`, the diff failed): three starts. The head, the base once, and `--is-shallow-repository`.
  - A base with a first-parent suffix (`nope^1`) adds one `rev-list --parents` of the head. Its two-dot path starts four, and its three-dot path starts five.
  - Root form of the two-dot path (`HEAD~1..HEAD`, a base that is the first parent of a root head): five starts. Those are the three, plus `rev-list --parents` of the head and `rev-parse --verify` of the stem. Its three-dot form starts six (re-measured with `GIT_TRACE`, 2026-11-07).
  - A head that does not resolve: one start.
- A decision record, or the mechanisms file, that the tree lists but whose blob is missing prints `stale-cites: unknown, <path> ...` and keeps the exit code, as every report line does.
- The tree is listed only when a non-Markdown file changed.
  - A range that changes only `RULE_FILES`, with the mechanisms blob missing (a partial clone), lists no tree. The file reads as absent, so the run prints no unknown and exits 0.
- `FAIL=false` is honored: the findings print and the step exits 0.
- Findings have their own exit path. The STE split script never sees a stale-cites finding (`actions/ste-lint/run.sh`), so each one fails the step unless `FAIL=false`. The split makes an STE finding on an untouched line report-only. STALE001 and STALE002 name lines the range leaves, which is the prose the PR must fix. STALE008 can fire on one too, when the range changed or removed the literal it cites. STALE010 fires on an added line.
- A touched `.py` file that does not parse at base or head is unknown the same way: `stale-cites: unknown, <file> ...`, and it alone keeps the exit 0. So is a cited `.py` file that does not parse at head, and a failed `git log` of STALE010's history read (`stale-cites: unknown, git log --format= failed: <git's message>; a cite into a folder absent at head was not checked`): both keep the exit 0. The five exit-2 reads above exclude them (ruling in the build brief of lane `record-claim-cites-code`, 2026-11-13, process-only, for the failed log).
- Cost, per ste-lint changed-scope run (each PR CI run and each `bin/ste-changed` call): one `python3` start (unmeasured). Git starts 3 (`rev-parse`, `merge-base`, `diff`) when the range removes or renames no path and changes only Markdown outside the rule files, and adds none of: a line in a decision record holding a code verb (a full claim is not needed: "- Run the tests." starts 4), a STALE005 capability verb or route word, a folder `.py` name cite, or a value cite of a code file. It starts 4 when it adds one of them, through one `git cat-file --batch`. A touched `.py` or `.sh` file adds one `git cat-file --batch`, which the name reader and the flag reader share, and, through the report, one `ls-tree`, so it starts 5 (unmeasured). A removed or renamed path adds `ls-tree` and that `cat-file --batch`, so 5 at most. Each tracked Markdown file is read once (unmeasured). It is read only when the findings have something to look for: a removed or renamed path, a name that a touched `.py` file no longer defines, or a flag that a touched `.py` or `.sh` file no longer declares. STALE008 starts at most the one `cat-file`: a Markdown-only range that adds a value cite of a `.py`, `.mjs`, `.js`, `.cjs`, `.ts` or `.sh` file starts 4, and one with no such line starts 3. Every tracked Markdown file is also read when a touched `.py` changed a module-level literal: one that holds a literal at base and, at head, holds a different literal or is gone. A change to or from a call is none. Otherwise it reads only the touched Markdown whose added lines hold such a cite, and a range with no such line reads no blob. The flag reader's read of a parent or helper module adds no start: it uses the `ls-tree` and the one `cat-file --batch` above, and only for a script that lost a flag. A touched `.py` file also loads the py-facts script once, in-process (importlib, no start, no `.pyc`) (unmeasured). It writes no file and starts no lasting process. One more `git log` start runs when an added cite's top folder is absent at head. It runs once per range. `CostTests` and `NameCiteTests` in `lint/test_stale_cites.py` pin these counts.
