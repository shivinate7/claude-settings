# A PR that removes a name also fixes each prose line that names it

## The ruling

The ste-lint CI step refuses a pull request that leaves stale prose of one kind. The kind is a tracked Markdown line that names a repo file or a Python name bound at module level that the same PR deleted, renamed or moved. `lint/stale_cites.py` is the check. `actions/ste-lint/run.sh` runs it in scope `changed`, before the markdown-only exit, so a code-only PR is checked too. Every repo that pins the ste-lint action gets it when its pin moves.

Owner, 2026-11-01 16:30 CST, in chat to triage: "make it a standing thing that stale prose never makes it anymore".

- Codes: STALE001, a path the range removed. STALE002, a name cited as "`file.py` `name`" or "(file.py name)" on one line, bound in that file at base and not at head. A dotted name, such as Class.method, reads its first part as the name. A renamed file counts by its base path and its head path. A bare word after a path is never a cite. Python is read with `ast`. `lint/stale_cites.py` `names_in` walks each module-level statement, also inside a module-level if, try, with, for, while or match, never inside a def or class. In those statements, py-facts `defined_names` (`skills/plain-english-map/scripts/lib/py-facts.py`, the one home) finds each def, class, import and assignment to a plain name. `lint/stale_cites.py` `target_bindings` adds each name in a tuple, list or starred assignment target, a for target, a with-as target and a walrus target. A def directly in a module-level class counts too. A def nested in a function does not. A name that moved but is still bound in the file (`f = h`, a re-import) is not removed. JavaScript and shell names are not checked. A cite of a name in such a file (`.mjs`, `.js`, `.cjs`, `.ts`, `.sh`) that the range touched prints `stale-cites: unknown, <md path>:<line> ...` and keeps the exit 0. It prints only when the range also removes a path or a Python name, since only then is Markdown read. A range that touches only such files prints nothing and passes, with no added git start and no Markdown read. STALE009, a sentence on an added decision-record line that states what code does, with no cite; report only. STALE010, a line the range adds that cites a Python name whose file is absent at head or does not bind it; a finding. Both follow decision `record-cites-live-code` (claims about code cite live code names).
- Scope: built on main are `stale-names-bound` (the removed-name check, STALE002), `value-cites` (the value check, STALE008), the Report below, and the opt-in tree mode (the dead-path check STALE003 and the bad-anchor check STALE004; decision `stale-cites-whole-tree`, the whole-tree record). The planned lanes (`stale-flags` and the records-only lane) follow `docs/plans/pointer-system.md`. The coordinator's picks of 2026-11-03 19:48 CST set their rules: a value cite matches the code as written, Python only, and a JavaScript value reads "unknown". The reverse list (code that nothing in prose cites) is planned, report-only, never a finding, the same form as decision `claude-md-change-is-flagged` (a CLAUDE.md change is reported, never held).
- Report, step L4 of the pointer plan: the check prints report lines after its findings, and the ste-lint step adds them to its summary under "Stale-cites report". A line starts `stale-cites: report, `. It is never a finding and never changes the exit code, the same form as decision `claude-md-change-is-flagged`. Two halves. The anchor half names each `<!-- rule:id -->` anchor whose sentence changed in a rule file (`RULE_FILES` in `lint/rule_audit.py`), with its `lint/rule_mechanisms.json` row (kind, ref, test). Then it lists this PR's changed files under `hooks/`, `lint/`, `bin/`, `actions/` and `.github/`, or "none". It gives no verdict on whether the guard or check changed. A guard row's logic can sit in any module, so the reviewer judges (orchestrator ruling, process-only, 2026-11-03 20:35 CST). The Home half names each changed non-Markdown file (added, changed, removed or renamed), the decisions whose Home line names it, and the rows whose ref or test is it. Only a real anchor counts: an anchor inside a code span is a mention, never named. A repo with no `lint/rule_mechanisms.json` gets the Home half only, with no error. Named readers: the lane reviewer, who checks that the guard or check behind an edited rule changed with it, and the batch runner, who reads the summary before a merge.
- Report cost: the report adds one `ls-tree` of the decisions folders and the mechanisms file when a non-Markdown file changed. It adds none when the run already listed the whole tree. The decisions folder is the first of `candidates(root, "decisions")` in `lint/layout.py` that holds a file, so a repo not rolled out to the layout is read at `decisions/` or `docs/decisions/`. It also adds one `git cat-file --batch`. That batch reads each decision record whole (a regex takes its Home line) and the mechanisms file once. A changed rule file adds its base and head blobs and the mechanisms file. Its list of changed files comes from the diff the run already read, so an edit to a rule file alone starts 4 git processes (`rev-parse`, `merge-base`, `diff`, `cat-file --batch`). A PR that changes only Markdown outside the rule files adds nothing. A `lint/rule_mechanisms.json` that is not JSON, or whose rules or rows are not objects, prints one `stale-cites: unknown, ...` line naming the file, and the Home half still prints without rows. Any other failed report read prints one `stale-cites: unknown, report not read, ...` line. The exit stays as it was.
- STALE008, a value cite: one backtick span `file.py: NAME = literal`, the cite grammar of MAP9 (`VALUE_CITE_RE` in `skills/plain-english-map/scripts/map-check.mjs`). The grammar is copied into `lint/stale_cites.py` because the ste-lint action runs Python only; `skills/plain-english-map/tests/value-cite-parity.json` holds the copies together, and both suites read it. A span with no file is no cite here. It fires in three cases only. The range changed the module-level literal and the cite still equals the base value. The range removed the assignment and the cite equals the base value. Or the range added the line and the cite is not the value at head, even when no literal changed. Lines are counted, not looked up: a second copy of a line already wrong at base is an added line, and a line the range only moved is not. A line already wrong at base and left alone never fires. A value is the module-level literal that py-facts `answer` reads (`ast.literal_eval` accepts it and JSON can hold it), compared by value. A head value that is no literal, such as a call, gives no finding. A cite of a `.mjs`, `.js`, `.cjs`, `.ts` or `.sh` value prints `stale-cites: unknown` on an added line always, and on an untouched line only when the whole tree is read and the range touched that file. A JSON value is not read. A `.py` cite the check cannot read is never skipped. On an added line, a value that is no JSON literal (MAP9 reads none) or a path no tracked file has is a finding. A name that holds no literal at head, or a file that does not parse, is unknown. An untouched line prints each of these as unknown, only when the whole tree is read. A cite of a path the range removed is STALE001's. Fenced blocks count as prose. A mark `<!-- ste-disable-line STALE008 -->` leaves a line out, its unknown too.
- Coordinator pick, 2026-11-07 13:32 CST, process-only: a `.mjs` value cite on an added line prints unknown too, not only on a whole-tree read.
- Coordinator pick, 2026-11-07 13:32 CST, process-only: a cite whose head value is no literal prints unknown, never a finding.
- Readers: `scan()` runs a list of readers (`READERS` in `lint/stale_cites.py`), one per check. The later lane `stale-flags` adds one entry. The report follows the findings.
- For STALE001 and STALE002, only the paths and names the range removed count. A line already stale at base, for a path or name the range did not touch, never fires. STALE008 judges an added line, and a line the range leaves when the range changed or removed the literal it cites. STALE009 and STALE010 judge only added lines. Each is the PR's own work, so the check is never red on work the PR did not do. STALE009 and STALE010 follow decision `record-cites-live-code` (claims about code cite live code names).
- A path matches only at a path boundary. `mods/session-board/hooks/lib.mjs` does not match `hooks/lib.mjs`.
- Behaviour change, three parts. First: a cite path is normalized (`./` and inner `..`) before STALE001 and STALE002 match it (`lint/stale_cites.py` `cite_path`). So `./lint/x.py` matches a deleted `lint/x.py`. Second: a cite path led by `..`, `~` or `/` in a STALE005 backing or a STALE008 value cite now gives one unknown line (`lint/stale_cites.py` `outside_repo`). Before, `~` and `/` gave a finding for STALE008 and a dead-backing report for STALE005, and `..` stopped the run. Third: STALE002 also reads a cite to the new path of a renamed file (`lint/stale_cites.py` `NameReader`). A cite `new.py gone`, where the range renamed `old.py` to `new.py` and dropped `gone`, now fails, on a line the range left too. It fires even when the line was already dead at base, since the cited file did not exist there. <!-- ste-disable-line STALE003 -->
- Left out: `docs/records.md` (generated at merge), each file `.ste-lint-exclude` names, and a line marked `<!-- ste-disable-line STALE001 -->`, `STALE002`, `STALE008`, `STALE009` or `STALE010`. A record that names a removed file on purpose takes the mark.
- Each Markdown file is read as committed at head, never from the working tree, through the same `git cat-file --batch` process. A byte that is not UTF-8 reads as a replacement character and the file is still checked.
- A base that does not resolve (a shallow clone with no history: the head resolves, the history does not) is unknown, not a finding. The check prints `stale-cites: unknown, ...`, names fetch-depth 0, and exits 0, so a repo that pins the action and checks out shallow is not red at its pin move (owner-lane call, 2026-11-01).
- A read that cannot run is unknown, never clear (rule `verification-report-unknown-reads`). The check prints `stale-cites: UNKNOWN, <the read>` and exits 2 in five cases. The first is a head that does not resolve (its `merge-base` or diff fails while the head is absent). The second is a base that does not resolve in a full clone. Here `merge-base`, or the diff of a two-dot range, fails. The head resolves, the base does not, the clone is not shallow, and the base is not the parent of a root commit. The third is a diff that fails while the base resolves (an unreadable head blob). The fourth is an unreadable `.ste-lint-exclude`: a dangling symlink and a file that is not UTF-8 are unreadable, and a missing file means that there are no excludes. The check reads it before the report, so an add-only range fails too. The fifth is a `--tree` line anchor whose cited tracked file has no blob. The shallow-base exit 0 above is the one carve-out: it covers a shallow clone, a base that resolves but shares no history with the head (`merge-base` only), and `<head>~1` where the head is a root commit (a first push to the default branch). The extra git starts that tell these apart run only after `merge-base` or the diff failed, so a passing run starts none. A failing base path starts four: `rev-parse --verify` of the head, `rev-parse --verify` of the base twice, and `rev-parse --is-shallow-repository` (traced with `GIT_TRACE`). A `<head>~1` base of a root commit in a full clone adds a fifth, `rev-list`. A head that does not resolve starts one. A decision record, or the mechanisms file, that the tree lists but whose blob is missing prints `stale-cites: unknown, <path> ...` and keeps the exit code, as every report line does. The tree is listed only when a non-Markdown file changed. A range that changes only `RULE_FILES`, with the mechanisms blob missing (a partial clone), lists no tree. The file reads as absent, so the run prints no unknown and exits 0.
- `FAIL=false` is honored: the findings print and the step exits 0.
- Findings have their own exit path. The STE split script never sees a stale-cites finding (`actions/ste-lint/run.sh`), so each one fails the step unless `FAIL=false`. The split makes an STE finding on an untouched line report-only. STALE001 and STALE002 name lines the range leaves, which is the prose the PR must fix. STALE008 can fire on one too, when the range changed or removed the literal it cites.
- A touched `.py` file that does not parse at base or head is unknown the same way: `stale-cites: unknown, <file> ...`, and it alone keeps the exit 0.
- Cost, per ste-lint changed-scope run (each PR CI run and each `bin/ste-changed` call): one `python3` start. Git starts 3 (`rev-parse`, `merge-base`, `diff`) when the range removes or renames no path, changes only Markdown outside the rule files, and adds none of: a line in a decision record holding a code verb (a full claim is not needed: "- Run the tests." starts 4), a STALE005 capability verb or route word, a folder `.py` name cite (not one led by `..`, `~` or `/`), or a value cite of a `.py`, `.mjs`, `.js`, `.cjs`, `.ts` or `.sh` file (a JSON value is not read). It starts 4 when it adds one of them, through one `git cat-file --batch`. A touched `.py` file adds one `git cat-file --batch` and, through the report, one `ls-tree`, so it starts 5. A removed or renamed path adds `ls-tree` and that `cat-file --batch`, so 5 at most. Each tracked Markdown file is read once. It is read only when the findings have something to look for: a removed or renamed path, or a name that a touched `.py` file no longer defines. STALE008 starts at most the one `cat-file`. It reads every tracked `.md` only when a touched `.py` changed a module-level literal, and otherwise only the touched `.md` whose added lines hold a value cite. Every tracked Markdown file is also read when a touched `.py` changed a module-level literal: one that holds a literal at base and, at head, holds a different literal or is gone. A change to or from a call is none. Otherwise it reads only the touched Markdown whose added lines hold such a cite, and a range with no such line reads no blob. A touched `.py` file also loads the py-facts script once, in-process (importlib, no start, no `.pyc`). It writes no file and starts no lasting process. `CostTests` and `NameCiteTests` in `lint/test_stale_cites.py` pin these counts.
- An opt-in whole-tree mode is in stale-cites-whole-tree. The range check here is unchanged.
