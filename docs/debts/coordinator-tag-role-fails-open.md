# Coordinator role fails open when the transcript holds no own tag or record

- **What.** Nothing writes a coordinator role file: `MERGE_ROLES` holds only `batch-runner`, and the coordinator runs no `--role` call. So a coordinator's role comes only from its own `cs-build` tag in the transcript: the newest `get_session` result for its own id, plus the tags its own later `set_session_tags` calls added. A coordinator whose transcript holds neither, as after `/clear`, reads as no role, and rule `coordinator-scope` never fires for it. The case `coordinator-scope: with no own record and no own tag call, the role is not held, so the write is allowed (/clear gap)` pins that.
- **Where.** `_own_tag_role` and `_cloud_coordinator` in `hooks/guard.py`; `own_session_read` with `applied` in `hooks/own_session.py`; `MERGE_ROLES` in `hooks/shared_names.py`. The session-start line tells a session to read its own record with `get_session`, but it does not say a coordinator must do it again after `/clear`.
- **Decision.** `session-tiers` (the session roles and their role guards, section Role guards).
- **Retire.** A coordinator's session role holds from its first judged call, with no tag call and no `get_session` result in the transcript. Or its start steps run `get_session` first, and a case proves the rule fires then. `hooks/test_guard.py` (family `coordinator-scope`) holds that case, and the `/clear` case above is re-pointed to deny.
