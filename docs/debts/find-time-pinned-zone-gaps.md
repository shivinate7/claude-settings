# Time finder misses some real date and zone reads

- **What.** `lint/find_time_pinned.py` lists a date or zone read only when no time is given. A local-zone read of a fixed time still depends on the machine's zone, and the finder passes it: Python `time.localtime(EPOCH)`, `time.ctime(EPOCH)`, `datetime.fromtimestamp(<fixed>)`, `.astimezone()`, `time.altzone`, `time.daylight`; JS getters on a fixed date, such as `new Date(2026, 2, 8, 12).getTimezoneOffset()` or `new Date("2024-01-01").getDate()`. It also misses a clock fed through another call or name: `time.localtime(time.time())`, `datetime.fromtimestamp(time.time())`, `new Date(a)` after a plain `a = Date.now()` with no `const`, `let` or `var`, `new Date(fmt(Date.now()))`, a bare `new Date;`, and Intl `timeZone` reads. Date libraries outside the listed set pass too: luxon `DateTime.now()` and `DateTime.local()`, date-fns `startOfToday()`, `arrow.Arrow.utcnow()`, `pd.Timestamp("now")` and `dateutil` `tz.tzlocal()`. The Swift scan has no calendar category: `Date()`, `Calendar.current` and `TimeZone.current` pass, and a `Date()` in an assert is listed only as elapsed-assert. Claude writes these forms in normal tests (`hooks/test_guard.py`, `hooks/test_decision_watch.py` hold fixed-time zone reads). `lint/test_find_time_pinned.py` pins `time.localtime(EPOCH)` and `time.ctime(EPOCH)` as clean today.
- **Where.** `lint/find_time_pinned.py` (`PY_CALENDAR_NOW`, the calendar scan, the Swift scan) and `lint/test_find_time_pinned.py`.
- **Decision.** `test-practices` (P5: an assert never reads the real date or zone).
- **Retire.** The finder lists each form above as calendar, the fixed-time zone cases move from clean to listed, and a red case for each shows it.
