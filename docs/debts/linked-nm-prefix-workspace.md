# A root install writes through a member's own linked node_modules

- **What.** An `npm install` or `npm ci` run in a workspace root whose `node_modules` is a real folder also reifies each member's own `node_modules`, and removes from it every entry the lock lacks. A member whose `node_modules` is a link then loses packages in the link's target (npm 10.9.9 printed "removed 2 packages"). The `linked-node-modules` rule allows that from the root, because from the root it judges only the root's folder. From a member, the rule now judges the member's own link as well as the root's (`install`, after `npm_walk` reaches a root from a member). `-w` and `--workspace` do not move the prefix: `npm prefix --workspace=a` run in a member prints the root, and `npm prefix -w a` run in the root errors, because `prefix` does not support workspaces (npm 10.9.9). So `npm ci -w a` from a linked root, and `npm ci --workspace=a` from a member, are refused. `--no-workspaces` stops the walk at the member (`npm_walk`, read by `npm_prefix_flag`). Accepted known limit: from the root, the guard would have to list every member and read each one's link.
- **Where.** The `install` judge in the `linked-node-modules` rule, `hooks/guard_push_delete.py`.
- **Decision.** `guard-linked-node-modules` (refuse an install or recursive delete through a linked node_modules).
- **Retire.** If a real incident shows the limit hit, judge each workspace member's `node_modules` link on an install run in the root. The member-cwd and root-cwd cases are in `tests/guard/s10425-linked-node-modules.py`; no test covers `-w` on install.
