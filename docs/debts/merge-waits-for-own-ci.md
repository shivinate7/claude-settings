# Merge proof can lag the head's own CI

- **What.** The merge tool can merge a PR before the PR head's own required CI run finishes, on a proof that checks less than CI does. The consultant merged PRs 3799, 3805 and 3806 on the merge tool's ready checks, which are not the lane-lint, before their own PR CI finished (timing from the session report; not re-read from CI). Main then went red with five causes: guard fixtures, a refusal text that named guard.py, the brief word cap, shellcheck SC2010 in `merge/test_install_from_main.sh`, and the compliance shoot-config regex. PR 3811 fixed them. Harm: a red main blocks every lane.
- **Where.** `merge/merge.py`, the ready check for a pending head (lines 37-40), which accepts a lane-lint PASS for a head whose run is still pending. `pending_lifted` (line 1222) records a lint PASS that lifted a pending run, and a carried proof under a heal commit (PR 3820, proof carries over heal): the head's own pending run then goes on to the PUT too.
- **Decision.** `merge-needs-current-base` (rule M3). Its pending clause came from owner ruling `own-merge-on-lint-pass` (2026-11-15 18:21 CST). The Lane draft PR grant in `.claude/CLAUDE.md` (owner, 2026-11-12 17:19 CST, changed 2026-11-20 13:06 CST) also lets the first proof of a head merge it. Both are owner rulings, and they stand.
- **Fix idea.** The lint-pass proof runs the suites that the diff touches (for example the guard fixture shards when `hooks/` changes), so a lint PASS proves what CI would. The fix keeps both rulings.
- **Owner.** Changing which proof may merge needs the owner.
- **Retire.** Close when a lint PASS on a diff that touches a suite is refused unless that suite ran, and a case in `merge/test_merge.py` pins the refusal.
