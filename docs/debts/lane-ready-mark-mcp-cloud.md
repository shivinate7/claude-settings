# A cloud lane cannot mark its own pull request ready

**What.** In cloud, `merge <pr> --ready --role lane --step <step>` passes the ready checks, then points at the MCP call `update_pull_request` with `draft=false` (route `pr-ready-mcp-cloud`), because the tool sends no GraphQL. The guard rule `merge-role-proof` refuses that MCP call for a session whose own record is a lane's ("Any other ready mark waits for the batch runner"). The tool and the guard point at each other, so the lane waits for the batch runner. Seen in lane `stable-refresh-mid-session` (PR #3550), relayed by the coordinator at 11:16 CST Nov 17; the lane's own words were not read. Triage marked PR #3618 ready by the same MCP call at 10:42 CST Nov 17 and it passed (step source, not re-read). Cost so far: one lane waited.

**Where.** `hooks/guard_merge.py`: `lane_mcp_ready_hit` refuses every `draft=false` update from a lane's record in cloud, for any pull request, with `LANE_READY_REASON`; `lane_ready_hit` lets the merge tool's own ready flag through for the lane's own step (`_lane_ready_own_pr`). The call site is the `mcp__github__update_pull_request` branch in `hooks/guard.py`. `merge/merge.py`: `READY_ROUTES` and `Host.ready`, which sends no GraphQL and marks nothing. Guard test family `lane-may-mark-ready` in `hooks/test_guard.py`.

**Decision.** `draft-until-reviewed` (ruling Q2: a lane marks its own PR ready once, with the merge tool's ready flag; state: live). `lane-may-mark-ready` is the name the lane and the step give as the decision, but main holds no decision file of that slug: it is the guard test family above. Decision `records-index-at-merge` step two says "the runner marks the PR ready by its session's route", which names the runner, not the lane. The guard's own reason cites `session-tiers` (a session's role decides which merge acts it may run).

**Retire.** The route the tool prints and the guard agree for a cloud lane. If the guard changes: cases in `hooks/test_guard.py`, red first on the current code, show a lane's `draft=false` update on its own step's pull request passing in cloud, and the same update on another pull request staying refused. If the tool's text changes instead: a case in `merge/test_merge.py`, which already pins `route pr-ready-mcp-cloud`, pins the new route.
