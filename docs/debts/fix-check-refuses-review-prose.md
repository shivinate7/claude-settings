# The fix-check refusal does not name prose below a review log's CI line

**What.** `merge --review-record --fix-check` refuses to chain from the newest review log on a pull request when that log has a prose line below the line `CI: read live by merge --reviewed`. The refusal says the reviewed head must be the Head of the newest earlier review log. It never names the prose. Source: the consultant's relay, not verified by triage. Pull request #3474's comment 6910116455, with prose, was refused. The same lines without prose, in comment 6910690439, chained. Pull request #3574 hit it too.

**Where.** `merge/merge.py`, two sites. `parse_review` returns None when the record does not end at its CI line before the `---` line. In `--review-record`, the `--fix-check` chain keeps that None as the newest earlier log, so `earlier[-1]` is None and the head test fails. The restart check (`earlier_top`) and the design-line check (`last_design_line`) skip the same log as no record. Read here, not tested.

**Decision.** `pr-review-record` (a review log names the head it reviewed, and only an open pull request takes one). Its form ends a record at the CI line, and its `--fix-check` rule reads the newest earlier record.

**Retire.** `merge/test_merge.py` does not yet hold this case. Add it: a newest review log with one prose line below the CI line, then `--review-record --fix-check` from that log's Head. It asserts that the refusal names the prose line. Today's refusal names no prose. `parse_review` still returns None for that log, as test_a_note_line_after_a_blank_line_below_the_ci_line_is_not_a_record pins. The parser route, reading record lines only, would change that pinned test and decision `pr-review-record`, so it needs the owner's grant first. The case is red on today's code and green after the fix.
