# The comment narration check misses some history wording and flags some legit lines

**What.** The check has no suppression marker. It flags these legit lines. It flags "formerly" in domain text, such as "Columns formerly named amt are still read". It flags "changed from a draft to a shipped state". It flags "Previously used tokens are rejected" at a sentence start. It flags "Rows added after review stay pending". It also flags "the old behaviour" before an irregular participle, such as "used by callers". The history phrase pattern names fixed word forms, so it misses other history wording. It misses "previously" inside a sentence. It misses "Changed from list to set". It misses "Added in response to review". It misses "This used to return None". It misses "the old behaviour" before a past verb with by, for, on, in, at, with or from after it, such as "failed on". It misses a dated history line after until, effective, valid or expires, such as "Until 2026-10-30 this returned None". It also passes history whose noun is snapshot or run, such as "changed from the old snapshot format to JSON". A moved block shows as added. An unreadable file does not stop the scan. The other files are read, their hits print, and the run exits 2 as unknown. The JS, TS and Astro part needs npx and the registry, or tsc on PATH. Without them the run exits 3, and code-check goes red. This holds even for a change that only deletes JS lines, since the file is listed before its hunks are read. No test pins a node per-file error row. No test pins the Astro attribute-expression, is:inline, typed script or void-tag cases. The probes pass. New vendored code in a pinning repo cannot be cleared. The exclude list may only shrink. The shell reader, `shell_comments`, has no parser. So it misses a comment inside the expansions of an unquoted heredoc body. A `<<` shift outside `((`, `$((` and `a[...]`, such as `let x=1<<2`, reads as a heredoc and exits 2. In `ls x[ ; cat <<EOF` the lone `[` opens a subscript. So the heredoc body reads as code and may exit 2. After `[[ (a)]] && ...`, a later `(b)#c` on the same line misses its comment. Inside the gloss of a real `round-N` decision id, a round number with the same N passes whatever wording surrounds it. An example is "(decision hold-unsafe-after-round-3, fixed after round 3)". The phrase "review round" and the other patterns still flag inside the gloss. zsh files are not scanned. A `case` after `time -p` or `coproc` reads as a plain word. So its `esac` has no case, and the file exits 2. A `#` after `|`, or a space inside an extglob or regex group, opens a comment, such as in `^(a|#b)`. The rest of the line is skipped. Inside `$(...)` the file exits 2. An id after an example word is skipped unless its clause has a past-tense history verb right after an id, or "in main" before the id. So "i.e. 41ddef83 reverted the guard", "reverted in main, i.e. 41ddef83", "Keys are kept in main, i.e. 41ddef83" and "works like 41ddef83" or "behaved like 41ddef83" hit. A history cite in other words still passes after an example word. A past or passive verb outside the list passes, such as "e.g. 41ddef83 changed the guard", "moved", "dropped", "rolled back" or "superseded". A verb before the id passes unless "in main" stands before it, and "since" before the id never flags, so "changed since the rewrite, i.e. 41ddef83" passes. A verb not right after the id passes too, such as "e.g. 41ddef83, which reverted the guard". A cite such as "e.g. 41ddef83 came after the rewrite" or "i.e. 41ddef83 undid the guard" passes. The clause ends at each comment line, so "# Ids such as 41ddef83, which" followed by "# reverted the old check." passes. The verb list is fixed, so a verb outside it misses. A listed history verb right after an id flags even as a plain participle. That is a rare false alarm. "Ids like 41ddef83 added by hand are rejected", "Ids such as 41ddef83 removed from the list stay gone" and "e.g. 41ddef83 cut off at 8 chars" all flag. "in main" before the id also matches a function name. That is a rare false alarm. "Set in main(), e.g. 41ddef83" flags. A "like" after a verb the check does not list still counts as an example word, so the id after it is skipped. "was like 41ddef83", "it is like 41ddef83" and "behaves just like 41ddef83" pass. origin/main flags all three. That is a miss. The harm is history in a comment, which rule building-comments-say-why forbids, or one wrong flag on example text. It is low.

**Where.** `lint/check_comment_narration.py`, also run by `actions/code-check` in every pinning repo.

**Decision.** `none`.

**Retire.** Add a case to `lint/test_check_comment_narration.py` for each missed phrase and each flagged legit line in What. Each case is red on the current check and green once the check handles it.
