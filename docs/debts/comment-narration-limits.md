# The comment narration check misses some history wording and flags some legit lines

**What.** The check has no suppression marker. It flags these legit lines. It flags "formerly" in domain text, such as "Columns formerly named amt are still read". It flags "changed from a draft to a shipped state". It flags "Previously used tokens are rejected" at a sentence start. It flags "Rows added after review stay pending". It also flags "the old behaviour" before an irregular participle, such as "used by callers". The history phrase pattern names fixed word forms, so it misses other history wording. It misses "previously" inside a sentence. It misses "Changed from list to set". It misses "Added in response to review". It misses "This used to return None". It misses "the old behaviour" before a past verb with by, for, on, in, at, with or from after it, such as "failed on". It misses a dated history line after until, effective, valid or expires, such as "Until 2026-10-30 this returned None". It also passes history whose noun is snapshot or run, such as "changed from the old snapshot format to JSON". A moved block shows as added. An unreadable file does not stop the scan. The other files are read, their hits print, and the run exits 2 as unknown. The JS, TS and Astro part needs npx and the registry, or tsc on PATH. Without them the run exits 3, and code-check goes red. This holds even for a change that only deletes JS lines, since the file is listed before its hunks are read. No test pins a node per-file error row. No test pins the Astro attribute-expression, is:inline, typed script or void-tag cases. The probes pass. New vendored code in a pinning repo cannot be cleared. The exclude list may only shrink. The shell reader, `shell_comments`, has no parser. So it misses a comment inside the expansions of an unquoted heredoc body. A `<<` shift outside `((`, `$((` and `a[...]`, such as `let x=1<<2`, reads as a heredoc and exits 2. In `ls x[ ; cat <<EOF` the lone `[` opens a subscript. So the heredoc body reads as code and may exit 2. After `[[ (a)]] && ...`, a later `(b)#c` on the same line misses its comment. Inside the gloss of a real `round-N` decision id, a round number with the same N passes whatever wording surrounds it. An example is "(decision hold-unsafe-after-round-3, fixed after round 3)". The phrase "review round" and the other patterns still flag inside the gloss. zsh files are not scanned. A `case` after `time -p` or `coproc` reads as a plain word. So its `esac` has no case, and the file exits 2. A `#` after `|`, or a space inside an extglob or regex group, opens a comment, such as in `^(a|#b)`. The rest of the line is skipped. Inside `$(...)` the file exits 2. The ids in these examples are made up. They are shaped like commit hashes. It flags a line with a hex id. After branch cull-narration-hex-id merges, a history cite right after an example marker is not flagged, such as "works like 41ddef83" or "i.e. 41ddef83 reverted the guard". The example markers are `like`, `i.e.`, `e.g.`, `for example`, `for instance` and `such as`. A real cite after any of them is skipped too. The example marker skips the id whatever the sentence says. The list join skips every later id of a comma, "and" or "or" list after an example marker, such as "e.g. 41ddef83, 03d62e85, 9f8e7d6c, aa11bb22 reverted in main". That line has four ids and zero hits. After branch cull-narration-hex-id merges, the speed cases in `lint/test_check_comment_narration.py` (`ExampleIds.BOUND`) use a 10 s hang bound, not a speed measurement. The old per-id scan still passes the 4000-id case, at about 7 s (6.8 to 9 s across runs). A larger list would catch the old scan. Its cost to the test run is unmeasured. The harm is history in a comment, which rule building-comments-say-why (comments say why, no history) forbids. It is low.
