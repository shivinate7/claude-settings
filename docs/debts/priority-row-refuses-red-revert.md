# The priority check refuses the red-main revert

- **What.** The priority check has no exit for `--base-red-ok`. On a red main, the revert that fixes main is refused while a row reads ok. The probe ran `merge 3314 --confirm --base-red-ok "revert" --priority-rows F`, with pull request 3314 standing in for the revert, and the row for pull request 3302 (row slug `ci-speed-stack-4`) reading ok. The check refused with "ready. Merge it first." Pull request 3302 cannot merge onto a red main, so the only way past the refusal is to omit the flag. The project-ops templates tell the runner to pass `--priority-rows` on every confirm, so this is likely to be hit. Breaks rule `verification-recovery-independent-of-state` (a recovery control must not depend on the state it recovers) and the red-main rule `git-red-main-reverts` (a red main reverts the blamed lane first). Found by a round-3 reviewer's probe on a scratch copy, recorded 2026-11-14 00:19 CST.
- **Where.** `merge/merge.py`, `priority_gate`, called in the flow's `a.confirm and not info["draft"]` branch (line 4873). The function takes no red-main argument, so `--base-red-ok` never reaches it.
- **Decision.** `priority-vs-merge-order` (a ready priority row goes before a lower pull request). Its ruling says the refusal names no flag that lifts it. The fix adds one, so rewrite that sentence in place when this closes.
- **Retire.** The check stands aside when `--base-red-ok` is given, for a red-main revert. A red-first case in `merge/test_priority_vs_merge_order.py` covers it: merge 3314 with `--base-red-ok "revert"` and an ok row for 3302 expects the merge to go on, and fails on the current code.
