The pick

One test decides each row: does the tool catch bugs Claude is likely to write, at a cost a lane will not feel? A type checker passes that test because it finds wrong code, not ugly code. A style linter or a formatter does not pass it, because it adds noise and no correctness.

The step is small: one new tool (mypy), wider use of four that exist (Ruff, tsc, ShellCheck and the Swift 6 compiler), and two config changes (joyous, ios-adblock). Formatters follow later, after o2. Style linters stay skipped.

How it lands

  1. One home in claude-settings. A shared composite action, actions/code-check, with pinned versions of each tool. A repo calls it from CI the same way it calls ste-lint today. This is the same idea as c76, where a repo's CI runs the same claude-settings tools as a local session.

  2. CI only, never on each edit. This follows c21. No hook runs a type checker on each edit.

  3. A strict list that only grows. Each repo keeps a list of files or folders that pass strict checks. CI fails a listed file that regresses. A lane adds a file to the list when it touches that file. Nobody fixes a whole repo in one sweep.

  4. Order. claude-settings first (162 Python files, and its guard code has the highest stakes). Then the two config fixes, joyous and ios-adblock. Then mypy in banchi, starting with store/orders.py and codes/qr.py, as its debt 061 asks. Then degen. q_max's checkJs goes last.

  5. Portability: yes. Each repo that has a language in the table gets its row. The roll-out to another repo waits for your word, because this project does not push to the other repos.
