Bottom line

Yes, there is real merit, and the biggest win isn't a new feature you're missing. It's that the native features now hold a lot of what your system builds by hand, so most of your effort could move from policing the process to running it.

You built the right ideas: roles, one checkout per worker, red-then-green proof, a review cap, a merge tool, an advisor. Claude has since shipped most of the plumbing those ideas need. What it hasn't shipped is your judgement layer (the guard, the records discipline, the merge-time record stamp). Keep that, and stop maintaining the plumbing.

The three moves that matter most:

  1. Turn your lane process into a saved Workflow. Builder, reviewer rounds 1 to 3, the Opus third try, the batch PR: today that lives as about 106 lines of CLAUDE.md, enforced by prompt-hook judges that check whether the orchestrator obeyed. A workflow script is the process, so it can't be disobeyed and doesn't need a judge.

  2. Use projects and threads as the orchestrator layer. The coordinator plus threads already does what your advisor session, session-board, per-lane orchestrators, handoff files and CI-wake hook were built for, and it keeps running with your Mac off.

  3. Ship claude-settings as a plugin and cut the guard down. Plugins can now carry hooks, agents, skills, output styles, bin/ tools and saved workflows. That kills most of install.sh/install.ps1 and their ~2,700 lines of tests. Then cull guard rules that mostly guard your own orchestration rules rather than real damage.

Side question: yes, project threads can change code, push branches and open PRs. This thread has all seven of your repos cloned and could open a PR now. One catch, covered under Gaps: this project's cloud environment doesn't run your claude-settings installer, so none of your hooks or guard rules apply to threads here today.

Keep

These have no native equivalent, and they are the parts that actually protect your repos and your phone's DNS.

  • The merge tool. Claiming record numbers at merge time, the lock and the revert-on-refusal are yours alone. GitHub's merge queue could take over the CI wait later, but not the claim.

  • Records and their checks. One file per ruling, slug-then-stamp, rule_audit, the STE lint. This is the memory that survives every session, and projects don't replace it. Project memory is off here anyway.

  • The guard's damage rules. Kill by pid, frozen paths, git location variables, rm on a variable, push-delete, worktree home. These stop real loss and run in every session.

  • The override pass. A clean, logged way to lift a refusal. Nothing native does this.

  • Your Mac-only tools. ios-ship, the one-simulator rule, the disk floor, the load brake. Threads run in the cloud, so these stay local and get reached through Remote Control.

  • Your rules as ideas. Red-then-green, one checkout per worker, three review rounds, "a guard that cries wolf is spent". These are good. The point below is where they live, not whether they're right.

Replace

These are plumbing that a built-in now does, often better, and each one you drop is code you stop testing.

  • Advisor session → project coordinator. Your advisor holds the plan and fields questions so sessions don't stall on you. That is exactly what the coordinator does here, without a junctioned sessions folder or a ListAgents naming rule.

  • Per-lane orchestrators, session-board, feedback inbox → threads. A thread per lane gives each its own context, title, checklist and "needs you" state. A new ask in the project chat becomes its own thread, so a burst of feedback can't get lost, which is the incident the inbox was built for.

  • CI wake → PR subscriptions. A thread that opens a PR subscribes to it and is woken by CI results, reviews and the merge. No PostToolUse hook parsing gh output.

  • Most of the handoff machinery. It exists because one long session compacts and forgets. Short threads with records on main rarely reach compaction. Keep a small version for long local sessions; drop the clear/fork pointers, re-read flags and checkpoint nudges once you work mostly in threads.

  • Installers → a plugin. Your 2026-09-28 decline (adoptions-declined-2026-09-28) said a plugin can't ship CLAUDE.md or permissions and cloud sessions don't load user plugins. The first half still holds: plugin settings.json only honours agent and subagentStatusLine. But a plugin now ships hooks, agents, skills, output styles, bin/ and workflows, which is most of what the installer lands. CLAUDE.md, env vars and permissions could come from a 20-line setup script instead of ~1,400 lines of installer plus ~2,700 lines of installer tests. Whether a repo's .claude/settings.json enabledPlugins loads in cloud sessions is the reopen condition; I didn't test it, so treat it as unmeasured.

  • Vendored skill copies. degen and ios-adblock each carry a copy of impeccable. Install it once from your marketplace.

Supercharge

This is where the built-ins multiply what you have, rather than just replacing it.

1. Your lane process as a saved Workflow. Write one workflow, say lane, that takes a brief and runs: test-author (red proof) → builder in a worktree → reviewer round 1 on Haiku → fix → round 2 on Sonnet → try 3 on Opus if round 2 fails → round 3 with the net-value test → draft PR. A second one, batch, merges passing lanes into the integration branch and runs your merge tool. What you gain:

  • The review cap, the model per role and "each layer proves once" become code paths. You can delete the Agent and SendMessage prompt judges for lane work, and most of subagent-model-cap's guard rules, because the script sets each model.

  • It's rerunnable and resumable: a failed run resumes with finished agents cached.

  • /workflows shows phase and progress, which covers the pace numbers your reports compute by hand.

  • Plugins can ship workflows, so every repo gets the same lane from claude-settings.

2. Projects as the top layer, workflows underneath. Use the project chat as your one place to talk. Each workstream (a degen objective, a home-app lane, a claude-settings change) is a thread. Each thread runs your lane workflow for its builds. You get your two-tier parallelism (lanes, then orchestrators per workstream) with no hand-built coordination, and it runs with your Mac asleep.

3. Remote Control for Mac-only steps. A cloud thread can start a session on your Mac for ios-ship, make native-check, the simulator check or HA work on your LAN. Your Mac-only rules then apply only to the step that needs them.

4. Scheduled tasks for the things you run by hand. The weekly guard-log read (guard-log-read-weekly), the rule cull, the janitor sweep and Renovate follow-ups fit a cloud scheduled task or a desktop scheduled task. That respects your "no timers inside a session" rule because it runs as its own session.

5. Guard rules tested against the built-ins first. Before writing a new guard rule, check whether a permissions deny rule, sandbox, or the auto mode classifier already stops it. Your building-guard-needs-incident rule says this in spirit. Adding "and no built-in covers it" would likely trim some of the 2,291 lines in guard.py.

Gaps and caveats

  • This project runs without your guard today. I checked this thread's container: no ~/.claude/hooks, no ~/.claude/settings.json, and CLAUDE_CODE_SUBAGENT_MODEL is unset. The environment's setup script doesn't run your install.sh --cloud. Threads here see each repo's CLAUDE.md (because the repos are cloned) but none of the hooks, roles, model cap or output style. If you want threads to work under your rules, add the one-line setup script from your README to this project's environment first.

  • Threads are cloud machines. Anything that needs your Mac (Xcode, the simulator, HA on your LAN, AdGuard) needs Remote Control, and the thread's folder access turns off while it runs.

  • Workflows cost tokens in bursts. A lane run spawns several agents. Your Haiku/Sonnet role table keeps that sane, but expect each run to cost more than a single-session build.

  • Agent teams are still experimental and don't isolate teammates in worktrees, so they're a worse fit than workflows for your one-checkout-per-worker rule.

  • Not verified here: whether repo-level enabledPlugins loads your marketplace plugins in cloud sessions, and whether every hook event your guard uses fires the same way in project threads. Both are one quick test each before you commit to the plugin route.

Suggested order

Each step is small, reversible and proves the next one is worth doing.

  1. Add your setup script to this project's cloud environment, so threads run under your guard and roles.

  2. Test one thing: does a repo's enabledPlugins load the claude-settings marketplace plugins in a cloud thread? That decides the plugin route.

  3. Write the lane workflow in claude-settings and run it on one real degen or home-app lane, next to the current hand-run process. Compare cost, wall-clock and review findings.

  4. If it holds up, delete the lane rules from CLAUDE.md and the Agent/SendMessage prompt judges, and point the rules at the workflow.

  5. Move to threads as the default: retire the advisor session and session-board, and shrink the handoff and inbox hooks.

  6. Package hooks, agents, skills, output style and workflows as one plugin; reduce the installers to CLAUDE.md, env and permissions.

  7. Run a guard cull against the built-ins, using your existing guard-log read.

Step 1 is a setting only you can change. I can build step 3, the `lane` workflow, as a draft PR in claude-settings from this thread whenever you want.
