Shared iOS Kit Question

Should your iOS apps share a kit repo?

A consultation for shiv, Oct 27. Checked at claude-settings 54be9f1, home-app 360a31f, degen f0617bd, mailaudit 37d4e7d, ios-adblock 78fb749 (each repo's main).

Short answer: you want one standard, not a new repo. You're not doing anything wrong.

You expect every iOS app to work the same way: the same build, tests, phone install and TestFlight path. Each app was built in its own session, so each one picked its own path. Each repo also got some things right, so the standard below takes the best habit from each repo and calls it the gold standard.

That standard belongs in claude-settings as one written page and a few checks, so every session in every iOS repo follows it. It does not need a new repo. The only code all four apps really share is the ship tool, and that already lives in claude-settings. Getting there is c47 ("one account file for iOS shipping"), plus one visit per repo to close the gaps in the table.

Your four options

A. One iOS standard in claude-settings, then one visit per repo my pick

How it works: claude-settings gets one page, "iOS apps", that holds the gold-standard column above, plus checks that flag a repo that drifts from it. The ship and simulator tools live beside it. c47 runs first. Then each app gets one visit that closes its gaps in the table.

You gainEvery app behaves the same way for you. A new iOS app starts at the standard. Sessions stop inventing their own path.
You loseFour repo visits of work. Swift helpers such as the keychain wrapper stay copied in each app, which is a small and known cost.

B. A separate shared iOS kit repo

How it works: a new repo holds a Swift package (keychain, sockets, maybe UI pieces) and project templates. Each app adds it as a pinned dependency.

You gainOne copy of a few hundred lines of helper code, and a template for a fifth app.
You loseA fifth repo, with its own CI and versions. Every kit change needs a version bump in four apps. mailaudit is public, so a private kit breaks its CI. The standard and the tools still have to live in claude-settings, because that is where sessions read their rules.

C. A, plus a shared Swift package later

How it works: A now. A shared package comes only when a fourth app needs the keychain wrapper, or the same bug turns up in two copies.

You gainEverything in A, and a written trigger for the kit.
You loseNothing now.

D. No change

You gainNo work.
You losemailaudit stays broken, and each app keeps drifting its own way.

My pick is A, with C's trigger written down. You plan to build more apps, so A also gets a "new iOS app" starter in claude-settings. It sets up a fresh app at the gold standard on day one: a project.yml, the same make targets, a Kit package for the logic, the CI workflow and an ios-ship entry. C's trigger will likely come with the next app. When it does, the shared package is public and holds only small helpers (keychain, sockets, haptics), never screens or colours.

Portability

  • The iOS standard, ship tool and simulator tool: yes, to every repo that ships an iOS app (home-app, degen, mailaudit, ios-adblock). Not to q_max, banchi or joyous, which ship none.
  • A Swift kit repo: no, not now. The overlap is too small to pay for a fifth repo.
