CI options: what runs when (claude-settings)

2026-10-27 · @u_SJaVBdDHgMim0rnhu3gT0g

Short answer

claude-settings ran about 16,800 runner-minutes a week of CI over the last two weeks. Almost 40% of it is the full run after each merge to main, and that run ended green only 4 times in 48 last week. So the most expensive tier is also the one that tells you least.

My pick: run CI once per batch (as now), cut batches less often (when about four lanes wait, or three hours pass), drop the run on every merge to main and the nightly run, and run the full suite at milestones that the build advisor declares. Estimated result: about 2,400 minutes a week, roughly 85% less. One thing must come first: the full run's Windows and Chromium jobs keep hitting their time caps, so a milestone run would be noise until that is fixed.

One honest caveat: claude-settings is a public repo, so its standard GitHub runners cost no money (GitHub Actions billing). Here the cost is waiting time, runner slots and red noise. q_max, degen, joyous and ios-adblock are private, so the same rule saves real minutes there.

Where q_max and degen sit

q_max already does most of the pick; degen adds the milestone idea; neither drops the run on main.

  • q_max, read at its main. D-695 (checks run in tiers: narrow on a branch, full on main): a lane runs only the test files its change reaches; main runs the full npm test after each merge; the full browser sweep runs only when you dispatch it. D-762 (only an integration batch runs CI; no nightly run): any PR that is not a batch runs no job, and the nightly is off because it billed about 60 minutes a night. D-718 (CI spend) records why: about 9,400 minutes in 5.8 days, 31 minutes per PR push. D-797 (a lane runs the tests its change reaches) found that picking tests by change does not pay for a batch: 13 of 20 batches still needed every test file. It pays only for a lane.

  • degen, rule tests-once-per-batch: a batch is cut at a milestone, when one objective's lanes have all landed, and is tested, deployed and sent to TestFlight one time. A lane runs only its own tests. No check enforces it yet. Its check.yml still runs on every push to main and has a nightly schedule.

  • claude-settings today: lanes stay drafts and skip CI; one ready batch PR runs a scoped CI; every merge to main runs everything; a nightly runs everything. It is q_max's shape plus a nightly, with batches cut about 8 times a day.

The options

Each option is a rule for what runs at four moments: per lane, per batch, per merge to main, and per milestone. A milestone is a moment the build advisor names, such as a roadmap phase change, every fifth batch, or before your machines pull a big change.

The options in plain terms:

  • A. q_max shape (drop the nightly; no CI on a lone lane). Catches: everything today does, one run later at worst. Misses: nothing new. Saves only about 15%, because the run on main stays.

  • B. No run on main. Catches: every defect the batch scope reaches, before it lands. Misses: a defect in a suite the scope skipped, such as the full Windows merge shards that run only off a PR, until the next milestone. Also misses a clash between two batches that merge back to back, unless the merge tool refuses a batch whose base moved since its run. That is unknown today and must be checked.

  • C. My pick: B plus fewer, larger batches. Catches: the same as B. Misses: the same as B, and a lane waits up to 3 hours longer to land. A red batch has more lanes to sort out, but the drop-the-lane rule already handles that.

  • Gold standard. Google runs a fast presubmit per change, then runs all affected tests after submit, in batches, and splits a red batch to find the culprit (Software Engineering at Google, ch. 23). GitHub's merge queue tests each PR as merged with main and the PRs ahead of it (GitHub docs). It catches the most, and it costs more than C. The gold standard assumes a full run you can trust, which claude-settings does not have yet.

The minutes for A, B, C and the gold standard are estimates from the measured per-run figures, not measurements. C assumes about 3 batches a day, so 21 batch runs times 1.8 times 59 minutes, plus two milestone runs of about 100 minutes.

The pick, and what it needs first

Pick C. It does what you described for q_max: let a lot land, then check. It cuts about 85% of the minutes, and it removes the run that is red or cut off five times in six.

Three things must land with it, in this order:

  1. Make the full run trustworthy. Fix or re-cap the Windows merge shards, the Windows guard and rest jobs, and the Chromium install, so a milestone run can end green. Without this, a milestone run is noise, and the full suites have no working tier at all.

  2. Prove a batch against today's main. Branch protection on main has strict set to false (checked by API today), so a batch can merge after main moved since its run. Either turn strict on, or have the merge tool refuse a batch whose base moved since its last green run. With fewer batches, main moves less, so this re-run is rare.

  3. Change the rules. The global CLAUDE.md rules on batches (git-integration-branch-merge, one integration PR per batch) and on proofs (roles-each-layer-proves-once, each layer proves a change once) gain the batch cadence and the milestone run. Then gates.yml drops its push-to-main trigger and its nightly, and keeps dispatch.

Risks you accept with C:

  • A defect that only the full Windows or macOS suites see waits for the next milestone. The build advisor can dispatch one early when a batch touches merge/, hooks/guard.py or the installers.

  • Lanes wait longer to land, up to 3 hours.

  • Unmeasured: how many defects the run on main caught that the batch run missed. Most main runs ended at a time cap, so the number is probably small, but I could not measure it.

Port to other repos: yes, as a global rule. q_max is closest already and needs only the milestone run in place of its run after each merge. degen needs its push and nightly triggers dropped. joyous and ios-adblock are private, so they gain the most money. Each repo changes its own workflow at its next visit, after you agree the plan.
