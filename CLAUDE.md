# How I work, in every repo

**Outcomes first.** Judge every rule, check, and design by the outcome for the person
the software serves.<!-- rule:outcomes-judge-by-outcome --> Treat a recorded decision as an argument, not a law. Never defer to a rotted argument.<!-- rule:outcomes-decision-is-argument --> When a decision looks
stale, name the record and the sentence. Measure the claim, or say "unmeasured". Name the
outcome the decision protected and what protects it now. Propose a fix. Wait for my grant.<!-- rule:outcomes-stale-decision-protocol --> A failing test is a claim, not law. Re-point it, red then green, or fix the
defect it found. If it may be stale and no ruling covers it, use the protocol
above.<!-- rule:outcomes-tests-are-statements --> My grant covers the act it names, never a
variant. My ruling covers each test and path that expects exactly what it ruled out; cite it
with its time.<!-- rule:outcomes-grant-covers-named-act --> Once ready, turn each rule below
into a hook or check. This file is the fallback, not the enforcement. Tracking, logging, monitoring or measuring reads on demand inside a process already running, never on a timer or on every tool call, and starts no new long-lived process. Each states its cost in its record (process starts, files written, how often), and a test proves that cost. A log needs a named reader, or it is not written. An agent's own write may read the machine load once, inside the guard hook already running for it (decision machine-load-brake).<!-- rule:outcomes-mechanize-rules -->

**Roles, if this session can spawn agents.** Pick the session's shape from my request: solo, one
lane, or coordinator (`session-tiers`, the session shapes). One lane: one line of work, run with its own agents; a lane session is one, and runs Opus (`agent-model-cap`). Coordinator: a standing build. It starts triage and the batch runner, then lane sessions. Say the pick in one line before you start.<!-- rule:roles-pick-mode-from-request --> Solo: the request is a short list of edits with
nothing to run in parallel. Build them yourself.<!-- rule:roles-solo-builds-short-edit-list --> In solo, a fresh reviewer reads the diff before
merge only when it touches a rule's behaviour, a guard's or check's verdict, or program logic. Other edits merge on passing checks alone.<!-- rule:roles-solo-reviews-logic-diffs-only --> A shape can grow: solo to one lane, one lane to coordinator. Say each switch in one line.<!-- rule:roles-solo-grows-switch-to-orchestrate --> Every session that spawns agents is an orchestrator.
Every orchestrator but a solo session plans, briefs, verifies, reports. It writes records, docs, and briefs. It builds
only when the change cannot move a verdict, one bounded command proves it, and the report
names both. A change that touches a rule's behaviour, a guard's or check's verdict, or product code a
reviewer must see goes to a lane, at
any size. Keep a fix under 40 lines, against reading cost alone.<!-- rule:roles-orchestrator-never-builds --> Each agent is one role: builder, reviewer,
designer, design reviewer, or Explore, never two. A lane that touches a screen gets a designer before
the builder and a design reviewer after it.<!-- rule:roles-one-role-per-agent --> A workflow agent takes the builder or reviewer role through `agentType`. Each
agent runs its role's model and effort from `agent-model-cap`, the model-per-role table.<!-- rule:roles-sonnet-is-the-default --> Sonnet is
the ceiling, except Plan, the built-in advisor (`advisorModel`), the designer, the design reviewer,
and a builder's third try (`roles-third-round-steps-up`), which run Opus. Any other agent runs Opus, or any
model above Sonnet, only on my grant for the spawn I name, or by override: `opus 2h` for a time,
`opus builders 2h` for one role.<!-- rule:roles-sonnet-is-the-ceiling --> When a task is Opus-shaped (long-horizon, whole-codebase, or many-hour
autonomous work), say so in one line before you dispatch, name why, and offer the switch. Then
wait for my grant.<!-- rule:roles-opus-shaped-say-so --> Owner raises Opus. The guard asks before an env write raises the agent model.<!-- rule:roles-opus-override-guarded --> A brief carries the task, the files, governing rulings, failure classes from
`outcomes-tests-are-statements`, and the check that proves the task done—in the fewest words. It
specifies a report cap in lines sized to the choice it
feeds. With no cap named, the cap is 25 lines.<!-- rule:roles-brief-contents --> Each layer proves a change once. A
test-author writes the new cases first and shows them red on the old code. The builder changes
product code until they go green. CI is the merge check for the full suites and the mutation tests. A
reviewer hunts bypasses and false alarms and never replays a passing run. The test-author's
recorded red run is enough. A reviewer re-runs it only when that record is missing or
in doubt. The orchestrator reads CI once, on the head it merges.<!-- rule:roles-each-layer-proves-once --> A change gets at most three review rounds. A change that only deletes and adds nothing gets one round. It skips rounds 2 and 3 and the net-value test, unless round 1 finds a safety hole Claude could hit in normal work (`hold-unsafe-after-round-3`, net-value hold after round 3). Rounds 1 and 2 still fix the defect (`outcomes-tests-are-statements`). After round 3, a change that changes a guard or check (`hold-unsafe-after-round-3`, net-value hold after round 3) gets the net-value test. The round-3 reviewer judges its net safety value against main: safety holes closed against safety holes opened, weighted by expected harm. A change that changes no guard or check skips the test and merges on green. A safety hole is a guard or check that lets through an act that main refuses or asks about. Turning a main refusal into an ask is also a safety hole. For any guard or check, an act counts only if Claude could write it by mistake or from a misread task. A form only an attacker would write does not count (`guard-guards-mistakes-only`, guards stop Claude's mistakes, not an attacker). An act that my typed override lets through is not a safety hole (`owner-override`, my typed override). Zero or positive net value merges on green. For every change, each open finding becomes a debt or a note, pointing to its decision (`roles-findings-are-debts-or-notes`). A change with negative net value is held: remove it from the batch, so the rest merges green. A held change is parked. It gets no fix lane and no more work until the owner decides. After round 3, red CI is not a named safety hole: split it, ship the passing part, and open the red part as a new lane. That lane starts at round 1, try 1. Its brief records what failed; if no split works or the test looks stale, ask the owner (`outcomes-stale-decision-protocol`); never weaken a test to reach green. A red batch still drops the lane first (`git-integration-branch-merge`); the split happens in that lane's own fix. A held change that is also red gets no red-CI split.<!-- rule:roles-review-cap-three --> A known gap is a debt only if Claude is likely to hit it in normal work. Write one record per debt in the repo's debt store, and point it to its decision where one exists. Any other finding is one line in the store's notes file. A note becomes a debt after a real incident.<!-- rule:roles-findings-are-debts-or-notes --> Third try: Opus. A builder's third try runs after review round 2 fails; its brief carries `Round 3 of 3`. Reviewers run Sonnet from round 2 on; round 1 uses the role's model.<!-- rule:roles-third-round-steps-up --> Resume a dead agent by name, never fresh. A finished reviewer's worktree is gone, so send a fresh reviewer the prior report instead.<!-- rule:roles-resume-by-name -->

**Parallelism, two tiers.** Fan tasks out to agents now, each in its own checkout. A
workflow run, the ultracode path, is a fan-out too. Give each workflow agent that writes
files `isolation: 'worktree'`.<!-- rule:parallelism-each-own-checkout --> A read-only workflow agent shares the caller's checkout.
Give an isolated workstream its own lane and orchestrator, briefed once.<!-- rule:parallelism-own-lane-orchestrator --> Never let lanes
talk mid-task. Message a peer only when a branch must hear something that changes its
work.<!-- rule:parallelism-no-mid-task-talk --> Argue "at max parallelism" by naming the open lanes, never by assuming the claim.<!-- rule:parallelism-argue-max-parallelism --> A brief or plan never caps lanes on its own, by a guessed number such as "one or two at a time" or "at most N lanes". An owner-named cap still holds. The load brake decides when the machine is too loaded.<!-- rule:parallelism-no-guessed-lane-cap --> When a lane ends, start in the same turn each queued item the owner asked for whose questions are all answered. A follow-up the session found is treated as asked when it serves my goal and can be undone, such as an archive push or a CI fix lane. Queue it, start it without asking me, and name it under Done, or under Next while it waits. Ask first for an act that cannot be undone, a change to my goal, or work in a repo other than the one the session started in. A message to a person, spend, a delete with no copy, and a deploy or change to a live system or device cannot be undone. A standing grant for that act still holds. A follow-up never lifts a wait that another rule here makes, such as a merge. Stop only where a rule here waits for my grant, for a test only I can run, or for the load brake.<!-- rule:parallelism-keep-going -->

**Shared trees.** No destructive git. Destructive git loses another agent's work in a shared tree.<!-- rule:shared-trees-no-destructive-git --> Push an unmerged branch to `archive/<branch>` on origin, or a new archive name if taken. Once the push succeeds, delete it locally with no question: nothing is lost.<!-- rule:shared-trees-archive-then-delete --> Kill only yours. Others' servers and processes are not yours to stop, unless my override covers the stop (`owner-override`, my typed override).<!-- rule:shared-trees-no-machine-wide-kill --> Give one checkout to each concurrent agent.<!-- rule:shared-trees-one-checkout-per-agent --> A branch switch
is a whole-tree act. Give each checkout its own ports and data.<!-- rule:shared-trees-own-ports-data --> Confirm which checkout
and branch you stand in before any git write or merge.<!-- rule:shared-trees-confirm-before-write --> Re-verify every edit after an
incident.<!-- rule:shared-trees-reverify-after-incident --> A delete names its target as an absolute or quoted-variable path, never after a cd.<!-- rule:shared-trees-delete-names-absolute-path -->

**Git, if this repo uses pull requests.** Move main only by pull request, merged only
when I name the act, or under a repo grant.<!-- rule:git-main-only-by-pr -->
Never merge failing CI.<!-- rule:git-never-merge-failing-ci --> While a batch's integration PR has a CI run in progress, nothing merges to main, by any session or by me.<!-- rule:git-no-merge-during-batch-ci --> A session that waits on CI sets a timed check-in when it starts to wait, and again after each red job, each wider apart. A run with a red job sends no "all checks done" wake.<!-- rule:git-ci-wait-checks-in --> A run that ends red posts one PR comment, which wakes the session that watches the PR (`ci-done-comment`).<!-- rule:git-ci-done-comment-wakes --> Keep command output. Discarded output hides failures from the reader.<!-- rule:git-never-discard-output --> A refusal's printed remedy
never names the forbidden target.<!-- rule:git-remedy-never-names-target --> Never allocate a numbered record on a branch.
Write a slug of 32 characters or fewer. Claim the number at merge. Name a lane by its branch slug, never by a session number.<!-- rule:git-slug-then-claim-number --> Ids, not paths. A path breaks when its file moves.<!-- rule:git-cite-by-id --> Give each record its
own file, one folder per kind.<!-- rule:git-record-own-file-per-kind --> One record per question. When its ruling changes, rewrite the record in place. Open a record only for a new question.<!-- rule:git-one-record-per-question --> Batch lane PRs that pass their local checks into one integration branch. Keep
each lane's own commit. A lane joins the batch after the review the roles rules require. Only the integration PR goes ready, and its run is the only CI run for the batch. Never push to a ready PR while its CI run can still go green; a late lane joins the next batch. Once a job is red, push the lane drop or the lane fix at once. The push cancels the old run, and the new run is the re-run. Each lane PR stays a draft until the integration PR merges. Then each lane PR closes as replaced. A lone lane is its own integration PR. A red integration run: read the failing job. Find the lane whose files it touches. Drop that lane, with any lane that depends on it: rebuild the branch from main without them, never revert. A lane dropped by a revert re-applies its diff after it merges main, and checks that each file is there. A job that ends at its cap with no red CI step is re-capped or split, not a reason to drop the lane. A lane red on form (record format, version bump, lint), not on a behaviour test, is fixed and re-merged instead, if the fix is a few lines in its own files. That holds only for the lane's first such fix in this batch; a second red drops it. A CI lint red that `bin/ste-changed` passes, while it blames an old ste-lint pin, is not a strike (`action-pins-follow-sessions`, CI pins follow the session's tools). The session moves that pin to claude-settings main in a lane of its own, with no question. Its reviewer checks only that the lane changes pin lines alone, to a main commit that descends from the old pin. The fix goes on the lane branch, never the batch branch. Run CI again, once, and merge the rest. Fix the dropped lane in its own lane. It joins the next batch after its fix. A held lane (`roles-review-cap-three`) is the exception: it is dropped and parked, and gets no fix lane until the owner decides. Never fix inside the integration branch. Before you open a PR, check other sessions' open PRs and offer to batch. A repo may name one session to batch PRs and run each merge, on the owner's grant.<!-- rule:git-integration-branch-merge -->

**Verification.** If the repo has screens, check each screen at every size and theme it
ships in. Give a verdict per screen, never a description.<!-- rule:verification-screens-verdict -->
Prefer a headless or isolated browser over my own, and use my login only when needed.<!-- rule:verification-browser-login-only-needed --> Before
a window or a screen capture lands on my screen, say so in one line.<!-- rule:verification-announce-own-screen --> Trust a guard only once it goes red on
the defect it guards.<!-- rule:verification-trust-guard-after-red --> A guard that goes red when nothing is wrong is
spent, because the reader learns to scroll past it. Before you route around a refusal, read the
guard's record. If it seems to allow the act, your report flags a possible false alarm.<!-- rule:verification-cry-wolf-guard-is-spent --> A green check proves only its platform
and the states its fixtures build.<!-- rule:verification-green-proves-only-its-fixtures --> A recovery control must not depend
on the state it recovers, or it fails on the one day it is needed.<!-- rule:verification-recovery-independent-of-state --> Verify long work against the repo, not your status line.<!-- rule:verification-verify-against-repo --> Never dry-run a refusal list.<!-- rule:verification-never-dry-run-refusal-list --> Take the newest version that passes its checks. Read its changelog
first. If it breaks a check, pin the newest one that passes and say why.<!-- rule:verification-newest-that-passes --> If this repo lints markdown, give every
published number and path a checked reader.<!-- rule:verification-checked-reader-for-numbers --> Verify a claim before you
rely on it, a document's own claims too. Report a read that could not run as unknown,
never as clear or broken.<!-- rule:verification-report-unknown-reads -->

**Tokens.** Never load a long document whole. Read one record, one section, or a
rendered view.<!-- rule:tokens-never-load-whole-doc --> A verification command's answer is its verdict, not its stream. Get the
verdict with one bounded command. Never scroll a log to find out whether something
passed.<!-- rule:tokens-verdict-not-stream --> Run every verification command through `verdict <cmd>`, which prints the verdict and keeps the full output in a log.<!-- rule:tokens-run-through-verdict --> Point a brief at files. Never paste them in.<!-- rule:tokens-point-brief-at-files --> Read an agent's report,
never its transcript.<!-- rule:tokens-read-report-not-transcript --> When compacting, keep the files, the commands, each ruling's home, and the pid and port of each server still running.
Drop the narration.<!-- rule:tokens-compacting-keep-essentials --> Move a CLAUDE.md section that matters only under one folder to a path-scoped rule. Keep it when it is needed before the first file read.<!-- rule:tokens-folder-rules-load-by-path --> Before you answer how code in a repo works, read its `docs/map/`.<!-- rule:tokens-read-map-first -->

**Building.** Never guess an answer the code should give you.<!-- rule:building-never-guess-answer --> A port or redesign keeps the existing app's behaviour as the default. Each choice cites where it was read, file and symbol. A question goes to the owner only when the work departs from that behaviour, says so in a "Departs from:" line, and is never marked blocking. A question the code or a standing grant answers is not asked.<!-- rule:building-port-keeps-behaviour --> Surface ambiguity instead
of resolving it silently.<!-- rule:building-surface-ambiguity --> Never drop an item without saying so.<!-- rule:building-never-drop-item-silently --> Give
each capability one home, and call it from everywhere. Extend that home before you
build a second. A duplicate needs a stated reason.<!-- rule:building-one-home-per-capability --> A guard's or check's allow list must point at the constant
the code emits, never a copy of it.<!-- rule:building-allow-list-is-the-constant --> Build a new guard or check rule
only against a named incident, a measured risk, or a likely risk: one Claude is likely to hit in normal work. Its record says which of the three it is, and the date it landed. At each cull, delete a guard rule that never fired in guard.log since it landed and whose record names no incident, with its code and tests.<!-- rule:building-guard-needs-incident --> Fix the cause, not the symptom. Name a
bandaid as one when it is the right call.<!-- rule:building-fix-cause-not-symptom --> Scan source code with the language's own parser or tokenizer when the repo has one. Otherwise, match strings and comments in one pass. Test every scanner on comment openers (`/*`, `//`, `#`) inside strings, on a multi-line template literal, and on a lone quote in text, such as JSX `<p>Don't</p>`.<!-- rule:building-scanner-respects-strings --> A capability no user can reach is not built. A design living
only in chat is not done. Land the design in its spec or decision record now, or declare
the design abandoned.<!-- rule:building-land-design-or-abandon --> Memory stays on, as short-term notes. Once a fact or ruling has a tracked home on main, delete its memory
file and its `MEMORY.md` line.<!-- rule:building-memory-is-short-term --> Comment only what complex code does and why. Never narrate history or review rounds.<!-- rule:building-comments-say-why -->

**Speak plainly.** Give every id a short plain name the first time it appears, like "D12, short titles for
records". That covers decision and debt ids, roadmap step ids, lane numbers, PR and issue numbers, commit hashes, rule anchors, and hook and script names. Never cite a bare id. A numbered id carries no order, so state the work order in words.<!-- rule:speak-cite-id-plus-gloss --> `GLOSSARY.md`, beside this file, gives each workflow thing one name. Use that name. A repo glossary adds its own terms and never defines a term from that file again. Write only the term the repo uses for a thing, but read my words by meaning. When I name a thing another way, act on it, answer with that term, and ask which I meant only when two things fit.<!-- rule:speak-one-name-per-thing --> Never explain a rule in a paragraph.<!-- rule:speak-never-explain-in-paragraph --> Rewrite
superseded text in place. Keep only what is true now, in the fewest words. Git keeps
the history.<!-- rule:speak-rewrite-superseded-in-place -->

**Output.** Write plainly: short sentences, one term per meaning, no filler.<!-- rule:output-write-in-ste -->
Rules for replies to me, and not to agents, live in the `shiv-stylisms` output style.
Never paste a passing run's output into a report. Give the verdict.<!-- rule:output-never-paste-passing-output -->
Bring my choices as a question with options and a recommendation.<!-- rule:output-bring-decisions-as-question --> An answer to a question I bring is a ruling. The report may hold it as a scratch note. Move it to its question's record, or to a deferred item. Cite that home before the work it governs merges. Mark a process answer process-only.<!-- rule:output-answer-has-a-home --> Bring each question to me. The question names what the session does meanwhile, or that it waits. Keep working on what does not depend on the answer. Do not ask for a pick that `parallelism-keep-going` lets you take with no question. Take it and name it under Done. Ask in chat first. At each wake, if I have not answered in chat for 5 minutes, send the question to the waiting page's writer (skill `waiting-page`). No timer counts the 5 minutes. A lane has no chat with me, so its question goes in its report. Send my chat answer to the writer too, so every question and answer ends in the page's record. While an agent, a lane or a background command of this session runs, or starts in the same response, never open a question box. The box stops the session until I answer, and nothing stops what runs. Ask in the reply, keep orchestrating, and read my answer at the next turn. A session may end its turn: each agent's end wakes it. A session that started another session never opens the box. The started session may wait on it. Ask in the reply. In any other session with nothing running, ask in the box. Before asking, read the repo's CLAUDE.md for standing grants. A grant the owner gives in chat lands in the repo's CLAUDE.md or the merge tool's config, never only in a handoff. My save on that page is my grant for the item it answers. Each item names its owning session. That session reads its own answers at each wake, and nobody relays them. The built-in advisor (`advisorModel`) is a second opinion on the session's own work. It answers no question for me and decides nothing, so it lifts no guard and grants no override.<!-- rule:questions-go-to-owner -->

**Reports, in order:** Done, Deviations, Input Needed, Next.<!-- rule:reports-order-of-labels --> Done: one line per item, BUILT,
RECORDED, or OTHER. BUILT and RECORDED carry a PR or commit. Per label, one item inline, several as bullets.<!-- rule:reports-done-format --> A Done item that agents built or reviewed names each one's role and model, such as "(builder sonnet, reviewer sonnet)".<!-- rule:reports-done-names-models --> Drop a label
that does not apply.<!-- rule:reports-drop-unused-label --> An orchestrator's report holds an `Unstarted:` line under Next: each queued item with every question answered that it left unstarted, with its reason, or `none`.<!-- rule:reports-name-unstarted-items --> No report when nothing landed.<!-- rule:reports-no-report-when-nothing-landed --> At each batch merge, the report also gives four pace numbers, as OTHER items under Done. A lone lane's merge is a batch merge too. Read them at report time, from git, GitHub and guard.log. Number one: wall-clock from first lane commit to merge. Number two: lanes run, and the most running at once. Number three: minutes with no lane running, and the reason, or "unknown". Number four: brake refusals with their readings: the `load-brake` lines in guard.log whose time falls between the first lane commit and the merge. Cost: git, GitHub and guard.log reads, once per batch merge. It adds no log, watcher or timer.<!-- rule:reports-batch-pace-numbers --> When a session's last PR has merged and no lane is open, its final report offers one command under Next: `python3 ~/.claude/janitor/sweep.py --root <repo> --attended --fast`, preview first, then with `--confirm`. Drop the offer when nothing is left to remove.<!-- rule:reports-offer-sweep-after-merge -->
