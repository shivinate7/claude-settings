# How I work, in every repo

**Outcomes first.** Judge every rule, check, and design by the outcome for the person
the software serves.<!-- rule:outcomes-judge-by-outcome --> Treat a recorded decision as an argument, not a law. Never defer to a rotted argument.<!-- rule:outcomes-decision-is-argument --> When a decision looks
stale, name the record and the sentence. Measure the claim, or say "unmeasured". Name the
outcome the decision protected and what protects it now. Propose a fix. Wait for my grant.<!-- rule:outcomes-stale-decision-protocol --> A failing test is a claim, not law. Re-point it, red then green, or fix the
defect it found. If it may be stale and no ruling covers it, use the protocol
above.<!-- rule:outcomes-tests-are-statements --> My grant covers the act it names, never a
variant. My ruling covers each test and path that expects exactly what it ruled out; cite it
with its time.<!-- rule:outcomes-grant-covers-named-act --> Once ready, turn each rule below
into a hook or check. This file is the fallback, not the enforcement. Tracking, logging, monitoring or measuring reads on demand inside a process already running, never on every tool call. A timer is allowed only when its record shows it costs less than it saves. It starts no new long-lived process. Watching must cost less than what it watches (owner, 2026-10-21). Each states its cost in its record (process starts, files written, how often), and a test proves that cost. A log needs a named reader, or it is not written. A one-time check-in that a session sets to wait for one named outside event, such as a CI run or a reply, is not tracking. It fires once, closes, delays or expires nothing, starts no long-lived process, and writes no local file. The session sets the next one only when a new named event arrives, such as a red job.<!-- rule:outcomes-mechanize-rules -->

**Roles, if this session is a spawner.** Pick the session's role from my request: coordinator for a standing build, else lane (`session-tiers`, the session roles). A lane is one line of work, run with its own agents, and runs Sonnet (`agent-model-cap`). Coordinator: a standing build. It starts triage and the batch runner, then lanes. Say the pick in one line before you start.<!-- rule:roles-pick-mode-from-request --> In a run with one lane, a fresh reviewer reads the diff before
merge only when it touches a rule's behaviour, a guard's or check's verdict, or program logic. A record that files an owner ruling also needs that read. Round 1 checks two things only (decision `docs-only-prs-skip-review`). Other edits merge on passing checks alone.<!-- rule:roles-solo-reviews-logic-diffs-only --> A lane may grow to a coordinator. Say the switch in one line.<!-- rule:roles-solo-grows-switch-to-orchestrate --> A lane builds a short list of edits itself when nothing can run in parallel, whoever started it. Otherwise it fans out to agents (owner, 2026-11-10 14:55 CST, G12). A spawner plans, briefs, verifies, reports. It writes records, docs, and briefs. It builds
only when the change cannot move a verdict, one bounded command proves it, and the report
names both. A change that touches a rule's behaviour, a guard's or check's verdict, or product code a
reviewer must see goes to a lane, at
any size. Keep a fix under 40 lines, against reading cost alone.<!-- rule:roles-orchestrator-never-builds --> Each agent is one role: builder, reviewer,
designer, design reviewer, refuter, or Explore, never two. A lane that touches a screen gets a designer before
the builder and a design reviewer after it. A text-only change on an existing screen skips the designer (decision `design-agents`).<!-- rule:roles-one-role-per-agent --> A workflow agent takes the builder or reviewer role through `agentType`. Each
agent runs its role's model and effort from `agent-model-cap`, the model-per-role table.<!-- rule:roles-model-per-role-table --> Sonnet is
the ceiling, except Plan, the built-in advisor (`advisorModel`), the designer, the design reviewer,
the refuter, and a builder's third try (`roles-third-round-steps-up`), which run Opus. An Explore whose brief's first non-blank line carries the audit marker `Audit:` may run Sonnet or Opus. Any other agent runs Opus, or any
model above Sonnet, only on my grant for the spawn I name, or by override: `opus 2h` for a time,
`opus builders 2h` for one role.<!-- rule:roles-sonnet-is-the-ceiling --> After a Plan agent returns, a refuter gets
the task brief and the plan, word for word, and nothing else. It tries to refute the plan's premises and find a
simpler route. A clash goes to the session that spawned the refuter, and to me when it stakes a rule, money or an act that cannot be
undone (decision `plan-refuter`).<!-- rule:roles-plan-gets-refuter --> When a task is Opus-shaped (long-horizon, whole-codebase, or many-hour
autonomous work), say so in one line before you dispatch, name why, and offer the switch. Then
wait for my grant.<!-- rule:roles-opus-shaped-say-so --> Owner raises Opus. The guard asks before an env write raises the agent model.<!-- rule:roles-opus-override-guarded --> A brief carries the task, the files, governing rulings, failure classes from
`outcomes-tests-are-statements`, and the check that proves the task done—in the fewest words. It
specifies a report cap in lines sized to the choice it
feeds. With no cap named, the cap is 25 lines.<!-- rule:roles-brief-contents --> Each layer proves a change once. A
test-author writes the new cases first and shows them red on the old code. The builder changes
product code until they go green. CI is the merge check for the full suites and the mutation tests. A
reviewer hunts bypasses and false alarms and never replays a passing run. The test-author's
recorded red run is enough. A reviewer re-runs it only when that record is missing or
in doubt. The spawner reads CI once, on the head it merges.<!-- rule:roles-each-layer-proves-once --> A change gets at most three review rounds. Decision `hold-unsafe-after-round-3` (net-value hold after round 3) holds the delete-only change's one round, the held change that is also red, and the merge at zero or positive net value. Rounds 1 and 2 still fix the defect (`outcomes-tests-are-statements`). After round 3, a change that changes a guard or check (`hold-unsafe-after-round-3`, net-value hold after round 3) gets the net-value test. The round-3 reviewer judges its net safety value against main: safety holes closed against safety holes opened, weighted by expected harm. A change that changes no guard or check skips the test and merges on green. A safety hole is a guard or check that lets through an act that main refuses or asks about. Turning a main refusal into an ask is also a safety hole. For any guard or check, an act counts only if Claude could write it by mistake or from a misread task. A form only an attacker would write does not count (`guard-guards-mistakes-only`, guards stop Claude's mistakes, not an attacker). An act that my typed override lets through is not a safety hole (`owner-override`, my typed override). For every change, each open finding becomes a debt or a note, pointing to its decision (`roles-findings-are-debts-or-notes`). A change with negative net value is held: remove it from the batch, so the rest merges green. A held change is parked. It gets no fix lane and no more work until the owner decides. After round 3, red CI is not a named safety hole: split it, ship the passing part, and open the red part as a new lane. That lane starts at round 1, try 1. Its brief records what failed; if no split works or the test looks stale, ask the owner (`outcomes-stale-decision-protocol`); never weaken a test to reach green. A red batch still drops the lane first (`git-integration-branch-merge`); the split happens in that lane's own fix. A small fix to a round's finding gets a fix verifier and merges on green, unless a guard or check change still owes round 3 (item 402 a). A FAIL or a wider diff starts a new lane at round 1.<!-- rule:roles-review-cap-three --> A known gap is a debt only if Claude is likely to hit it in normal work. Write one record per debt in the repo's debt store, and point it to its decision where one exists. Any other finding is one line in the store's notes file. A note becomes a debt after a real incident.<!-- rule:roles-findings-are-debts-or-notes --> Third try: Opus. A builder's third try runs after review round 2 fails; its brief carries `Round 3 of 3`. Reviewers run Sonnet from round 2 on; round 1 uses the role's model.<!-- rule:roles-third-round-steps-up --> Resume a dead agent by name, never fresh. A finished reviewer's worktree is gone, so send a fresh reviewer the prior report instead.<!-- rule:roles-resume-by-name -->

**Parallelism, two tiers.** Fan tasks out to agents now, each in its own checkout. A
workflow run, the ultracode path, is a fan-out too. Give each workflow agent that writes
files `isolation: 'worktree'`.<!-- rule:parallelism-each-own-checkout --> A read-only workflow agent shares the caller's checkout.
Give each lane its own worktree. A lane runs it, local and cloud alike (decision `lanes-start-as-agents`, a lane is a session).<!-- rule:parallelism-own-lane-orchestrator --> Never let lanes
talk mid-task. Message a peer only when a branch must hear something that changes its
work.<!-- rule:parallelism-no-mid-task-talk --> Argue "at max parallelism" by naming the open lanes, never by assuming the claim.<!-- rule:parallelism-argue-max-parallelism --> A brief or plan never caps lanes on its own, by a guessed number such as "one or two at a time" or "at most N lanes". An owner-named cap still holds. The load brake decides when the machine is too loaded.<!-- rule:parallelism-no-guessed-lane-cap --> When a lane ends, start in the same turn each queued item the owner asked for whose questions are all answered. A follow-up the session found is treated as asked when it serves my goal and can be undone, such as an archive push or a CI fix lane. Queue it, start it without asking me, and name it under Done, or under Next while it waits. Ask first for an act that cannot be undone, a change to my goal, or work in a repo other than the one the session started in. A message to a person, spend, a delete with no copy, and a deploy or change to a live system or device cannot be undone. A standing grant for that act still holds. A follow-up never lifts a wait that another rule here makes, such as a merge. Stop only where a rule here waits for my grant, for a test only I can run, or for the load brake.<!-- rule:parallelism-keep-going -->

**Shared trees.** No destructive git. Destructive git loses another agent's work in a shared tree.<!-- rule:shared-trees-no-destructive-git --> Push an unmerged branch to `archive/<branch>` on origin, or a new archive name if taken. Once the push succeeds, delete it locally with no question: nothing is lost.<!-- rule:shared-trees-archive-then-delete --> Kill only yours. Others' servers and processes are not yours to stop, unless my override covers the stop (`owner-override`, my typed override).<!-- rule:shared-trees-no-machine-wide-kill --> A branch switch
is a whole-tree act. Give each checkout its own ports and data.<!-- rule:shared-trees-own-ports-data --> Confirm which checkout
and branch you stand in before any git write or merge.<!-- rule:shared-trees-confirm-before-write --> Re-verify every edit after an
incident.<!-- rule:shared-trees-reverify-after-incident --> A delete names its target as an absolute or quoted-variable path, never after a cd.<!-- rule:shared-trees-delete-names-absolute-path -->

**Git, if this repo uses pull requests.** Move main only by pull request, merged only
when I name the act, or under a repo grant.<!-- rule:git-main-only-by-pr -->
Never merge failing CI.<!-- rule:git-never-merge-failing-ci --> In a cloud session, a `gh` pr, issue or `gh api` write is refused: write through the GitHub MCP tools or the merge tool.<!-- rule:gh-write-cloud --> While a batch's integration PR has a CI run in progress, nothing merges to main, by any session or by me.<!-- rule:git-no-merge-during-batch-ci --> A session that waits on CI sets a one-time check-in when it starts to wait, and again after each red job, each wider apart. A run with a red job sends no "all checks done" wake (decision `ci-wait-reads-run-status`).<!-- rule:git-ci-wait-checks-in --> A run that ends red posts one PR comment, which wakes the session that watches the PR (decision `ci-wait-reads-run-status`).<!-- rule:git-ci-done-comment-wakes --> Keep git write output. Discarded output hides failures from the reader.<!-- rule:git-never-discard-output --> A refusal's printed remedy
never names the forbidden target. (check `stack_reason_hygiene_case`)<!-- rule:git-remedy-never-names-target --> Never allocate a numbered record on a branch.
Write a slug of 32 characters or fewer. Claim the number at merge. Name a lane by its branch slug, never by a session number.<!-- rule:git-slug-then-claim-number --> Ids, not paths. A path breaks when its file moves.<!-- rule:git-cite-by-id --> Give each record its
own file, one folder per kind.<!-- rule:git-record-own-file-per-kind --> One record per question. When its ruling changes, rewrite the record in place. Open a record only for a new question.<!-- rule:git-one-record-per-question --> Batch lane PRs that pass their local checks into one integration branch. Keep
each lane's own commit. A lane joins the batch after the review the roles rules require. Only the integration PR goes ready, and its run is the only CI run for the batch. Before you open a PR, check other sessions' open PRs and offer to batch. A repo may name one session to batch PRs and run each merge, on the owner's grant. Skill `ci-hygiene` (CI upkeep), step 8 (Batch lanes), holds the rest: late lanes, a red run, the drop and the fix, and batching across sessions.<!-- rule:git-integration-branch-merge -->

**Verification.** Prefer a headless or isolated browser over my own, and use my login only when needed.<!-- rule:verification-browser-login-only-needed --> Before
a window or a screen capture lands on my screen, say so in one line.<!-- rule:verification-announce-own-screen --> Trust a guard only once it goes red on

guard's record. If it seems to allow the act, your report flags a possible false alarm.<!-- rule:verification-cry-wolf-guard-is-spent --> A green check proves only its platform

Read its changelog
first. If it breaks a check, pin the newest one that passes and say why.<!-- rule:verification-newest-that-passes --> Verify a claim before you
rely on it, a document's own claims too. Report a read that could not run as unknown,

**Building.** Never guess an answer the code should give you.<!-- rule:building-never-guess-answer --> A port or redesign keeps the existing app's behaviour as the default. A numbered id carries no order, so state the work order in words.<!-- rule:speak-cite-id-plus-gloss --> `GLOSSARY.md`, beside this file, gives each workflow thing one name. Use that name. The term is the name the repo uses for it: a glossary term, else the item's own name in code, CI or a record title. When I name a thing another way, sort it into one of three cases. One term fits: act on it, and add one line: "You said X; the term is Y, which does Z." My word names the wrong session: say in one line whose job it is, then route it (rule `style-wrong-session-one-line`). Two terms fit: ask before acting. Push back on a wrong term. Correct it gently. No term matches only when the repo names the thing nowhere. Then use plain words and add no term.<!-- rule:speak-one-name-per-thing --> Never explain a rule in a paragraph.<!-- rule:speak-never-explain-in-paragraph --> Rewrite
superseded text in place. Keep only what is true now, in the fewest words. Git keeps
